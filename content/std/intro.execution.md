!!! tldr
    - 同一线程内的求值只有偏序。两个求值之间可能有先后（sequenced before），可能先后不定但不重叠（不定序），也可能完全无序、可以交叠。
    - 对同一内存位置的修改，如果与另一次修改或读取无序，行为未定义。`i = i++ + i` 是 UB，`i = i++ + 1` 从 C++17 起不是。
    - C++17 给 `<<`、`>>`、`=`、`[]`、`->*` 和函数调用的被调函数规定了顺序；`+`、`==` 等运算符的操作数之间，以及各个函数实参之间，仍然没有规定顺序。
    - 函数调用不会与调用者的其他求值交织：`i + f()` 的结果未指定，但不是 UB。
    - 一个完整表达式的全部求值先于下一个完整表达式。临时对象一般在完整表达式结束时销毁。

## 求值顺序只是偏序

```cpp run title="seq-std.cpp"
void g(int i) {
  i = 7, i++, i++;              // OK：i 变为 9

  i = i++ + 1;                  // OK（C++17 起）：i 自增
  i = i++ + i;                  // UB
  i = i + 1;                    // OK

  union U { int x, y; } u;
  (u.x = 1, 0) + (u.y = 2, 0);  // UB
}
int main() { g(0); }
```

这是标准的例 3。四行代码都在同一个表达式里多次读写 `i`，结果却分成了良定义和 UB 两类。要说清楚区别，需要先把一次求值拆开来看。

### 值计算与副作用（¶7）

¶7 下面这些操作是**副作用**（side effect），即执行环境或翻译环境状态的改变：

- 读取 volatile glvalue 所指的对象（读设备寄存器可能改变设备状态）；
- 修改对象；
- {{c++26}} 产生一个注入声明（[[expr.const.reflect]]），这是静态反射在翻译期造成的效果，所以定义里出现了翻译环境；
- 调用库 I/O 函数；
- 调用做了以上任何一件事的函数。

一个表达式的**求值**（evaluation）一般包括两部分。**值计算**（value computation）对 glvalue 是确定它指代哪个对象，对 prvalue 是取出对象里的值。另一部分是发起副作用。以 `i++` 为例，值计算得到 `i` 原来的值，副作用是把 `i` 加 1；这两部分在时间上可以分开。

库 I/O 调用返回，或者 volatile 访问被求值时，这个副作用就算完成了，即使真正的 I/O 还没有发生。

### 三种关系（¶8）

¶8 [[g:sequenced-before|**sequenced before**]] 是同一线程内两个求值之间的关系，非对称、可传递，构成偏序。A sequenced before B，意思是 A 的执行必须在 B 之前。在它之外还有两种情况：

| 关系 | 含义 | 能否交叠 | 例子 |
|---|---|---|---|
| sequenced before | A 先执行完，再执行 B | 否 | 分号分隔的两条语句；`&&`、`,` 的左操作数先于右操作数 |
| **不定序**（indeterminately sequenced） | A 在 B 之前或 B 在 A 之前，哪个未指定 | 否 | 函数调用与调用外的求值（¶12）；各个形参的初始化（[[expr.call#8]]） |
| **无序**（unsequenced） | 两个方向都没有 sequenced before | 可以 | `+`、`*`、`==` 的两个操作数 |

注 3 和注 4 指出了区别所在：无序的求值可以交叠，编译器可以把 `a + b` 中计算 `a` 的指令和计算 `b` 的指令交错排列；不定序的两个求值各自是一个整体，只是谁先谁后不定。

说表达式 X sequenced before 表达式 Y，是指 X 的每一个值计算和副作用都先于 Y 的每一个值计算和副作用。C++17 说 `<<` 的左操作数先于右操作数，用的就是这个强意义：左边的副作用也全部先完成。

### 无序的冲突访问是 UB（¶10）

¶10 除非另有规定，一个运算符的各个操作数、一个表达式的各个子表达式，它们的求值是无序的。注 5 补充，同一个表达式在循环里多次求值时，无序或不定序的部分每次的顺序可以不同。

运算符各操作数的值计算先于运算符结果的值计算：要先知道 `a` 和 `b` 才能算 `a + b`。但这条只管值计算，不管副作用。

!!! std
    The behavior is undefined if a side effect on a memory location […] is unsequenced relative to […] another side effect on the same memory location […] or a value computation using the value of any object in the same memory location.

完整的规则是：如果

- ¶10.1 对某个内存位置的副作用，或 ¶10.2 在某个内存位置开始或结束对象的生命期，

与下面任何一项无序：

- ¶10.3 对同一内存位置的另一个副作用；
- ¶10.4 在与该位置重叠的存储中开始或结束对象的生命期；
- ¶10.5 使用同一内存位置中某个对象的值的值计算；

并且两个求值不是潜在并发的，行为就未定义。潜在并发指它们在不同线程上，或者一方在信号处理函数里（[[intro.races#17]]）；那种情况由下一节的数据竞争规则处理，注 7 也是这个意思。

规则说的是[[intro.memory|内存位置]]（一个标量对象，或一串相邻的非零宽位域），不是变量。相邻的位域可能共享一个内存位置，联合的成员共享存储。¶10.2 和 ¶10.4 把生命期的开始和结束也算进来，因为给联合成员赋值会切换活跃成员。注 6 说明，在一个内存位置开始一个对象的生命期，可能结束其他内存位置里对象的生命期（[[basic.life]]）。

回到例 3：

- `i = 7, i++, i++;`：逗号运算符的左操作数先于右操作数（[[expr.comma]]），`i` 依次变为 7、8、9。
- `i = i++ + 1;`：[[expr.assign]] 规定右操作数先于左操作数，赋值本身的副作用又在两边的值计算之后。`i++` 的副作用属于右操作数，先于赋值完成，两者有序。C++11/14 中这两个副作用无序，是 UB。
- `i = i++ + i;`：右操作数内部，`+` 的两个操作数无序，`i++` 的副作用与右边 `i` 的值计算无序，命中 ¶10.5。
- 联合那一行：`u.x = 1` 开始 `u.x` 的生命期，`u.y = 2` 开始 `u.y` 的生命期，两者在同一块存储上，又分属 `+` 的两个无序操作数，命中 ¶10.2 和 ¶10.4。

<div class="compare" markdown="1">

```cpp run title="seq-ok.cpp" ok
#include <cstdio>
int a[4] = {};
int main() {
  int x = 5;
  x = x++;    // x 保持 5
  int i = 0;
  a[i] = i++ + 10;
  // 右边先求值：i 变为 1，
  // 再求左边 a[i]，即 a[1]
  std::printf("%d %d %d\n",
              x, a[0], a[1]);
}
```

```cpp run title="seq-ub.cpp" ub
int h(int i) {
  // + 的两个操作数都修改 i，
  // 彼此无序
  return i++ + i++;
}
int main() { return h(0); }
```

</div>

左边打印 `5 0 10`。本机 Clang 23 对右边给出 `-Wunsequenced` 警告（`-Wall` 已包含），对左边不警告。

### C++17 之后哪些地方有顺序

¶10 只说除非另有规定，具体的规定分散在第 7 章各处：

| 表达式 | 顺序 | 出处 |
|---|---|---|
| `a && b`、<code>a &#124;&#124; b</code> | 若求值 b，a 先于 b | [[expr.log.and#2]]、[[expr.log.or#2]] |
| `a ? b : c` | a 先于 b 或 c | [[expr.cond]] |
| `a , b` | a 先于 b | [[expr.comma#1]] |
| `a << b`、`a >> b` | a 先于 b（C++17） | [[expr.shift#4]] |
| `a = b`、`a += b` 等 | b 先于 a，赋值在两边的值计算之后（C++17） | [[expr.assign#1]] |
| `a[b]` | a 先于 b（C++17） | [[expr.sub#1]] |
| `a->*b`、`a.*b` | a 先于 b（C++17） | [[expr.mptr.oper#4]] |
| `f(args…)` | f 先于每个实参和默认实参（C++17）；各形参的初始化彼此不定序 | [[expr.call#8]] |
| `{a, b, c}` | 从左到右，即使它被当作构造函数实参 | [[dcl.init.list#4]] |
| `new T(args)` | 分配函数调用先于初始化器中的表达式；初始化先于 new 表达式的值计算 | [[expr.new#25]] |
| `a + b`、`a == b`、`a < b`、`a & b` 等 | 无序 | ¶10 |

```cpp run title="cpp17-order.cpp" ok
#include <cstdio>
#include <iostream>
#include <map>
int main() {
  int i = 0;
  std::cout << i++ << ' ' << i++ << '\n';   // C++17 起保证打印 "0 1"

  std::map<int, int> m;
  m[0] = m.size();      // 右边先求值：size() 在插入之前，m[0] == 0
  std::printf("%d\n", m[0]);
}
```

重载的运算符用运算符记法调用时，操作数也按对应内建运算符的顺序求值（[[over.match.oper]]），所以 `std::cout << i++ << i++` 有保证。如果写成函数调用记法 `operator<<(operator<<(std::cout, i++), i++)`，就回到普通函数调用的规则，两个实参不定序，结果未指定。[[expr.call]] 的例 5 对比的正是这两种写法。

在 C++14 中，`m[0] = m.size()` 里的 `operator[]` 和 `size()` 是两个不定序的函数调用，`m[0]` 可能是 0 也可能是 1。

!!! note "为什么不规定完整的求值顺序"
    C 和 C++ 一直把操作数的求值顺序留给实现：编译器可以先算需要更多寄存器的一边，可以按调用约定决定实参的求值方向，也可以更自由地合并和重排。代价是 `f(i++, i++)` 这类代码在不同编译器上结果不同。C++17 的 [[P0145R3]] 只给读者习惯从左往右读的那几种运算符补上了顺序，没有动普通算术运算符，也没有规定实参之间的顺序。

## 完整表达式（¶2–¶6、¶9）

```cpp run title="full-expr.cpp" ok
#include <cstdio>
struct T {
  const char* n;
  T(const char* s) : n(s) { std::printf("ctor %s\n", n); }
  ~T() { std::printf("dtor %s\n", n); }
  int v() const { return 1; }
};
int use(int a, int b) { std::printf("use\n"); return a + b; }

int main() {
  int x = use(T("a").v(), T("b").v());  // 整个初始化是一个完整表达式
  std::printf("next %d\n", x);
}
```

`T("a")` 和 `T("b")` 谁先构造未指定，它们分属两个不定序的形参初始化。但两者都在 `use` 返回之后、打印 `next` 之前销毁，因为临时对象在所属完整表达式的末尾销毁（[[class.temporary]]）。本机输出依次是 `ctor a`、`ctor b`、`use`、`dtor b`、`dtor a`、`next 2`。

¶9 一个完整表达式的每个值计算和副作用，都先于下一个要求值的完整表达式的每个值计算和副作用。脚注 29 补充，完整表达式求值之后，还要依次调用零个或多个临时对象的析构函数，通常按构造的逆序。

¶5 [[g:full-expression|**完整表达式**]]（full-expression）有以下几种：

| | 种类 | 例子 |
|---|---|---|
| ¶5.1 | 不求值操作数 | `sizeof(f())` 中的 `f()` |
| ¶5.2 | *constant-expression* | 数组界、`case` 标签 |
| ¶5.3 | 立即调用 | {{c++20}} `consteval` 函数的调用 |
| ¶5.4 | *init-declarator*（包括结构化绑定）或 *mem-initializer*，连同初始化器 | `int x = use(...);` |
| ¶5.5 | 对象生命期结束时生成的析构调用，临时对象和生命期被延长的临时对象除外 | 块结束时局部变量的析构 |
| ¶5.6 | 契约断言的谓词 | {{c++26}} `pre(n > 0)` 中的 `n > 0` |
| ¶5.7 | 不属于其他表达式、也不属于其他完整表达式的表达式 | 表达式语句、`return` 的操作数、`if` 的条件 |

¶5 还有三条补充。一个语言构造如果按定义会产生隐式函数调用（例如 range-for 调用 `begin()`），这个构造本身就当作一个表达式。为了满足语言构造的要求而施加在结果上的转换（`if` 条件转换为 `bool`、左值到右值转换）属于这个完整表达式。对初始化器来说，执行初始化本身（包括聚合的默认成员初始化器）也属于完整表达式。

例 2 中有一行说明了最后一点会带来什么：

```cpp run title="noexcept-dtor.cpp" ok
struct S {
  S(int) noexcept {}
  ~S() noexcept(false) {}
};
static_assert(!noexcept(S(4)));   // 临时对象的析构也属于这个完整表达式
int main() {}
```

`noexcept(S(4))` 的操作数是不求值操作数，本身就是一个完整表达式，末尾销毁临时对象的析构调用也算在内。析构函数是 `noexcept(false)`，所以结果是 `false`。

### 默认实参属于调用者

¶2–¶4 定义了一组辅助概念，用来说清楚完整表达式包含哪些部分：

- ¶2 **构成表达式**（constituent expression）把初始化器展平：`B b = { 5, { 1+1 } };` 的构成表达式是 `5` 和 `1+1`。
- ¶3 E 的**直接子表达式**（immediate subexpression）包括 E 的操作数、E 隐式调用的函数、lambda 按值捕获的初始化，以及 ¶3.4 E 所用的默认实参、¶3.5 聚合初始化所用的默认成员初始化器。
- ¶4 **子表达式**是直接子表达式关系的传递闭包。注 1 指出 lambda 函数体里的表达式不是 lambda 表达式的子表达式，因为函数体要到调用闭包时才执行。¶4 还定义了**潜在求值子表达式**：去掉嵌套在不求值操作数（[[expr.context]]）里的那些。

¶3.4 和 ¶3.5 的效果是，默认实参和默认成员初始化器虽然写在别处，却在调用点或初始化点求值，属于调用者的完整表达式。它们产生的临时对象在调用者的完整表达式结束时才销毁，它们的副作用也参与调用者表达式里的顺序分析。¶6 的注 2 说的正是这一点。

!!! note "range-for 中的临时对象"
    完整表达式的边界决定了临时对象活多久。`for (auto x : make().items())` 在 C++20 及以前会产生悬垂引用：`make()` 返回的临时对象在 *for-range-initializer* 这个完整表达式结束时就销毁了。C++23 在 [[class.temporary]] 中增加了一种延长生命期的情形，让这里的临时对象活到整个循环结束。

## 函数调用（¶11–¶14）

¶11 调用函数 f 时（不论 f 是否 inline），各阶段依次 sequenced before：

1. 每个实参表达式，以及指代 f 的后缀表达式；
2. {{c++26}} 这次调用的每个前置条件断言；
3. 函数体中的每个表达式和语句；
4. {{c++26}} 这次调用的每个后置条件断言。

不论是否 inline，是说内联展开不能改变这个顺序。

### 函数调用不交织（¶12）

```cpp run title="no-interleave.cpp" unspecified
#include <cstdio>
int i = 0;
int f() { return ++i; }
int main() {
  int r = i + f();          // 不是 UB：读 i 和 f() 里的 ++i 不定序
  std::printf("%d\n", r);   // 1 或 2，未指定
}
```

`i + i++` 是 UB，`i + f()` 却不是，区别在于自增发生在函数里。

¶12 设 F 是一次函数调用（¶12.1）、一次 *await-expression* 的求值（¶12.2）或一次 *throw-expression* 的求值（¶12.3）。同一线程上（在信号处理函数里时，限于同一次处理函数调用）不在 F 之内的每个求值，要么先于 F 内的全部求值，要么后于 F 内的全部求值。脚注 30 概括为：函数的执行不会相互交织。所以读 `i` 要么完整地在 `f` 之前，要么完整地在 `f` 之后，结果只有两种可能。

F 调用或恢复一个协程时，只有上一次挂起之后、下一次挂起之前的求值算在 F 之内，协程每一段连续执行被看作一个整体。

¶13 有些语境会在没有函数调用语法的地方调用函数：*new-expression* 调用分配函数和构造函数，隐式转换调用转换函数。¶14 规定，上述顺序约束是函数调用本身的性质，与调用的写法无关，所以对这些隐式调用同样成立。

C++17 的形参初始化规则和 ¶12 一起，修复了一个经典的内存泄漏：

```cpp run title="no-leak.cpp" ok
#include <memory>
struct A {};
int g() { throw 0; }
void h(std::unique_ptr<A>, int) {}
int main() {
  try {
    h(std::unique_ptr<A>(new A), g());   // C++17 起：g 抛异常时不会泄漏
  } catch (int) {}
}
```

C++14 中实参的各个子表达式之间无序，编译器可以按 `new A`、`g()`、构造 `unique_ptr` 的顺序执行，`g()` 抛出异常时 `new A` 的内存就泄漏了。C++17 起，[[expr.call#8]] 规定每个形参的初始化连同其全部值计算和副作用，与其他形参的初始化不定序。`new A` 和构造 `unique_ptr` 属于同一个形参的初始化，`g()` 插不进中间。

C++17 规定被调函数的后缀表达式先于实参，让链式调用也按从左往右执行。下面是 [[expr.call]] 例 4 的改编：

```cpp run title="chain.cpp" ok
#include <cassert>
#include <string>
int main() {
  std::string s = "but I have heard it works even if you don't believe in it";
  s.replace(0, 4, "").replace(s.find("even"), 4, "only").replace(s.find(" don't"), 6, "");
  assert(s == "I have heard it works only if you believe in it");
}
```

C++14 中 `s.find("even")` 可能在第一个 `replace` 之前求值，得到错误的下标。C++17 起，成员调用 `E.replace(...)` 的后缀表达式（包括 `E`，也就是前一个 `replace` 调用）先于实参求值。

## 信号处理函数（¶15）

¶15 因调用 `std::raise` 而执行的信号处理函数，在 `raise` 调用之后、`raise` 返回之前执行，和普通的函数调用一样。注 8 补充，其他原因触发的信号处理函数通常与程序其余部分无序。所以异步信号处理函数只能安全地访问 `volatile std::sig_atomic_t` 或无锁的原子对象（[[intro.races#18]]、[[support.signal]]）。

## 常量求值中按词法顺序（¶16）

¶16 表达式作为核心常量表达式（[[expr.const.core]]）求值时，本来无序或不定序的操作数和子表达式按词法顺序求值。函数调用用到的默认实参，按照在对应位置写了实参的情形排序。

常量求值的结果会进入类型系统（数组界、模板实参），必须在所有实现上一致。规定词法顺序后，常量求值里不再有顺序未指定的情况。

```cpp run title="constexpr-order.cpp" ok
constexpr int h() {
  int i = 0;
  int r = i++ + i++;    // 常量求值中按词法顺序：0 + 1
  return r * 10 + i;
}
static_assert(h() == 12);
int main() {}
```

!!! lawyer "常量求值里的 `i++ + i++` 还是 UB 吗"
    ¶10 的 UB 以无序为前提，¶16 又规定这些求值在常量求值中按词法顺序进行。按字面读，上例在常量求值时结果确定。本机 Clang 23 接受它并得到 12，同时照常给出 `-Wunsequenced` 警告。同一个函数在运行期调用时，`i++ + i++` 仍然是 UB。这一段是 C++23 之后的新措辞，写可移植代码时不要依赖它。

<details class="fine" markdown="1"><summary>其余条文</summary>

¶1 每次进入一个块，块里每个自动存储期对象都对应一个新实例。对象在块执行期间存在并保持最后存入的值，块被挂起时也是如此：调用其他函数、协程挂起（[[expr.await]]）、收到信号时，局部变量都保持原值。递归的每一层有自己的一份局部变量，协程恢复后局部变量还是挂起前的值，依据都在这里。

</details>

!!! impl "实现视角"
    - 实参的求值方向因编译器而异。常见的观察是 GCC 在 x86-64 上多从右往左求值实参，Clang 从左往右；本机 Clang 23 对 `f(i++, i++)` 传入 `0 1`。
    - 本机 Clang 23 对 C++17 起已经良定义的 `a[i] = i++ + 10`、`i += i++` 不警告，但对 `f(i++, i++)` 仍然报告 multiple unsequenced modifications。按 [[expr.call#8]]，两个形参的初始化是不定序而不是无序，这不是 UB，只是结果未指定。这条警告应当理解为可移植性提醒。GCC 的对应选项是 `-Wsequence-point`。

!!! history "从顺序点到 sequenced before"
    - C++98/03 沿用 C 的顺序点（sequence point）模型：两个相邻顺序点之间，一个对象最多被修改一次，而且读取旧值只能用于计算新值。`i = ++i + 1` 是 UB。
    - C++11 为了多线程内存模型，用 sequenced before、无序、不定序取代了顺序点，并把值计算和副作用分开描述。一些原来是 UB 的表达式变成良定义，例如 `i = ++i + 1`：前置自增的副作用先于它的值计算，赋值又在其后。
    - C++17 的 [[P0145R3]] 给 `<<`、`>>`、赋值、`[]`、`->*`、`.*` 和被调函数规定了顺序，形参的初始化变为不定序。提案讨论过让实参严格从左往右求值，最终只采用了较弱的不定序。
    - C++20 加入协程，*await-expression* 纳入不交织规则；立即调用成为完整表达式。
    - C++26 中契约断言的谓词成为完整表达式，函数调用的顺序链里加入前置和后置条件，副作用的定义加入了反射的注入声明。

## 常见误解

!!! pitfall "C++17 规定了求值顺序"
    只规定了一部分。`a + b`、`a == b` 的操作数，`f(g(), h())` 中 `g` 和 `h` 的调用，顺序仍然未指定。C++17 对实参的改变只是：每个实参作为整体求值，不再与其他实参交叠。`std::printf("%d %d", i++, i++)` 不是 UB，但输出未指定。

!!! pitfall "逗号都是逗号运算符"
    `f(a, b)` 中的逗号分隔实参，没有顺序。`int x = i++, y = i++;` 中的逗号分隔两个 *init-declarator*，每个都是一个完整表达式（¶5.4），所以有序。只有 `(a, b)` 这样的逗号运算符才保证从左到右。重载的 `operator,` 用运算符记法调用时，C++17 起也遵循从左到右。

!!! pitfall "循环里每次的顺序都一样"
    在循环里写 `sum += f() * g();`，不能假设每次迭代都先调用 `f`（注 5）。优化后的代码可能把第一次迭代单独剥离出来，并改变它的调用顺序。

## 思考题

!!! question "1. 下面哪些是 UB？（C++17 及以后）"
    ```cpp
    int i = 0, a[4] = {};
    i = ++i + i++;        // (a)
    a[i++] = i;           // (b)
    i += i++;             // (c)
    i = (i++, i);         // (d)
    ```

<details markdown="1">
<summary>答案</summary>

- (a) UB。右操作数 `++i + i++` 中，`+` 的两个操作数都修改 `i`，彼此无序。
- (b) 良定义。赋值的右操作数 `i` 先于左操作数 `a[i++]` 的全部求值（包括 `i++` 的副作用），设 `i` 原来是 0：右边读到 0，左边 `a[i++]` 指代 `a[0]`，之后 `i` 变为 1，最终 `a[0] = 0`。C++14 中是 UB。
- (c) 良定义。复合赋值同样是右边先求值：设 `i` 原来是 0，右边得 0，`i` 变为 1；再读左边的 `i` 得 1，结果 `i = 1 + 0 = 1`。
- (d) 良定义。逗号运算符左先于右，`i` 先自增，再读出新值赋回。
</details>

!!! question "2. 为什么不定序的冲突访问只是结果未指定，无序的冲突访问却是 UB？"

<details markdown="1">
<summary>答案</summary>

依据是注 3 和注 4。无序的求值可以交叠，编译器可能把一次写拆成几条指令，与另一次读写交错，结果可能是任何值。标准不约束这种情况，规定为 UB，换取优化的自由。不定序的两个求值保证不交叠，只可能一个先完成，结果只有有限几种，所以只是未指定。
</details>

!!! question "3. `std::cout << f() << g();` 中 `f` 一定在 `g` 之前调用吗？如果 `operator<<` 是成员函数呢？"

<details markdown="1">
<summary>答案</summary>

C++17 起一定。不论 `operator<<` 是成员还是非成员，只要用运算符记法，操作数就按内建 `<<` 的规定求值（[[over.match.oper]]、[[expr.shift#4]]）。`(cout << f()) << g()` 中外层的左操作数是 `cout << f()`，它整体先于 `g()`。C++14 中，如果 `operator<<` 是成员函数，后缀表达式 `(cout << f()).operator<<` 与实参 `g()` 之间没有顺序，`g` 可能先被调用。
</details>
