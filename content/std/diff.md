把编译选项从 `-std=c++17` 改成 `-std=c++20`，原来能编译的代码会不会报错？会不会编译通过但行为变了？标准对这个问题的正式回答就在 **Annex C（Compatibility，兼容性）**。它按版本列出每一条**可能破坏现有合法代码**的改动：哪一节改了、改了什么、为什么改、对旧代码有什么影响。

这份附录不讲新特性本身（新特性不会让旧代码失效，除非它占用了旧代码在用的名字或语法），只讲**代价**。新增关键字、新增头文件、新的 token、重载决议规则的调整、库函数签名的变化，都在这里登记。

## 条目的格式

每个条目由几个固定字段组成：

- **Affected subclause**：受影响的正文小节。这是判断时真正要读的地方，附录只是摘要。
- **Change**：改了什么。
- **Rationale**：为什么改。
- **Effect on original feature**：对旧代码的影响，通常落到"原来良构的代码变成非良构"、"行为改变"、"变成 IFNDR"或"变成 UB"之一。
- **Difficulty of converting** 与 **How widely used**：只有 [diff.iso]（C 与 C++ 的比较）保留这两项。各个 C++ 版本之间的条目没有这两个字段，我们在子页面里按经验补上"改写难度"。

多数条目附有一个前后对比的例子，注释里写 *ill-formed; previously well-formed* 之类的判定。子页面把这些例子改写成可编译的形式，在 Clang 23.1.3（libc++）上用新旧两个 `-std=` 分别编译，展示变化是否真的出现。

## 法律地位：资料性

Annex C 标着 **(informative)**，与 [[ub]]、[[ifndr]] 一样不创造规则。某段代码在新标准下是否良构，由正文决定，附录只是把"正文哪里改了"指出来。两点推论：

1. **它不是穷尽的。** 附录只收录委员会认为值得登记的不兼容。一些以缺陷报告（DR）形式修正的问题被视为"旧标准本来就该这样"，常常不出现在这里；库实现细节导致的差异更不会出现。
2. **它不说明编译器怎么做。** 许多改动在编译器里是以 DR 方式**回溯到所有语言模式**的。例如 C++17 对 `auto x{1}` 的推导改变和继承构造函数语义的改变，Clang 在 `-std=c++14` 下也按新规则处理；C++20 的隐式捕获规则，Clang 在 `-std=c++17` 下同样适用。所以"切换 `-std=` 看不到变化"并不说明附录写错了，可能只是编译器早已统一了行为。子页面的实测会逐条注明。

## 与 Annex D 的关系

Annex D [[depr]] 列的是**仍然有效但已弃用**的特性；它们从 Annex D 被删除的那一刻，就会作为一条不兼容出现在 Annex C 里。例如 `std::auto_ptr` 在 C++11 进入 Annex D，C++17 删除时登记为 [[diff.cpp14.depr]] ¶1；`<codecvt>` 和 `<strstream>` 的删除登记在 [[diff.cpp23.depr]]。所以每个 C++ 版本小节的最后一节通常是 "Annex [depr]"，记录本轮从弃用走到删除的东西。

升级时两份附录要一起看：Annex C 告诉你**这一版**会坏什么，Annex D 告诉你**下一版**可能会坏什么。

## 升级 `-std=` 时怎么用它

1. **先用旧标准加兼容性警告编译。** Clang 为大部分语言层面的不兼容提供了 `-Wc++11-compat`、`-Wc++14-compat`、`-Wc++17-compat`、`-Wc++20-compat`、`-Wc++23-compat`、`-Wc++2c-compat` 一组警告，在**旧模式**下就能指出新模式会出问题的地方：

    ```text
    $ clang++ -std=c++17 -Wc++20-compat -fsyntax-only compat.cpp
    compat.cpp:1:5: warning: 'concept' is a keyword in C++20 [-Wc++20-compat]
    compat.cpp:2:5: warning: 'requires' is a keyword in C++20 [-Wc++20-compat]
    compat.cpp:4:5: warning: 'char8_t' is a keyword in C++20 [-Wc++20-compat]
    ```

    `-Wdeprecated` 则会报出 Annex D 中正在走向删除的用法（见 [[depr]]）。

2. **再按附录逐节核对编译器查不出来的项。** 附录里有一类改动**不会产生诊断**：行为静默改变（C++23 范围 `for` 延长临时对象生命周期、C++20 的反向 `==` 候选选了另一个函数）、变成 IFNDR（C++20 起不同翻译单元的默认实参必须相同）、变成 UB（C++20 伪析构调用结束对象生命周期）。这些只能靠人读。子页面的"改写难度"一栏里把这类条目标为"需人工审查"。

3. **注意新头文件和新保留名。** 每一版都有"New headers"条目：如果项目里有一个自己的 `<version>`、`<format>` 或 `<print>`，并且 include 路径排在系统路径前面，升级后会拿到错误的头文件。这些条目看似琐碎，实际项目里确实会撞上。

## 各版要点速览

| 版本差 | 最可能碰到的不兼容 |
|---|---|
| C++26 → 草案 | 抛异常的 `operator delete` 声明非良构；聚合的基类可以用指派初始化，导致重载歧义 |
| C++23 → C++26 | 枚举与浮点/其他枚举混合运算非良构；数组之间直接比较非良构；`delete` 不完整类型非良构；`T...[n]` 成为包索引；`to_string(double)` 输出改变；移除 `<codecvt>`、`<strstream>`、`wstring_convert` |
| C++20 → C++23 | 范围 `for` 延长临时对象生命周期；`return x;` 中的可移动 id 变成 xvalue；`a[1, 2]` 的含义改变；`std::format` 的格式串在编译期检查 |
| C++17 → C++20 | 新关键字（`concept`、`requires`、`char8_t`、`co_*` 等）；`u8` 字面量的类型变成 `char8_t`；有用户声明构造函数的类不再是聚合；反向 `==` 候选；`module`/`import` 开头的行；`throw()` 删除 |
| C++14 → C++17 | 三字符组删除；`register` 删除；`bool` 自增删除；异常说明进入类型系统；动态异常说明删除；`auto_ptr` 等删除 |
| C++11 → C++14 | 数字分隔符 `'`；`constexpr` 成员函数不再隐式 `const` |
| C++03 → C++11 | 新关键字；`>>` 闭合模板；收窄转换；`auto` 不再是存储类说明符；`export` 改作他用 |

## 阅读建议

- 想快速评估升级风险：先看上面的速览表，再读对应版本页面里标为"静默改变"和"需人工审查"的条目。
- 想理解某条规则为什么长成现在这样：附录的 Rationale 往往是最短的设计动机说明，顺着 Affected subclause 链接回正文，比读提案快。
- 写跨 C/C++ 的头文件：读 [[diff.iso]] 和 [[diff.library]]。
