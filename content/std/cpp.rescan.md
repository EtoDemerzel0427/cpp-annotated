[[cpp.replace]] 讲了宏调用的前五步：划分实参、实参替换、`#`、`##`、删除 placemarker。本页是第六步，也是最微妙的一步：**重新扫描**（*rescanning*）。

宏展开的结果里可能还有宏名，所以要再扫描一遍；可如果宏展开后又出现了它自己，再扫描就会无限循环。标准的解决办法是把这样的宏名标记为"不可再替换"——社区俗称**涂蓝**（*painted blue*）。这条规则只有三句话，却决定了 C/C++ 宏系统的计算能力边界：它是宏不能直接递归的原因，也是 Boost.Preprocessor 之类宏元编程库能用 `EVAL`/`DEFER` 绕开限制的原因。

前置知识：[[cpp.replace]] 全页，尤其是实参在代入前先完全展开（[[cpp.subst#1]]）。

## 重新扫描（¶1）

¶1：替换列表中所有形参都已代入、`#` 和 `##` 都已处理之后，**删除所有 placemarker**。然后，得到的记号序列**连同源文件后续的所有记号**一起被重新扫描，寻找更多可以替换的宏名。

"连同后续所有记号"是关键：替换结果的末尾可以和源文件中**宏调用之后**的记号结合，形成新的宏调用。

```cpp
#define LP (
#define F1(x) [x]
#define CALL(m) m(5)
F1 LP 1)        // F1 ( 1)  —— 不展开
CALL(F1)        // [5]
```

第一行：扫描到 `F1` 时，下一个预处理记号是 `LP`，不是 `(`，所以 `F1` 不是调用；`F1` 被跳过（它没有被涂蓝，只是错过了机会）。随后 `LP` 展开为 `(`，但扫描已经越过了 `F1`，不会回头。结果是 `F1 ( 1)`。

第二行：`CALL(F1)` 展开为 `F1(5)`，重新扫描时 `F1` 后面紧跟 `(`，构成调用 → `[5]`。

另一个例子是宏名在替换列表末尾，从源文件"借"实参：

```cpp
#define h g(~
#define g f
#define f(a) [a]
h 5)            // h → g(~ → f(~ ，再连同源文件中的 5) → f(~ 5) → [~ 5]
```

替换结果 `g(~` 的括号没有闭合，而闭合的 `)` 在源文件后续记号中。这正是"连同后续记号"的作用。

## 标准大例子逐步推演（¶2）

这是标准中最长的宏例子，几乎每一处都对应一条规则。定义：

```cpp
#define x       3
#define f(a)    f(x * (a))
#undef  x
#define x       2
#define g       f
#define z       z[0]
#define h       g(~
#define m(a)    a(w)
#define w       0,1
#define t(a)    a
#define p()     int
#define q(x)    x
#define r(x,y)  x ## y
#define str(x)  # x
```

先注意前四行：`f` 的替换列表里有 `x`，定义 `f` 时 `x` 是 3，之后 `x` 被重定义为 2。替换列表存储的是**记号**，不在定义时展开；`x` 在**使用时**才被替换，所以下文所有的 `x` 都是 2。

### 第一行

```cpp
f(y+1) + f(f(z)) % t(t(g)(0) + t)(1);
// → f(2 * (y+1)) + f(2 * (f(2 * (z[0])))) % f(2 * (0)) + t(1);
```

**`f(y+1)`**：实参 `y+1` 展开后不变，代入得 `f(x * (y+1))`。重新扫描：`f` 是**正在被替换的宏**，涂蓝，不再展开（尽管它后面跟着 `(`）；`x` → `2`。结果 `f(2 * (y+1))`。

**`f(f(z))`**：先完全展开实参 `f(z)`（[[cpp.subst#1]]）：
- 内层 `f(z)` 的实参 `z` 展开为 `z[0]`——`z` 的替换列表中的 `z` 被涂蓝；
- 代入得 `f(x * (z[0]))`，内层的 `f` 被涂蓝，`x` → `2`：`f(2 * (z[0]))`。

外层代入：`f(x * (f(2 * (z[0]))))`，重新扫描：外层 `f` 涂蓝；`x` → `2`；内层 `f` **早已是蓝的**。结果 `f(2 * (f(2 * (z[0]))))`。

**`t(t(g)(0) + t)(1)`**：外层 `t` 的实参是 `t(g)(0) + t`，先完全展开它，且"如同它是翻译单元的剩余部分"：
- `t(g)`：实参 `g` 展开为 `f`（`f` 是函数式宏，但在实参 `g` 中它后面没有 `(`，所以不调用，也**不涂蓝**）。代入得 `f`。
- 重新扫描 `f` 连同（实参内的）后续记号 `(0) + t`：`f(0)` 构成调用 → `f(2 * (0))`。
- `+ t`：`t` 后面没有 `(`（实参到此为止），保持原样。
- 实参展开结果：`f(2 * (0)) + t`。

外层 `t` 代入：替换列表就是 `a`，结果为 `f(2 * (0)) + t`。重新扫描（连同源文件后续 `(1);`）：遇到 `t`——它是**正在被替换的宏** `t` 的名字，在替换列表的扫描中被发现，涂蓝。所以后面的 `(1)` 不构成调用。结果 `f(2 * (0)) + t(1)`。

### 第二行

```cpp
g(x+(3,4)-w) | h 5) & m
    (f)^m(m);
// → f(2 * (2+(3,4)-0,1)) | f(2 * (~ 5)) & f(2 * (0,1))^m(0,1);
```

**`g(x+(3,4)-w)`**：`g` 是对象式宏 → `f`；重新扫描连同后续 `(x+(3,4)-w)`，构成 `f` 的调用。实参 `x+(3,4)-w` 只有一个——实参的划分在展开**之前**完成，`(3,4)` 中的逗号在括号内，`w` 展开出的逗号此时还不存在。实参展开为 `2+(3,4)-0,1`；代入并展开 `x`：`f(2 * (2+(3,4)-0,1))`。

注意 `w` 展开出的逗号**不会**把实参分成两个——它是在实参被确定之后才出现的。

**`h 5)`**：如上一节，`h` → `g(~` → `f(~`，连同源文件的 `5)` 构成 `f(~ 5)` → `f(2 * (~ 5))`。

**`m\n(f)`**：`m` 与 `(` 之间隔着换行——在宏调用的语境中换行只是空白（[[cpp.replace.general#13]]），所以这是调用 `m(f)`。实参 `f` 单独展开时后面没有 `(`，保持 `f`。代入 `a(w)` 得 `f(w)`。重新扫描：`f` **不是**正在被替换的宏（正在替换的是 `m`），所以 `f(w)` 是调用。实参 `w` → `0,1`；结果 `f(2 * (0,1))`。

**`m(m)`**：实参 `m` 单独展开时后面没有 `(`，保持 `m`。代入 `a(w)` 得 `m(w)`。重新扫描：`m` 是正在被替换的宏，涂蓝；`w` → `0,1`。结果 `m(0,1)`。

`m(f)` 与 `m(m)` 的对比是理解涂蓝规则的最佳教材：同样的替换列表 `a(w)`，换一个实参，结果截然不同。

### 第三、四行

```cpp
p() i[q()] = { q(1), r(2,3), r(4,), r(,5), r(,) };
char c[2][6] = { str(hello), str() };
// → int i[] = { 1, 23, 4, 5, };
//   char c[2][6] = { "hello", "" };
```

- `p()`：零形参宏，零实参 → `int`。
- `q()`：一个形参、一个**空**实参 → 空。所以 `i[q()]` → `i[]`。
- `r(4,)`：`4 ## <placemarker>` → `4`；`r(,5)` → `5`；`r(,)` → placemarker，删除后什么也没有。
- `str()`：空实参字符串化为 `""`。

!!! impl "实测"
    Clang 23 `-E` 对这个例子的输出与标准逐记号一致（只有空白的差异，如 `2 +(3,4)`）。

## 涂蓝：递归抑制（¶3）

¶3 三句话，逐句看。

!!! std
    If the name of the macro being replaced is found during this scan of the replacement list (not including the rest of the source file's preprocessing tokens), it is not replaced.

    在重新扫描**替换列表**（不包括源文件的后续记号）时发现了正在被替换的宏的名字，则不替换它。

**第一句**：在扫描宏 M 的替换结果时遇到 M，不替换。括号里的限定很重要：如果 M 的名字出现在源文件**后续**的记号里（即替换结果之后），它是可以正常替换的。

```cpp
#define foo foo bar
foo         // → foo bar    （替换列表中的 foo 被涂蓝）
foo foo     // → foo bar foo bar   （第二个 foo 来自源文件，不受影响）
```

**第二句**：此外，若**嵌套**的替换遇到正在被替换的宏的名字，也不替换。

```cpp
#define AA BB
#define BB AA
AA          // AA → BB（AA 正在被替换）→ BB 的替换列表是 AA，此时 AA 仍在"正在被替换"之列 → 不替换
            // 结果：AA
BB          // 同理：BB
```

**第三句**：这些未被替换的宏名记号**永远**不再可用于替换，即使之后在本来会替换它的语境中被（重新）检查。

这就是"涂蓝"：颜色是**记号的属性**，跟着记号走。一个蓝色的 `foo` 被当作实参传给另一个宏、再被代入、再被扫描，它仍然是蓝的：

```cpp
#define id(x) x
#define ff(x) x
#define gg ff(gg)
gg          // gg → ff(gg) → 实参 gg 展开时，gg 正在被替换 → 涂蓝 → ff 返回蓝色的 gg
            // 结果：gg
id(gg)      // id 的实参 gg 先完全展开，得到蓝色的 gg；代入 id 后重新扫描，
            // 此时 gg 已不在"正在被替换"之列，但它是蓝的 → 仍不展开
            // 结果：gg
```

如果没有第三句，`id(gg)` 中 `gg` 被代入 `id` 的替换列表后，`gg` 已经不再"正在被替换"，就会再次展开为 `ff(gg)` → `gg` → …… 而把它包在 `id(id(id(...)))` 里就能绕开递归保护。第三句堵住了这条路。

!!! note "为什么叫\"涂蓝\""
    "painted blue" 是 C 委员会内部的行话，源于描述这一算法时用不同颜色标记记号的做法。标准正文中没有这个词，只说"nonreplaced macro name preprocessing tokens"。

## 结果不是指令，但 _Pragma 会被执行（¶4）

¶4：完全宏替换后的记号序列**不作为预处理指令处理**，即使它看起来像一个；但其中所有的 `_Pragma` 一元运算符表达式会按 [[cpp.pragma.op]] 处理。

```cpp
#define DEFINE_X # define X 1
DEFINE_X        // → # define X 1，作为普通记号进入阶段 7——语法错误，而不是定义 X

#define WARN_OFF _Pragma("GCC diagnostic ignored \"-Wunused\"")
WARN_OFF        // OK：_Pragma 在宏展开结果中被执行
```

这是 `_Pragma` 存在的全部理由：宏可以生成 `_Pragma`，不能生成 `#pragma`。（与 [[cpp.pre#2]] 互补：后者说宏展开前不是指令的行，展开后也不会变成指令；¶4 说宏展开的**结果**本身不会被当作指令。）

## 实现视角：Prosser 的隐藏集算法

!!! impl "隐藏集（hide set）"
    标准的措辞（"正在被替换""嵌套替换"）不太容易直接实现。C89 标准化期间，Dave Prosser 给出了一个参考算法：每个记号携带一个**隐藏集**——一组"对这个记号而言不可展开"的宏名。

    - 对象式宏 `T` 展开时：结果中每个记号的隐藏集 = 宏名记号 `T` 的隐藏集 ∪ {T}。
    - 函数式宏 `T(...)` 展开时：结果中每个记号的隐藏集 = (宏名记号 `T` 的隐藏集 ∩ 闭合 `)` 的隐藏集) ∪ {T}。
    - 扫描到标识符时，若它是宏且不在它自己的隐藏集里，就展开。

    隐藏集就是"涂蓝"的实现：一个名字在某记号的隐藏集里，等价于"这个记号被涂成了该宏的蓝色"。GCC 用每个记号上的一个 `NO_EXPAND` 标志加上"当前正在展开的宏上下文栈"来近似实现；Clang 的 `Token` 有一个 `DisableExpand` 标志位，配合 `MacroInfo` 上的"当前正在展开"标记实现同样的语义。

函数式宏规则中的**交集**是精妙之处：它处理的是"宏调用的一部分来自替换结果、另一部分来自源文件"的情形——只有闭合括号也处在同一个展开中时，才继续隐藏。

### f(2)(9) 难题

这个交集规则正好用于一个著名的例子（出自 C 标准的示例）：

```cpp
#define f(a) a*g
#define g(a) f(a)
f(2)(9)
```

- `f(2)` → `2*g`，`g` 的隐藏集为 {f}。
- `g` 后面是源文件中的 `(9)`，构成调用 `g(9)`。`g` 的隐藏集 {f}，闭合 `)` 来自源文件，隐藏集为空；交集为空，并上 {g}：结果 `f(9)` 中各记号的隐藏集为 {g}。
- `f` 不在 {g} 中 → 展开 → `9*g`。
- 最终：`2*9*g`。

但按标准的文字，`g(9)` 的展开是不是"`f` 的嵌套替换"呢？如果是，那 `f(9)` 中的 `f` 应当涂蓝，结果就是 `2*f(9)`。C 标准明确把这种情形列为**未指定**的（C 标准在附录中把"这算不算嵌套替换"列为未指定行为，并在正文示例中说两种结果都可能）。C++ 标准没有类似的说明，这个问题在 C++ 中也长期悬而未决。

Clang 23 和 GCC 都得到 `2*9*g`——也就是 Prosser 算法的结果。

## 延迟展开：在涂蓝规则下做递归

宏不能直接递归，但可以利用"重新扫描次数"来模拟。核心技巧是**延迟**：让一个宏名与它的 `(` 在本轮扫描中"错过"，到下一轮扫描时才相遇。

```cpp
#define EMPTY()
#define DEFER(m) m EMPTY()
#define EXPAND(...) __VA_ARGS__
#define A() 123

DEFER(A)()            // → A ()      本轮扫描中 A 后面是 EMPTY，不是 (
EXPAND(DEFER(A)())    // → 123       EXPAND 的实参先展开为 A ()，代入后重新扫描时 A ( ) 相遇
```

为什么 `DEFER(A)()` 停在 `A ()`？`DEFER(A)` 代入后得 `A EMPTY()`，重新扫描：`A` 的下一个记号是 `EMPTY`，不是 `(`，所以 `A` 被**跳过**（注意：不是涂蓝，只是错过）；然后 `EMPTY()` 展开为空。扫描已经越过 `A`，不会回头——和上文 `F1 LP 1)` 是同一个原理。

每多一层 `EXPAND`，就多一轮扫描。用 `#define EVAL(...) EVAL1(EVAL1(EVAL1(__VA_ARGS__)))` 这类嵌套，可以得到成百上千轮扫描。配合延迟，一个宏可以"在下一轮"引用自己——因为到下一轮时，它已经不在"正在被替换"之列，而且延迟的那个名字记号**从未被涂蓝**（它只是错过了）。这就是 Boost.Preprocessor、P99 等库实现循环和递归的基础。

```cpp run title="defer.cpp" ok
#define EMPTY()
#define DEFER(m) m EMPTY()
#define EXPAND(...) __VA_ARGS__
#define A() 123
static_assert(EXPAND(DEFER(A)()) == 123);
int main() {}
```

!!! warning "这是在利用规则，不是规则的目的"
    这些技巧完全符合标准，但可读性和可调试性很差；C++ 中的大多数场景应该用模板、`constexpr`、折叠表达式乃至反射来代替。宏元编程仍有价值的地方主要是：生成声明（X-macro）、字符串化标识符、条件编译。

## 陷阱

!!! pitfall "以为宏会\"递归\""
    ```cpp
    #define LIST(x, ...) x __VA_OPT__(, LIST(__VA_ARGS__))
    LIST(1, 2, 3)   // → 1 , LIST(2, 3)，内层 LIST 被涂蓝，不会继续
    ```
    宏没有递归。需要处理不定个数的元素时，要么用 `__VA_ARGS__` 直接传给函数/模板，要么借助上面的延迟展开技巧。

!!! pitfall "宏名后面的括号来自另一个宏"
    `#define LP (` 之后，`F LP x)` 不会调用函数式宏 `F`——扫描到 `F` 时下一个记号是 `LP`。要让它工作，需要多一轮扫描：`EXPAND(F LP x))`。

## 思考题

!!! question "思考题 1"
    ```cpp
    #define a a b
    #define b a
    a
    ```
    展开结果是什么？逐步说明每个 `a`、`b` 为何展开或不展开。

<details markdown="1">
<summary>展开查看答案与解析</summary>

结果是 `a a`。

1. `a` 展开为 `a b`，正在替换 `a`。替换列表中的 `a` → 涂蓝。
2. 继续扫描遇到 `b`，它不是正在替换的宏，展开为 `a`——这是**嵌套替换**，此时 `a` 和 `b` 都在"正在被替换"之列（`b` 的展开嵌套在 `a` 的展开之中）。按 ¶3 第二句，嵌套替换遇到正在被替换的宏名 `a`，不替换，涂蓝。
3. 结果：`a a`，两个 `a` 都是蓝色的。

用 Clang `-E` 可以验证。
</details>

!!! question "思考题 2"
    为什么 `m(f)` 展开为 `f(2 * (0,1))`，而 `m(m)` 展开为 `m(0,1)`？用隐藏集算法重新解释一遍。

<details markdown="1">
<summary>展开查看答案与解析</summary>

`m(a)` 的替换列表是 `a(w)`。

- `m(f)`：实参 `f` 展开后仍为 `f`（隐藏集为空）。代入后结果 `f ( w )` 中每个记号的隐藏集 = (源文件中 `m` 的隐藏集 ∩ 源文件中 `)` 的隐藏集) ∪ {m} = {m}。`f` 不在 {m} 中，且后跟 `(`，所以展开 `f(w)`。
- `m(m)`：实参 `m` 单独展开时后面没有 `(`，原样保留。代入后结果 `m ( w )` 中的 `m` 隐藏集为 {m}——包含它自己，不展开。`w` 的隐藏集 {m} 不含 `w`，展开为 `0,1`。

注意第二种情况中，`m` 之所以不展开，是因为它在代入后才获得隐藏集 {m}；实参展开阶段它没被涂蓝（只是后面没有 `(`）。按标准的说法：`m` 是在"正在替换 `m` 的替换列表的重新扫描"中被发现的，因而不替换并永久涂蓝。
</details>

## 小结

!!! summary
    - 替换完成后删除 placemarker，再**连同源文件后续记号**重新扫描：替换结果的末尾可以和后面的 `(...)` 组成新调用。
    - 实参的划分在展开之前完成，实参展开出的逗号不会增加实参个数。
    - 扫描替换列表时遇到正在替换的宏名、或嵌套替换中遇到它：不替换，并且**永久**涂蓝——蓝色跟着记号走，经由实参传递也不褪色。
    - 宏名后面"下一个记号"不是 `(` 时只是错过调用，不是涂蓝；延迟展开技巧就利用了这一点。
    - 宏展开结果不是指令，但其中的 `_Pragma` 会被执行。
    - `f(2)(9)` 这类"一半在替换结果、一半在源文件"的情形，C 明确为未指定，主流实现按 Prosser 算法得到 `2*9*g`。
