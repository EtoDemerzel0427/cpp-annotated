!!! tldr
    - 契约把前置条件、后置条件写在函数声明上，并让构建方式决定违反时怎么处理；C 的 `assert` 宏两点都做不到。
    - C++20 草案里曾有一版契约（`[[expects: …]]`），2019 年在标准发布前被整体撤回，从未出现在任何已发布的标准中。
    - 撤回的根源是三个问题没有共识：没检查的契约能否被编译器当作假设、违反后能否继续执行、语义由全局开关还是逐条指定。
    - C++26 的回答是四种具名的求值语义（ignore、observe、enforce、quick-enforce），由实现选择；没有假设语义；没有共识的地方一律非良构，留给以后扩展。
    - 争论没有结束：同一个内联函数在不同翻译单元中以不同语义编译的问题、总是强制检查的断言，都留到了 C++29；虚函数上的契约已进入 C++29 草案。

## 契约要解决什么问题

一个函数的接口约定有三部分：调用者必须保证什么（**前置条件**，precondition），函数返回时保证什么（**后置条件**，postcondition），以及函数体里某一点上必然成立的条件（断言）。C 的 `assert` 只能表达第三种。

<div class="compare" markdown="1">

```cpp
// C 的 assert：只能写在函数体里
#include <cassert>
int isqrt(int x) {
    assert(x >= 0);
    int r = 0;
    while ((r + 1) * (r + 1) <= x) ++r;
    return r;
}
```

```cpp
// C++26：条件是声明的一部分
int isqrt(int x)
    pre(x >= 0)
    post(r: r * r <= x);
```

</div>

左边的条件藏在实现里，调用者、静态分析器和编译器在调用处都看不到它；它只有开（`abort`）和关（`NDEBUG`）两种状态。右边的条件写在声明上，调用处就能检查；违反之后做什么，由构建方式选择。C++26 的这段代码本机 Clang 23 还不能编译，本页的契约代码因此都不标判定。

这套思想叫**契约式设计**（Design by Contract），由 Bertrand Meyer 通过 Eiffel 语言在 1980 年代推广。Eiffel 还规定了契约与继承的关系：覆盖函数的前置条件只能放宽、后置条件只能加强。后面会看到，这条规则在 C++ 里引起了最长的一段争论。

## 早期的两次尝试

### 仿照 D 语言（2004–2006）

第一份提案 [[N1613]] 照搬了 D 语言的做法，在函数体之前加上 `in`、`out` 块：

```cpp title="N1613 的语法（历史提案，未被采纳）"
int foo(int& i)
in {              // 前置条件
    i > 0;
}
out {             // 后置条件
    i == in i + 1;
    return % 2 == 0;
}
do {              // 函数体
    ++i;
    return 4;
}
```

它还包括类不变式、引用参数旧值的语法（`in i`，后来几经改名），以及 Eiffel 式的继承规则。经过几次修订仍未进入 C++0x。Stroustrup 的总结是，失败主要因为复杂度和记法让人觉得过重（HOPL IV §9.6.1）。

### 断言宏（2013–2015）

第二次尝试来自 Bloomberg：[[N3604]] 把公司内部长期使用的断言宏标准化，带有 safe、debug、optimized 三个检查级别、多种构建模式和用户可定义的违约处理函数。最后一版里，宏的名字恰好叫 `contract_assert`。

这条路线同样没有成功。Stroustrup 指出两个问题：它基于宏；它只是实现内部的断言，没有让接口本身表达更多东西（HOPL IV §9.6.1）。不过它带来的检查级别和违约处理函数两个概念，在后来的每一版设计里都能找到。

## C++20 契约：三个开关

2016 年，宏契约一方与另一组强调静态分析的作者合写了 [[P0380R1]]，再由 [[P0542R5]] 写成措辞，2018 年并入 C++20 工作草案。它用一种像属性、但并不是属性的语法：

```cpp title="C++20 工作草案中的契约（2019 年已移除）"
int f(int x, int y)
    [[expects: x > 0]]           // 前置条件
    [[expects audit: y != 0]]    // 检查级别为 audit
    [[ensures r: r > x + y]]     // 后置条件，r 是返回值
{
    int n = get_n();
    [[assert: n > 0]];           // 断言
    return x + y + n;
}
```

一条契约是否被检查、违反后会怎样，由三个开关组合决定：

- **检查级别**（contract level），写在每条契约上：`default` 开销低，生产环境也可以检查；`audit` 开销高，只在专门的构建中检查；`axiom` 只给静态分析器看，从不在运行时检查。
- **构建级别**（build level），全局设置：`off`、`default`、`audit`，决定哪些级别的契约会被检查。
- **违约继续模式**（violation continuation mode），全局设置：违约处理函数返回之后，程序终止还是继续执行。

继续模式最有争议。Bloomberg 的经验是，给大型老代码库加契约时一定会出现违反，其中有些代码其实没错，错的是新写的契约。如果可以记录违反然后继续运行，就能在已上线的程序里打开契约、一次运行发现多处问题。这一点后来被各方接受为渐进采用契约的前提（HOPL IV §9.6.1）。

## 为什么被撤回

### 没检查的契约变成了假设

按 P0542R5 的措辞，一条没有被检查的契约如果谓词为假，行为未定义。换句话说，关掉检查之后，编译器可以假设谓词成立。看一段代码：

```cpp title="C++20 契约语法（HOPL IV 中的例子）"
[[assert: p != nullptr]];
p->m = 7;
```

如果打开了检查、继续模式又允许违反后继续执行，那么检查失败后下一行仍会运行。编译器从 `p->m` 推出 `p` 非空（否则后一行就是 UB），再据此删掉前面的检查。本来用来发现错误的检查，被它要捕捉的错误本身优化掉了，这种现象常被称为 time-travel optimization（HOPL IV §9.6.1）。一部分人认为未检查即假设正是设计意图，可以帮助优化；另一部分人认为加一条契约就引入新的 UB 不可接受（P2899R1 §3.5.4）。

### 全局开关还是逐条指定

2018 年下半年，Bloomberg 的作者们提出让每条契约直接写出自己的语义，例如 `[[assert check_maybe_continue: x > 0]]`；2019 年的 [[P1607R1]] 提议用这种逐条指定的语义取代检查级别。理由是三级刻度加一个全局继续开关不够用：大型机构需要对不同的库、不同的条件分别控制。反对的一方认为这是在特性冻结前夕改变已有共识的设计，可能把断言变成一种新的控制流机制（HOPL IV §9.6.1）。

### 撤回

2019 年 7 月，C++20 特性冻结的那次会议上，EWG 先接受了 P1607 的方向，随后改为采纳 [[P1823R0]]，把整个契约从 C++20 中移除。P1823R0 的理由是：刚接受的修改是改进还是倒退没有共识，连原设计的作者之间也有分歧；没有实现经验；按照火车模型（每三年准时发布，没准备好的特性坐下一班），继续强推会给整个 C++20 带来风险。

会后成立了契约研究组 SG21。同时，向编译器注入假设的需求被单独拿出来，成了 C++23 的 `[[assume]]` 属性（[[P1774R8]]，见 [[dcl.attr.assume]]）。这样，优化提示和正确性检查从此是两个不同的工具。

## C++26：从最小可行产品重新出发

### 先列出分歧

SG21 没有在 C++20 设计上修补，而是先整理失败的原因。[[P2076R0]] 把分歧归纳为几个问题，P2900 对每一个都给出了明确的回答（P2899R1、P2900R14 §3.1）：

| C++20 时的分歧 | C++26（P2900）的处理 |
|---|---|
| 没检查的契约是否被假设成立 | 不提供假设语义。契约不引入新的 UB，谓词自身的 UB 除外 |
| 违反后能否继续执行 | 保留 observe 语义，但规定契约不是控制流，不能用来做错误处理 |
| 用一条级别刻度控制检查 | 取消级别。每次求值用哪种语义由实现决定 |
| 全局开关与逐条指定语义 | C++26 都不规定，留给实现和以后的扩展 |

新设计先只做一个最小可行产品（minimum viable product，MVP）：三种断言、几种语义、一个违约处理函数，其余全部推后。[[P2900R14]] 于 2025 年 2 月并入 C++26 草案。

### 语法

C++20 的双方括号被放弃了。契约与属性性质不同：属性可以被实现忽略，契约不能。SG21 比较了几种语法后选择了 [[P2961R2]] 的写法：

<div class="compare" markdown="1">

```cpp
// C++20 草案（已移除）
int f(int x)
    [[expects: x > 0]]
    [[ensures r: r > x]]
{
    [[assert: x != 42]];
    return x + 1;
}
```

```cpp
// C++26
int f(int x)
    pre(x > 0)
    post(r: r > x)
{
    contract_assert(x != 42);
    return x + 1;
}
```

</div>

`pre` 和 `post` 是上下文关键字，只在这个位置有特殊含义，不会破坏名叫 `pre` 的变量。断言语句用新关键字 `contract_assert` 而不是 `assert`，以免与 C 的 `assert` 宏冲突。

### 三个开关变成四种语义

C++20 里，一条契约的行为要从三个开关的组合推出来。C++26 把可能的结果直接列成四种[[g:evaluation-semantic|求值语义]]（[[basic.contract.eval#1]]）：

| 语义 | 检查谓词 | 违反之后 |
|---|---|---|
| ignore | 否 | — |
| observe | 是 | 调用违约处理函数，返回后继续执行 |
| enforce | 是 | 调用违约处理函数，然后终止 |
| quick-enforce | 是 | 立即终止，不调用处理函数 |

每次求值使用哪一种是实现定义的（[[basic.contract.eval#2]]），标准只建议实现提供全部 ignore 和全部 enforce 两种编译选项，并默认 enforce（[[basic.contract.eval#3]]）。quick-enforce 是后加的（[[P3191R0]]），面向承受不了违约处理机制开销、或希望尽量缩小攻击面的场合。

违约处理函数也从实现定义的设置方式，变成一个可替换的普通函数 `::handle_contract_violation`（见 [[g:contract-violation-handler]]、[[support.contract]]）：

```cpp title="handler.cpp（C++26，本机无法编译）"
#include <contracts>
#include <cstdio>

void handle_contract_violation(
    const std::contracts::contract_violation& v) {
    std::fprintf(stderr, "contract violated: %s\n",
                 v.comment());
    // 正常返回后：observe 下继续，enforce 下终止
}
```

### 几条乍看奇怪的规则从哪里来

P2900 列出了一组设计原则，其中几条直接解释了今天的条文：

- 在正确的程序里，契约断言是多余的。加上或去掉任何一条都不应改变正确程序的含义。所以契约不影响概念是否满足、重载决议的结果、`noexcept` 运算符的值。
- 谓词不应有副作用，各次求值彼此独立。所以标准允许实现不真正求值谓词，只要能知道它的值（[[basic.contract.eval#5]] 的例子里，谓词中的 `s.g++` 可能根本不发生）。
- 没有共识的问题，一律先规定为非良构，而不是未指明或未定义。以后放宽为合法时，不会改变任何已有程序的含义。C++26 中虚函数不能带 `pre`/`post`，就是这条原则的应用。

另一项相关的改动是可观察检查点（[[g:observable-checkpoint]]，[[P1494R5]]）：契约检查之前已经发生的输出，不会被检查之后的 UB 抹掉（[[basic.contract.eval#6]]）。这是对 C++20 time-travel 问题的另一半回答。

## 虚函数：反复最多的问题

覆盖函数和被覆盖函数的契约是什么关系？有两种模型。

第一种是 Eiffel 和 D 的继承模型：覆盖函数继承基类的契约，可以放宽前置条件、加强后置条件。第二种是 [[P3097R3]] 的调用方/被调用方模型：每个函数有自己独立的契约。通过基类引用做虚调用时，先检查静态选中的函数（基类那个）的前置条件，再检查实际调用的函数的前置条件；后置条件反过来。

```cpp title="C++29 草案中的虚函数契约（本机无法编译）"
struct Shape {
    virtual void scale(double k) pre(k > 0);
};
struct Circle : Shape {
    void scale(double k) override pre(k >= 0);
};

void g(Shape& s) {
    s.scale(2.0);
    // 先检查 Shape::scale 的 pre，再检查 Circle::scale 的 pre
}
```

这样做的理由是：通过 `Shape&` 调用的人只知道 `Shape` 的约定，应当按它来检查；`Circle` 的作者也有权保护自己的实现。代价是它偏离了几十年来的经典模型，也没有部署经验。

SG21 和 EWG 在两种模型之间来回了几次。P3097 的模型一度并入 P2900，又在 2025 年 2 月 P2900 进入 C++26 的那次会议上被移除，C++26 因此规定虚函数带 `pre`/`post` 非良构。2026 年 6 月，P3097R3 并入 C++29 工作草案，当前草案的 [[expr.call#5]] 就是上面描述的检查顺序，`__cpp_contracts` 的值也随之变为 `202606L`。按"先非良构，后放宽"的原则，这一步没有改变任何 C++26 程序的含义。

## 进入 C++26 之后仍然存在的反对意见

P2900 并入 C++26 时有相当数量的反对票，C++26 定稿前又有人提议把它移出。反对意见里有几个技术问题至今还在讨论：

- **谓词本身可能有 UB。** 契约检查是为了发现错误，但谓词里的越界访问、空指针解引用照样是 UB。反对者（[[P3173R0]]、[[P3506R0]]）认为这违背了安全优先的原则。P2900 的立场是契约不引入新的 UB，但不消除谓词自身的 UB。
- **契约提供哪一种安全。** 只要实现可以选择 ignore 或 observe，契约就不能保证某个检查一定会拦住执行。[[P3500R1]] 区分了功能安全（程序按规格运行）与语言安全（没有 UB），并说明了在现有设计下让断言总是强制执行的几种做法。
- **不同翻译单元以不同语义编译。** 同一个内联函数或模板可能在多个以不同语义编译的翻译单元里实例化，链接器最终留下哪一份不确定。于是库作者没法保证自己的检查一定以 enforce 执行（[[P3835R0]]）。

第三个问题催生了"总是强制检查"的断言提案（[[P3911R2]]，候选语法如 `pre!(…)`），但它对 ABI 的影响没能在 C++26 时间框架内解决，被推到 C++29（[[P3850R0]]）。C++29 的路线还包括给契约加标签、按库分组控制语义（[[P3400R4]]），以及让现有断言宏接入同一套违约处理机制（[[P3290R6]]）。标签实际上把 C++20 检查级别想解决的问题又拿了回来，只是这次由用户自己定义分组。

## 与标准库加固的关系

和 P2900 同一次会议并入 C++26 的还有标准库加固（[[P3471R4]]）。它给 `std::span`、`std::string_view`、`std::vector`、`std::optional` 等的越界和空值访问规定了[[g:hardened-precondition|加固前置条件]]：在加固的实现中，这些条件在调用前一定会被检查；在未加固的实现中，违反它们仍是 UB（[[structure.specifications#3.5]]）。

<div class="compare" markdown="1">

```cpp
// 未加固的实现
std::vector<int> v(3);
int x = v[10];   // UB
```

```cpp
// 加固的实现（C++26）
std::vector<int> v(3);
int x = v[10];   // 契约违反，
                 // 以终止型语义处理
```

</div>

最初的措辞允许用 observe 语义检查加固前置条件。可是在 observe 下，处理函数返回后越界访问照样会发生。[[P3878R1]] 主张加固不得使用 observe，2025 年 11 月被采纳；当前草案要求以终止型语义（enforce 或 quick-enforce）检查加固前置条件（[[structure.specifications#3.5.1]]）。

## 常见误解

!!! pitfall "C++20 里有契约"
    没有。C++20 契约只在工作草案中存在了约一年，在 C++20 发布前就被 P1823 整体移除。GCC 曾有该版本的实验性实现，那不是标准 C++。

!!! pitfall "C++26 的契约默认会被检查"
    标准没有这样规定。每次求值用哪种语义由实现定义（[[basic.contract.eval#2]]）；默认 enforce 只是建议做法（[[basic.contract.eval#3]]），不是强制要求。

!!! pitfall "没检查的契约会被优化器当作假设"
    这是 C++20 契约的问题。C++26 的 ignore 语义没有任何效果：谓词仍是潜在求值的（其中 odr-use 的函数照样需要定义），但不会被求值（[[basic.contract.eval#4]]）。需要向编译器注入假设，应使用 `[[assume]]`（[[dcl.attr.assume]]）。

!!! pitfall "contract_assert 只是换了名字的 assert"
    `contract_assert` 是语句而不是宏，不受 `NDEBUG` 控制；它的语义由实现在四种中选择；违反时调用可替换的违约处理函数；谓词抛出异常也算违反（[[basic.contract.eval#7]]）。
