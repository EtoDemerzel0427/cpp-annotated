[[lex.phases]] 只有一段（¶1），却是整本标准的时间轴，它规定了哪条规则在什么时候生效。很多看似奇怪的现象，例如宏不能产生注释、`#include "a" "b"` 不会拼接、原始字符串里的反斜杠加换行不会拼接、`#if` 里 `new` 等于 0，都是阶段次序的直接推论。

读这一节前最好知道，[[g:preprocessing-token|预处理记号]]（[[lex.pptoken]]）与记号（token，[[lex.token]]）是两种不同的东西：前者存在于阶段 3–6，后者从阶段 6 开始才存在。

!!! std
    The precedence among the syntax rules of translation is specified by the following phases.

    阶段描述的是语法规则之间的优先次序，不是编译器必须照做的流水线。

脚注 7 进一步说明，实现只需表现得如同（as if）这些阶段依次发生，实际上可以把多个阶段合并。Clang 的 `Lexer` 就是在一次扫描里同时完成解码、行拼接和记号化的。所以下文讨论的先后是**语义上的先后**：一个阶段的结果决定了下一个阶段看到什么。

## 总览

| 阶段 | 输入 → 输出 | 关键动作 | 典型后果 |
|---|---|---|---|
| 1 | 字节 → 翻译字符集元素序列 | UTF-8 解码；CR/CRLF → 换行 | 必须支持 UTF-8 源文件 {{c++23}} |
| 2 | 字符 → 逻辑源行 | 删 BOM；`\` + 空白 + 换行 被删除 | `//` 注释末尾的 `\` 会吞掉下一行 |
| 3 | 字符 → 预处理记号 + 空白 | 注释 → 一个空格；识别 UCN | 宏无法生成注释；最长匹配 |
| 4 | 预处理记号 → 预处理记号 | 执行指令、展开宏、`_Pragma` | `#include` 递归走 1–4 |
| 5 | 预处理记号 → 预处理记号 | 相邻字符串字面量拼接 | `"a" MACRO "b"` 可以拼接 |
| 6 | 预处理记号 → 记号 | 转换为关键字/标识符/字面量… | 关键字从这里才存在 |
| 7 | 记号 → 翻译后的 TU | 语法、语义分析；实例化；常量求值 | 实例化失败即非良构 |
| 8 | 多个 TU → 程序映像 | 解析外部引用、链接库 | 链接 |

## 阶段 1：输入文件与字符映射（¶1.1）

¶1.1 规定了三件事。

**(a) 必须支持 UTF-8 文件。** 实现必须支持由 UTF-8 code unit 序列构成的输入文件，还可以另外支持实现定义的其他种类的输入文件。如果支持其他种类，文件种类以实现定义的方式确定，而这种方式**必须包含一种与内容无关的、把文件指定为 UTF-8 的手段**。注 1 点明了用意：只靠识别 U+FEFF 字节序标记（BOM）是不够的。换句话说，编译器必须提供命令行选项之类的开关，让用户能声明某个文件是 UTF-8，而不是让编译器去猜。

为什么要这样写？在 C++20 及以前，从源文件到基本源字符集的映射完全是实现定义的，标准连 UTF-8 都不保证。于是同一份含中文注释的源码，在 MSVC 的默认设置（按系统代码页解释）下可能读成乱码。这条规则来自 C++23 的 [[P2295R6]]。

**(b) UTF-8 文件的解码。** 如果文件确定为 UTF-8，它必须是良构的 UTF-8 序列（否则程序非良构），解码为 Unicode 标量值序列后，再一一映射到[[g:translation-character-set|翻译字符集]]（[[lex.charset]]）的元素。

**(c) 换行规范化。** CR LF 对和单独的 CR 都替换为一个换行字符，所以 Windows（CRLF）和老式 Mac（CR）风格的文件行为相同。这一点在原始字符串中尤其重要：

```cpp run title="crlf.cpp" ok
#include <cstring>
// 无论此文件以 LF 还是 CRLF 保存，s 里的换行都只是一个 '\n'
const char* s = R"(line1
line2)";
int main() { return std::strlen(s) == 11 ? 0 : 1; }
```

对于其他种类的输入文件，字符映射以实现定义的方式完成，行尾指示同样表示为换行字符。

!!! impl "实现视角"
    - GCC 默认假定源文件是 UTF-8，可用 `-finput-charset=` 指定其他编码。
    - Clang 只接受 UTF-8 源文件（以及带 BOM 的 UTF-8）。
    - MSVC 在没有 BOM 时默认按当前代码页解释，用 `/source-charset:utf-8` 或 `/utf-8` 指定 UTF-8，这正是 ¶1.1 要求的与内容无关的手段。

### 三字符组（trigraph）去哪了

在 C++14 及以前，阶段 1 还要替换三字符组（`??=` → `#`、`??/` → `\`、`??!` → `|` 等 9 个）。C++17 删除了这一要求（[[N4086]]）。Annex C（[[diff.cpp14.lex]]）指出，实现仍可以把三字符组的翻译作为实现定义的输入字符映射的一部分继续保留，但不得在原始字符串字面量内部这样做。

删除的理由很实际：三字符组几乎只会意外出现，最有名的一例是注释末尾的 `????/`：

```cpp run title="trigraph.cpp" std=c++14 flags="-std=c++14" impl
#include <cstdio>
int main() {
  // 会打印吗????/
  std::puts("yes");
}
```

在 C++14 中，`??/` 是 `\`，于是阶段 2 把下一行拼进注释，`puts` 就消失了。用 Clang 实测，`-std=c++14` 下什么也不打印；`-std=c++17` 及以后打印 `yes`，并给出 "trigraph ignored" 警告。

## 阶段 2：BOM 与行拼接（¶1.2）

¶1.2 做三件事。

1. 如果第一个翻译字符是 U+FEFF，删除它。
2. **行拼接**：删除每个由反斜杠、零个或多个除换行外的空白字符、换行组成的序列，物理源行由此拼成[[g:logical-source-line|逻辑源行]]。每个物理行上只有最后一个反斜杠有资格参与拼接。
3. 如果文件非空且（拼接后）不以换行结尾，就按末尾追加了一个换行处理。

反斜杠与换行之间允许空白，是 C++23 的变化（[[P2223R2]]）。之前标准要求反斜杠紧邻换行，但 GCC 早就容忍尾随空白，而 MSVC 和 Clang 不容忍，同一份代码在不同编译器上意义不同。标准选择了 GCC 的行为，因为尾随空白肉眼看不见，让它改变程序的意义只会制造 bug。Clang 现在仍会对此警告 `-Wbackslash-newline-escape`，但照标准拼接。

```cpp run title="splice.cpp" ok
#include <cstring>
int main() {
  const char* q = "a\   
b";   // 上一行反斜杠后有 3 个空格：C++23 起仍然拼接，q == "ab"
  return std::strcmp(q, "ab");
}
```

### 拼接先于注释识别

阶段 2 在阶段 3（识别注释）之前，所以 `//` 注释末尾的反斜杠会把下一行拼进注释：

```cpp run title="comment-splice.cpp" ok
int main() {
  int x = 1; // 这一行以反斜杠结尾 \
  x = 2;
  return x;   // 返回 1：x = 2; 是注释的一部分
}
```

Clang 对此给出 `-Wcomment`（"multi-line // comment"）警告。这是行拼接最常见的出错来源，在注释里画 ASCII 图、或在 Windows 路径末尾写 `C:\dir\` 时尤其容易出现。

### 拼接可以形成 UCN

注 2：行拼接可以拼出一个 *universal-character-name*。

```cpp run title="ucn-splice.cpp" ok
const char32_t* s = U"\u00\
41";                 // 拼接后为 U"\u0041"，即 U"A"
int main() { return s[0] == U'A' ? 0 : 1; }
```

在 C++20 及以前，标准规定这种情况是 UB；C++26 的 [[P2621R2]] 清理词法中的 UB 时把它改成了明确合法。

### 原始字符串会撤销拼接

阶段 2 是无条件的，但 [[lex.pptoken#5]] 规定，在原始字符串字面量的两个引号之间，阶段 2 的变换要撤销（revert）。所以原始字符串里写的 `\` 加换行会原样保留，见 [[lex.string]] ¶4 的例子。这是阶段模型中少有的回退操作，目的是让 `R"(...)"` 真正做到所见即所得。

### 末尾换行

C++03 要求非空源文件以换行结尾，否则是 UB；从 C++11 起改为视作追加了一个换行。这对 `#include` 很重要：即使被包含文件不以换行结尾，它的最后一行也不会和包含者的下一行粘在一起。

## 阶段 3：分解为预处理记号（¶1.3）

源文件分解为[[g:preprocessing-token|预处理记号]]（[[lex.pptoken]]）和空白序列（含注释）。要点如下。

- **文件不得以不完整的预处理记号或不完整的注释结尾**（脚注 9 举的例子是缺少闭合 `"` 或 `>` 的 *header-name*，或没有闭合的 `/*`）。这是一条 shall 规则，违反即非良构。因此每个被 `#include` 的文件自身必须在词法上完整，不能在 a.h 里开一个 `/*`，指望在 b.h 里关掉。
- 每个注释替换为一个空格（U+0020），换行保留。
- 除换行外的非空空白序列是保留还是替换成一个空格，是未指定的。这几乎只影响 `-E` 输出的外观；字符串化（`#`）本身就会规范化空白，所以无法写出依赖它的可移植程序。
- 在形成下一个预处理记号的过程中（不包括消耗注释和空白时），*universal-character-name* 会被识别并替换为对应的翻译字符集元素，但在 *c-char-sequence*、*s-char-sequence*、*r-char-sequence*、*h-char-sequence*、*q-char-sequence* 里除外。
- 划分预处理记号是上下文相关的，例如 `<` 在 `#include` 之后可以开始一个 *header-name*（[[lex.header]]）。

### 注释在阶段 3 就消失了

由于注释在阶段 3 已经替换成空格，阶段 4 的宏永远看不到注释，也造不出注释：

```cpp title="no-comment-macro.cpp" error
#define CAT(a, b) a##b
CAT(/, /) this is not a comment   // error: 拼出的 // 不是合法的预处理记号
```

`##` 的结果必须是一个合法的预处理记号，而 `//` 不是任何预处理记号（它只是注释的开始）。在当前草案中这是非良构（[[cpp.concat]]）；在 C++23 及以前是 UB。

同理，注释替换为一个空格，意味着 `a/**/b` 是两个记号 `a` 和 `b`。K&R C 时代某些预处理器把 `/**/` 当作粘合记号的手段，与此不同。

### 为什么 UCN 在字面量内部不在阶段 3 替换

在 *c-char-sequence*/*s-char-sequence* 中，UCN 保持原样，直到字面量求值时才编码（[[lex.string#10]]）。这是因为 `"\u0041"` 和 `"A"` 虽然最终可能相同，但 UCN 在字面量里还要接受额外检查（例如能否在关联编码中表示）；而在 *r-char-sequence* 中，`\u0041` 根本不是 UCN，只是 6 个普通字符。在 *h-char-sequence* 中不做替换，则避免了误读 `#include "C:\users\..."` 这类路径（其中出现了 `\u`）。

## 阶段 4：预处理（¶1.4）

源文件作为 *preprocessing-file*（[[cpp.pre]]）进行分析：执行预处理指令，展开宏调用（[[cpp.replace]]），执行 `_Pragma` 一元运算符表达式（[[cpp.pragma.op]]）。`#include` 使所命名的头文件或源文件**从阶段 1 到阶段 4 递归处理**。最后删除所有预处理指令，此后分隔预处理记号的空白不再有意义。

由此可以得出几个推论。

1. **被包含文件各自独立地经历阶段 1–3**。所以每个文件可以有自己的编码判定和自己的 BOM，一个文件里没闭合的注释不能延续到另一个文件。
2. **阶段 4 中还没有关键字**。[[lex.name]] 注 4 说，阶段 4 里的 *identifier* 包含那些到阶段 7 才区分为关键字的预处理记号。于是在 `#if` 中，除 `true`/`false` 以外的所有标识符和关键字都替换为 `0`（[[cpp.cond]]）：

```cpp run title="if-keyword.cpp" ok
#if new == 0 && true && !false   // new 在这里只是一个标识符，求值为 0
int ok = 1;
#endif
int main() { return ok - 1; }
```

3. **空白不再有意义**：阶段 4 之后，`a  +  b` 与 `a+b` 的记号序列完全相同。但在阶段 4 内部，空白是有意义的，例如 `#define F(x)` 定义的是函数式宏，`#define F (x)` 定义的是对象式宏（[[cpp.replace]]）。

## 阶段 5：字符串字面量拼接（¶1.5）

如果有两个或更多相邻的 *string-literal* 预处理记号，先按 [[lex.string]] 确定一个公共编码前缀，每个字符串都视为带有该前缀，然后拼接。

由于拼接发生在宏展开之后，宏产生的字符串可以参与拼接：

```cpp run title="concat.cpp" ok
#define GREETING "Hello, "
const char* s = GREETING "world";             // "Hello, world"
static_assert(sizeof(GREETING "world") == 13);
int main() {}
```

反过来，`#include` 在阶段 4 处理，那时字符串还没有拼接，所以 `#include "dir/" "file.h"` 不会变成 `"dir/file.h"`（[[cpp.include]] 的注 2 也特意提到这一点）。

拼接的细节，包括 `\xA` 与 `"B"` 拼接时不会合并成 `\xAB`、前缀冲突的处理、用户定义字面量后缀的处理，见 [[lex.string#7]]、[[lex.string#8]] 与 [[lex.ext#8]]。

!!! history
    在 C++20 及以前，翻译阶段一共有 9 个：拼接之前还有一个阶段 5，负责把字符/字符串字面量中的字符从源字符集映射到执行字符集，之后是拼接（阶段 6）、分析（阶段 7）、实例化（阶段 8）、链接（阶段 9）。C++23 的字符集重构（[[P2314R4]]）把编码移入字面量自身的语义（[[lex.charset]]、[[lex.ccon]]、[[lex.string]]）；后来实例化也被并入分析阶段，于是成了今天的 8 个阶段。很多教材和博客仍按旧的 9 阶段编号，读的时候注意版本。

## 阶段 6：预处理记号 → 记号（¶1.6）

每个预处理记号转换为一个记号（[[lex.token]]）。这一步做了几件之前没有做的事：

- 区分关键字与标识符（[[lex.key]]）；
- 把 *pp-number* 变成 *integer-literal* 或 *floating-point-literal*，如果它两者都不是（例如 `0xe+foo`、`1..2`），程序非良构（[[lex.ppnumber]]、[[lex.pptoken#3]]）；
- 字面量从这时起有了类型和值（在此之前，[[lex.ppnumber#2]] 说 pp-number 没有类型和值）；
- 如果某个单个非空白字符形式的预处理记号不能转换为记号（如源码中游离的 `` ` `` 或 `$`），程序非良构（[[lex.pptoken#3]]）。

## 阶段 7：分析与翻译（¶1.7）

记号构成一个**翻译单元**（translation unit），作为 *translation-unit*（[[basic.link]]）进行语法和语义分析并翻译。本阶段包含的内容远不止语法分析。

### 记号可能被替换

注 3：分析过程中偶尔会把一个记号替换为一串其他记号。最著名的是 [[temp.names]] 的规则：在模板实参列表中，第一个非嵌套的 `>>` 当作两个 `>` 处理。这不是词法层面的特例（词法上 `>>` 仍按最长匹配形成一个记号，见 [[lex.pptoken#5]]），而是语法分析阶段对记号的拆分。

### 模块依赖

当前 TU 有接口依赖的模块单元与头文件单元（[[module.unit]]、[[module.import]]），是否要求其源码可用，由实现定义。实践中，编译器需要的是这些单元编译后的接口产物（BMI/CMI），而不是源码。注 4 提醒，TU 之间通过具有外部链接或模块链接的名字以及数据文件来通信。

### 实例化

在分析和翻译记号的同时，执行所需的实例化（包括显式请求的实例化，[[temp.explicit]]）。实例化可以在哪些上下文中进行，由各自的实例化点决定（[[temp.point]]）。注 6 指出，其他规则可能带来进一步的约束，例如一个 constexpr 函数模板特化的实例化点可能在 TU 末尾，但在某些常量表达式里使用它需要更早实例化（[[temp.inst]]）。

**任何实例化失败，程序即非良构。**

### 常量求值及其副作用 {{c++26}}

在分析和翻译过程中，每个显式常量求值（manifestly constant-evaluated）的表达式都会求值（[[expr.const.defns]]）。这些值会影响程序中命名的类型和使用的反射值，从而影响语法分析本身；求值还可能产生**影响分析的副作用**。

C++26 静态反射（[[P2996R13]]）引入了可产生副作用的常量求值，这一段规则才变得必要。`std::meta::define_aggregate` 这类元函数在 `consteval` 块中求值时会完成一个类的定义，这是对编译器状态的修改。标准必须说明，在程序点 P 分析代码时，哪些副作用已经发生。¶1.7 的答案是：表达式 E 作为完全表达式求值所产生的副作用在 P 处已完成，当且仅当

- ¶1.7.1　E 是某个 *consteval-block-declaration*（[[dcl.pre]]）对应的表达式，并且
- ¶1.7.2　该 consteval 块（或它所实例化自的模板定义）从 P 可达（[[module.reach]]），或者从这样一点可达：P 处于某些类的完整类上下文中，取其中最外层类的 *class-specifier* 之后的那一点。

第二个分支照顾的是完整类上下文（[[class.mem.general]]）：成员函数体虽然写在类的中间，语义上却视为在类结束之后分析。标准的例 2 改编如下（需要实现了反射的编译器；Clang 23 主线尚不支持，因此无法在本地验证）：

```cpp
#include <meta>
class S {
  class Incomplete;
  class Inner {
    void fn() {
      /* p1 */ Incomplete i;   // OK：p1 在 S 的完整类上下文中
    }
  } /* p2 */ ;
  consteval {
    std::meta::define_aggregate(^^Incomplete, {});
  }
} /* p3 */ ;
```

在 p1 处，`Incomplete` 已经是完整类型，因为 (1) `define_aggregate` 的调用在 consteval 块中；(2) p1 位于 `S` 的完整类上下文中，而该 consteval 块从 p3（`S` 的 *class-specifier* 之后）可达。反之，如果在 p2 处（不在完整类上下文中）声明 `Incomplete i;`，就不行。

## 阶段 8：链接（¶1.8）

翻译后的 TU 组合在一起，所有外部实体引用得到解析（[[basic.link]]）；链接库组件，以满足对当前翻译中未定义的实体的外部引用。所有翻译器输出收集到一个**程序映像**中，其中包含在执行环境中执行所需的信息。

标准没有提到目标文件、静态库、动态库，这些都是实现细节（见 [[lex.separate]] 注 2）。标准的模型里不存在动态链接：从标准的角度看，程序映像在执行前就已经完整。

## 次序带来的经典后果

| 现象 | 原因 |
|---|---|
| 宏不能生成注释 | 注释在阶段 3 被移除，宏在阶段 4 展开 |
| `//` 注释末尾的 `\` 吞掉下一行 | 拼接（阶段 2）先于注释识别（阶段 3） |
| 原始字符串中的 `\`+换行保留 | 阶段 2 的变换在原始字符串内被撤销 |
| `#include "a" "b"` 不拼接 | `#include` 在阶段 4 处理，拼接在阶段 5 |
| `"x" MACRO "y"` 能拼接 | 宏展开（4）先于拼接（5） |
| `#if new` 为 0 | 关键字在阶段 6/7 才区分 |
| `#define R "x"` 后 `R"y"` 不是 `"x" "y"` | 阶段 3 的最长匹配先形成原始字符串记号，见 [[lex.pptoken#6]] |
| `0xe+foo` 编译失败 | 阶段 3 形成单个 pp-number，阶段 6 转换失败 |
| `vector<vector<int>>` 可以写 | 阶段 7 的语法规则把 `>>` 拆成两个 `>` |
| 模板实例化错误发生在编译期 | 实例化属于阶段 7 |

## 陷阱

!!! pitfall "以为编译器真的分 8 遍处理"
    阶段是概念性的。比如注释替换为空格这一步，在实际编译器中只是跳过注释并记下一个空白标志。用阶段推理的是结果，而不是编译器内部的流程。诊断位置、`-E` 输出的格式都不受阶段模型约束。

!!! pitfall "旧的 9 阶段编号"
    网上常见的"phase 5 是字符集转换、phase 6 是字符串拼接"，说的是 C++20 及以前的编号。当前草案中拼接是阶段 5，转换为记号是阶段 6。

!!! pitfall "以为 `#if 0` 里的内容不做词法分析"
    被跳过的组仍然经过了阶段 3。按 [[lex.pptoken#1]] 的字面规则，`#if 0` 块里一个游离的 `'` 同样使程序非良构；不过实测 Clang 23 对被跳过组中的这类字符不给诊断。不要在 `#if 0` 里随手写英文说明文字（例如 `don't`），应改用真正的注释。

## 思考题

!!! question "思考题 1"
    下面的程序返回什么？

    ```cpp
    #define STR(x) #x
    #define XSTR(x) STR(x)
    int main() {
      const char* s = XSTR(a/**/b);
      return s[1] == ' ';
    }
    ```

<details markdown="1">
<summary>答案</summary>

返回 1。阶段 3 把注释替换为一个空格，所以宏实参是两个记号 `a` 和 `b`，中间有空白。字符串化时，记号之间的空白规范化为一个空格（[[cpp.stringize]]），结果是 `"a b"`，`s[1] == ' '`。
</details>

!!! question "思考题 2"
    为什么 C++26 需要在阶段 7 里专门写一段规则，规定副作用何时完成，而 C++20 的 `constexpr`/`consteval` 求值不需要？

<details markdown="1">
<summary>答案</summary>

C++20 的常量求值对编译器状态没有可观察的副作用：它只计算出一个值，最多导致模板实例化（实例化的上下文已由实例化点规则管理）。C++26 的反射元函数（如 `define_aggregate`）可以修改程序本身，例如完成一个类的定义。于是在程序某一点类 X 是否已完整，取决于哪些 consteval 块已经求值，标准必须给出一个与编译器实现顺序无关的答案，即以可达性（reachability）和完整类上下文为准。
</details>

!!! question "思考题 3"
    a.h 的内容是 `/* begin`（无换行），b.h 的内容是 `end */`。main.cpp 依次 `#include "a.h"`、`#include "b.h"`。这个程序是否良构？

<details markdown="1">
<summary>答案</summary>

非良构。`#include` 让 a.h 独立地经历阶段 1–4；阶段 3 要求源文件不得以不完整的注释结尾（¶1.3），而 a.h 以未闭合的 `/*` 结尾，违反了这条 shall 规则。注释不能跨文件。
</details>

## 小结

!!! summary
    - 8 个阶段：解码与换行规范化 → 拼接（删 BOM）→ 预处理记号化（注释变空格、UCN 识别）→ 预处理（递归 1–4）→ 字符串拼接 → 转为记号 → 分析/实例化/常量求值 → 链接。
    - 阶段是一个 as-if 模型，用来推导结果，而不是描述编译器的结构。
    - C++23：UTF-8 源文件成为必需支持；`\` 与换行之间允许空白。C++17：三字符组移除。
    - C++26：词法中的若干 UB 改为非良构或明确合法；阶段 7 增加了常量求值副作用（反射）的可见性规则。
