!!! tldr
    - Annex B 列出 44 项编译器可能有上限的数量（嵌套层数、参数个数、constexpr 递归深度、模板实例化深度等），每项给一个建议的最小值。这些数字只是建议，不是要求。
    - 实现可以因为程序超出它的限制而拒绝程序，标准没有规定限制必须是多少。
    - 常量求值中超出限额，表达式就不是核心常量表达式；在不要求常量的地方，编译器会悄悄改成运行时初始化。
    - Clang 的 constexpr 深度（512）、constexpr 步数（约 1 048 576）和模板实例化深度（1024）正好取了建议值，都可以用编译选项调整。
    - Clang 的 `#include` 嵌套上限是 200，低于建议的 256，这并不违反标准。

## 合法的程序，编译器可以拒绝吗

```cpp error
constexpr int f(int n) { return n == 0 ? 0 : 1 + f(n - 1); }
static_assert(f(511) == 511);   // OK：共 512 层调用
static_assert(f(512) == 512);   // error: 不是常量表达式（超出 512 层）
```

`f(512)` 没有违反任何语言规则，但本机 Clang 23 拒绝了第三行，附注是 `constexpr evaluation exceeded maximum depth of 512 calls`。抽象机的资源是无限的，真实的编译器不是，这种情况由 Annex B（Implementation quantities，实现限额）和几处正文共同处理。

[[intro.compliance.general#2.1]] 要求实现接受并正确执行没有违反任何规则的程序，但留了一个例外：除非程序超出了实现的资源限制。标准没有规定这些限制必须是多少。[[intro.compliance.general#9]] 只是建议实现在文档里说明它的限制，并指向 Annex B。

Annex B 标着 informative（资料性）。¶1 说实现在许多数量上可能有限制，并列出了一些可能的限制，每项后面方括号里的数字是**可能的最小值**（potential minimum value）。这个数字不是下限保证，实现可以更低。C 标准要求实现至少能翻译一个同时达到全部翻译限制的程序，C++ 连这样的弱保证也没有。

## 常量求值和模板实例化：有明确后果的两项

有两处正文直接引用了 Annex B，让超限有了确定的后果。

[[expr.const.core#2.7]]：超出实现定义限额的表达式不是核心常量表达式。所以 constexpr 递归太深或求值步数太多，结果是这个表达式不是常量，而不是编译器卡死。在要求常量的地方（`static_assert`、`constexpr` 变量、数组长度）这就是编译错误。在只是可以常量求值的地方，编译器会退回到运行时：

```cpp run ok
#include <cstdio>
constexpr int f(int n) { return n == 0 ? 0 : 1 + f(n - 1); }
int g = f(600);   // 超出 512 层，不再是常量初始化，改为动态初始化
int main() { std::printf("%d\n", g); }
```

本机编译没有任何警告，运行打印 `600`，只是 `g` 在程序启动时才计算。

[[temp.inst#18]]：递归实例化的总深度有一个实现定义的上限，无限递归实例化的结果未定义（见 [[ub.temp]]）。

```cpp error
template <int N> struct R { static constexpr int v = R<N - 1>::v + 1; };
template <> struct R<0> { static constexpr int v = 0; };

static_assert(R<1025>::v == 1025);   // OK：恰好在上限内
static_assert(R<1026>::v == 1026);   // fatal error: 超出 1024 层
```

最外层的 `R<1025>` 本身不计入递归深度，所以 `R<1025>` 可以，`R<1026>` 报 `recursive template instantiation exceeded maximum depth of 1024`。这是 fatal error：Clang 遇到它会立即停止整个编译。

Clang 的三个默认值正好是 Annex B 1.38、1.39、1.41 的建议值：

| 限制 | 默认值 | 调整选项 |
|---|---|---|
| constexpr 函数递归深度 | 512 | `-fconstexpr-depth=N` |
| 一次常量求值的步数 | 约 1 048 576 | `-fconstexpr-steps=N` |
| 模板实例化深度 | 1024 | `-ftemplate-depth=N` |

步数的测法是在常量求值中跑一个简单的累加循环：1 048 571 次迭代通过，1 048 572 次失败，附注是 `constexpr evaluation hit maximum step limit; possible infinite loop?`。

## 解析器：栈往往先耗尽

Clang 有一个显式的括号嵌套上限 `-fbracket-depth`，默认 2048，花括号嵌套到第 2049 层时报 `bracket nesting level exceeded maximum of 2048`。但嵌套的圆括号表达式在 1 104 层时，前端就因栈溢出崩溃了，没有诊断信息，退出码 139；嵌套类定义在 759 层时同样崩溃。

这些深度都远超 Annex B 建议的 256，正常代码碰不到。但它说明对于递归下降的解析器，真正的限制往往是机器栈，而不是文档里的某个数字。机器生成的代码最容易撞上。

几项值得多说一句：

- 1.17 的建议值只有 256 KiB，来自嵌入式和分段内存的时代。在 64 位平台上，Clang 接受 1 TiB 的静态数组声明（能否链接和运行是另一回事），而 2⁶¹ 个 `char` 的数组报 `array is too large`：对象的字节数必须能用 `std::size_t` 表示，实现还要为指针差 `std::ptrdiff_t` 留出余地。
- 1.18 是表中唯一低于建议值的一项：头文件嵌套到第 199 层通过，第 200 层（连主文件在内）报 `#include nested too deeply`。真实代码几乎不会碰到。

## 小结

| 问题 | 答案 |
|---|---|
| Annex B 的数字是要求吗？ | 不是，只是资料性的可能最小值，实现可以更低 |
| 程序超出限制时怎样？ | 实现可以拒绝它（[[intro.compliance.general#2.1]]） |
| 常量求值超限呢？ | 表达式不是核心常量表达式（[[expr.const.core#2.7]]）；不要求常量的地方退回运行时初始化 |
| 最可能碰到的限制 | constexpr 的深度和步数、模板实例化深度；机器生成的代码还可能撞上解析器的栈深度 |
