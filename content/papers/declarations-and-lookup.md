!!! tldr
    - C++20 及以前的作用域和名字查找条文分散在几十段里，"作用域"一词有两种定义，很多情形只能靠推测；积压的相关 CWG issue 有几十个，无法逐个修。
    - [[P1787R6]] 整体重写了 [[basic.scope]] 和 [[basic.lookup]]：作用域是程序文本的一段区域，声明栖居于某个作用域、把名字绑定在目标作用域里，查找由单次搜索、搜索、无限定搜索几层操作组合而成。
    - 绝大多数代码的含义没有变。新条文大多是把编译器早已采用的做法写成规则；实现之间有分歧时，选择更一致的那一种。
    - 少数边角情形确实变了，例如带限定名的友元声明里形参类型在哪里查找，以及 `p->X<0>::f()` 在模板中需要写 `template`。本机 Clang 23 在这两处仍按 C++20 的规则处理。
    - 它以缺陷报告（DR）的身份通过，所以没有附录 C 的兼容性条目，编译器也不按 `-std=` 区分新旧规则。

## 旧条文为什么修不动

下面这段代码（例子一）里，`f` 中的 `x` 指什么？

```cpp run title="udir.cpp" error
namespace F { float x; }
namespace A {
  namespace I { int x; }
  using namespace I;
  using F::x;
  void f() {
    x = 0;      // error: 有歧义
    A::x = 1;   // OK：F::x
  }
}
```

答案是第一行有歧义，第二行指 `F::x`。C++20 的条文（以 [[N4861]] 为准）可以推出这个结论，但要拼凑三处规则：using 声明（using-declaration）在 `A` 里引入一个同义词；using 指令（using-directive）让 `I` 的成员在无限定查找时看起来像是声明在同时包含指令和 `I` 的最近外层命名空间里，这里就是 `A`；限定查找 `A::x` 又有另一条规则，先看 `A` 自己的声明，找不到才进入被提名的命名空间。三条规则各写各的，彼此的关系要读者自己推。

这种情况在旧条文里很普遍。[[P1787R6]] 的引言列出了几个根本问题：

- [basic.scope] 用两种方式定义"作用域"，一种是声明区域（declarative region）里名字有效的部分，另一种隐含在查找规则里（[[CWG554]]、[[CWG2165]]）。
- 很多查找规则针对的是一整段程序文本，比如一个包含若干名字和 `<` 的 *template-id*，而不是一个名字。
- 全局命名空间有时被说成一个声明区域，有时被说成多个。
- 很多规则只说"在某某的上下文中查找"，不说从哪个位置查、能看到哪些声明。模块出现后，"只能看到本翻译单元中前面的声明"这个默认假设不再成立，这些规则就变得有歧义。
- 两个同名声明到底是同一个实体的重声明，还是两个互相冲突的实体，没有统一的判断规则。

结果是几十个相关的 CWG issue 积压多年。作者的判断是，条文本身的含糊妨碍了逐个解决它们，于是选择整体重写 [basic.scope]、[basic.lookup] 和 [temp.res] 的一部分。按论文的统计，这一次解决了 63 个核心语言 issue，另有 21 个只在邮件列表上讨论过的问题。

## 新的词汇

重写的核心是一组新定义，它们今天都在 [[basic.scope.scope]] 和 [[basic.lookup.general]] 里。逐条的释义见那两页，这里只列出新旧对照：

| C++20 的说法 | C++23 起的说法 | 变化 |
|---|---|---|
| 声明区域、潜在作用域、作用域 | 作用域（[[g:scope]]） | 只剩一种含义：程序中的一段区域，彼此嵌套成树 |
| 声明点（point of declaration） | 位点（[[g:locus]]） | 属于一个声明，而不是一个名字 |
| 名字被引入某个声明区域 | 声明栖居于（[[g:inhabit]]）某个作用域，把名字绑定（bind）在目标作用域（[[g:target-scope]]）里 | 栖居和目标分开，友元、块作用域 `extern` 这类特殊声明能直接描述 |
| 友元"不能被查找找到" | 友元声明不绑定名字 | 从查找的特例变成声明的性质 |
| 可见、在作用域中 | 先于（[[g:precedes]]）某个程序点 | 明确把模块导入的声明算进来 |
| 在某某的上下文中查找 | 从某个程序点出发查找 | 每次查找都有确定的起点 |
| using 声明引入同义词 | 搜索时用它所指的声明替换它 | 不再产生新的声明 |

查找本身拆成几层操作，每一层只做一件事：

1. **单次搜索**（[[g:single-search|single search]]）：在一个作用域里找绑定了这个名字、并且先于查找点的声明（[[basic.lookup.general#3]]）。
2. **搜索**（[[g:search-in-scope|search]]）：如果作用域是类，单次搜索找不到时再合并基类中的结果（[[class.member.lookup#1]]）。
3. **无限定搜索**（[[g:unqualified-search|unqualified search]]）：如果作用域是命名空间，同时搜索当前活跃的 using 指令提名的命名空间；什么也没找到就到父作用域继续（[[basic.lookup.unqual#2]]）。
4. **无限定查找**从名字所在的程序点出发，在直接作用域里做无限定搜索（[[basic.lookup.unqual#3]]）；**限定查找**在查找上下文（[[g:lookup-context]]）里做搜索（[[basic.lookup.qual#3]]）。

例子一用新规则读起来是一条直线。`x` 是无限定名，从 `f` 的函数体出发向外做无限定搜索，到达 `A` 时，`A` 本身和 `I`（被活跃的 using 指令提名，且包含于 `A`）一起被搜索；`A` 里的 using 声明被替换成 `F::x`，于是同时找到 `F::x` 和 `I::x`，有歧义（[[basic.lookup.general#1]]）。`A::x` 是限定名，在 `A` 里搜索就找到了 `F::x`，按 [[namespace.qual#1]]，只有什么也没找到时才会进入被提名的命名空间。本机 Clang 23 在 `-std=c++20` 和 `-std=c++23` 下都只在 `x = 0` 一行报告 `reference to 'x' is ambiguous`。这个例子的结论没有变，变的是推导过程。

另一个后来补充的词是宿主作用域（host scope）：声明栖居于块作用域时就是那个块作用域，否则是目标作用域。它不在 P1787R6 里，是之后加入草案的，见 [[basic.scope]]。

## 设计上的取舍

P1787 不是一个可以挑方案的新特性，它的取舍体现在两个层面。

第一个层面是整体重写还是逐个修补。相关的 issue 大多是同一类问题的不同表现：某条规则没说从哪里查、看得到什么。逐个修补只会在已经难读的条文上再加特例。论文选择先定义一套能覆盖所有情形的概念，再把各个 issue 作为这套概念的推论来解决。代价是改动量很大，论文说其中很多改动单独看只是编辑性的，但数量多到必须由 CWG 逐条审查。

第二个层面是遇到具体分歧时站在哪一边。论文的原则是：编译器做法一致的，就把做法写成规则；编译器之间不一致的，选择让语言更一致的那一种。具体的选择包括：

- **using 声明不再引入声明。** 旧条文把 `using F::x;` 描述为在当前作用域里声明一个同义词。模块出现后就有了一个难题：这个同义词算不算被导出？论文采纳了核心组邮件列表上提出的方案，查找时直接用 using 声明所指的声明替换它（[[basic.lookup.general#3]]），这个问题就不存在了。
- **规则跟着实现走。** 有些旧规则编译器普遍不遵守，论文直接删掉了。例如 [[CWG1960]] 涉及的一条 using 声明规则，论文称它被实现普遍忽略，并且和 using 声明之间有微妙的相互作用。
- **规则不跟着实现走。** 类的完整类上下文（complete-class context，成员函数体、默认实参等可以看到整个类的地方）里允许不受限制地向后查找，论文保留了这一点，并注明它与当时编译器对非模板类的实际行为不同。在完整类上下文之外，向后补充的声明如果会改变查找结果，程序非良构，不要求诊断；这条限制旧条文就有，现在写在 [[class.member.lookup#6]]。
- **`.`、`->` 之后的名字统一看作限定名。** 旧条文对成员访问后的名字有专门的双重查找规则，新条文把它们归入成员限定名（[[g:member-qualified-name]]），走和 `N::x` 相同的限定查找流程。这带来了下文例子三的行为变化（[[CWG1835]]）。
- **友元声明里的查找只多看一个作用域。** 下文例子二，CWG 对 [[CWG2370]] 的意见是只在被提名的类或命名空间里搜索一次，找不到就回到普通的无限定查找，而不是沿着那个作用域一路向外找。

## 例子二：带限定名的友元声明（行为改变）

```cpp run title="friend.cpp" ok
namespace A {
  using F = float;
  void f(F);
}
namespace B {
  using F = short;
  class Y {
    friend void A::f(F);   // F 是 A::F（float）
  };
}
int main() {}
```

`friend void A::f(F);` 想把 `A` 里已有的 `f(float)` 声明为友元。问题在于形参类型 `F` 该在哪里查找：友元声明写在 `B::Y` 里，`B` 也有一个 `F`。

C++20 的 [basic.lookup.unqual] ¶10 只为友元是成员函数的情形规定了先在那个成员函数的类里查找；其他情形，包括这里的命名空间成员 `A::f`，一律按授予友元关系的类里的无限定名处理。于是 `F` 找到 `B::F`，也就是 `short`，`A` 里没有 `f(short)`，声明非良构。

[[basic.lookup.unqual#6]] 改成：友元声明的 *declarator-id* 是限定名、其嵌套名说明符指定类或命名空间 S 时，出现在这个限定名之后的无限定名先在 S 里做一次搜索，找不到再做普通的无限定查找。`F` 在 `A` 里找到 `A::F`，声明良构。这与在 `A` 之外定义 `A::f` 时形参的查找方式一致，那时 `F` 也是先在 `A` 里找。

!!! impl "编译器现状"
    本机 Clang 23 在 `-std=c++20`、`-std=c++23`、`-std=c++2c` 下都拒绝这一行，报告 `friend declaration of 'f' does not match any declaration in namespace 'A'`，即仍按 C++20 的规则把 `F` 解析为 `B::F`。写成 `friend void A::f(A::F);` 在新旧规则下含义相同，两种模式都能通过。用标准 [[basic.lookup.unqual#6]] 的例 2 测试，Clang 还在 S 是类的情形下沿着 S 的外层作用域继续查找：`friend void W::X::g(D);` 找到 `W::D`（`void`）而报错，`friend void W::X::g(I);` 找到 `::I`（`int`）而通过，两处都与当前草案的判定相反。

## 例子三：成员访问之后的 `<`（行为改变）

<div class="compare" markdown="1">

```cpp title="C++20 可以" error
struct A { void f() {} };
template<int> using X = A;

template<class T>
void g(T* p) {
  p->X<0>::f();  // error（C++23）
}
template void g(A*);
```

```cpp title="两种规则下都可以" ok
struct A { void f() {} };
template<int> using X = A;

template<class T>
void g(T* p) {
  p->template X<0>::f();
}
template void g(A*);
```

</div>

`p->X<0>::f()` 用一个命名空间作用域的别名模板 `X<0>` 来限定成员 `f`。编译器在解析到 `X` 后面的 `<` 时就必须决定它是模板实参列表的开头还是小于号。

C++20 的 [basic.lookup.classref] 为此专门规定：`.` 或 `->` 之后跟着标识符和 `<` 时，先在对象表达式的类里查找这个标识符，找不到再在整个后缀表达式所在的上下文里查找。`*p` 的类型依赖于 `T`，第一步无法进行，第二步找到 `::X`，于是 `<` 开始模板实参列表，左边的写法可以编译。

新条文删除了这条特殊规定。`X` 是成员限定名，查找上下文是依赖类型，按 [[basic.lookup.qual#3]] 在定义处不做查找；它也不是无限定名，不会做无限定查找。按 [[temp.names#7]]，没有 `template` 关键字、查找又没有找到模板时，`<` 就是小于号，整个表达式被解析为 `((p->X) < 0) > ::f()`。实例化 `g<A>` 时 `A` 里没有成员 `X`，程序非良构。要表达原来的意思必须写 `p->template X<0>::f()`，[[basic.lookup.qual]] 的例 3 逐行讲了这些情形。

如果对象表达式不是依赖的，比如 `void h(A* p) { p->X<0>::f(); }`，在 `A` 里找不到 `X` 时会回退到无限定查找，找到 `::X`，新旧规则下都良构。变化只出现在模板里。

!!! impl "编译器现状"
    本机 Clang 23 在 `-std=c++20`、`-std=c++23`、`-std=c++2c` 下都接受左边的代码，不给出警告，仍按 C++20 的规则处理。

## 哪些东西真的变了

对日常代码来说，P1787 几乎是透明的。它改变的是规则的写法，不是大多数程序的含义：

- 例子一那样的普通代码，新旧条文给出相同的答案，只是新条文的推导路径唯一。
- 一部分 issue 的解决方式是把编译器早已采用的做法写进标准。例如 [[CWG110]] 的限制被降级为注释，论文注明这与 GCC、Clang、ICC 的行为一致。
- 真正改变含义的是例子二、例子三这类边角情形。
- 有一处新的弃用：`N::template X` 这样在 `template` 关键字后写类模板或别名模板名、却不带模板实参列表的写法（比如用作模板模板实参）被弃用（[[depr.template.template]]）。本机 Clang 23 对 `S<N::template X>` 在 `-std=c++23` 下没有给出弃用警告。

[[diff.cpp20]] 里没有与 P1787 对应的条目。原因是它被当作缺陷报告处理：委员会认为新条文表达的是一直以来的本意，所以它对之前的标准模式同样适用，编译器也不会按 `-std=` 切换新旧行为（DR 的含义见 [[papers/how-to-read-a-paper]]）。上面的测试也印证了这一点：Clang 在 C++20 和 C++23 模式下的表现完全相同。

实现进度方面，GCC 的 C++ 状态页把 P1787R6 标为 DR、尚未实现；Clang 的 C++ 状态页的 C++23 表格里没有列出这篇论文。从上面的例子看，Clang 23 已经符合新规则的部分，主要是那些新规则本来就照搬现有做法的地方。

与这次重写配套的模板一侧的改动，比如未知特化的成员（member of an unknown specialization）这个术语被依赖的限定名取代，见 [[temp.dep]] 和 [[topics/two-phase-lookup]]；ADL 和定制点的设计见 [[topics/name-lookup-and-customization]]。

## 思考题

!!! question
    在例子二里，把 `namespace A` 中的 `using F = float;` 删掉，`friend void A::f(F);` 中的 `F` 按当前草案找到什么？如果 `A` 里只声明了 `void f(float);`，这一行还良构吗？

<details markdown="1">
<summary>答案</summary>

在 `A` 里搜索 `F` 什么也找不到，于是按 [[basic.lookup.unqual#6]] 退回到从友元声明处出发的无限定查找，依次经过 `Y`、`B`，找到 `B::F`，即 `short`。`A` 里没有 `f(short)`，这个友元声明与 `A` 中的任何声明都不对应，非良构。这时新旧规则的结论相同。
</details>

!!! question
    `template<class T> void g(T t) { t.foo<0>(); }`，其中 `foo` 是 `T` 的成员函数模板。为什么这里必须写 `t.template foo<0>()`？它和例子三有什么不同？

<details markdown="1">
<summary>答案</summary>

`foo` 是成员限定名，查找上下文 `T` 是依赖的，定义处不查找（[[basic.lookup.qual#3]]），`<` 只能按小于号解析（[[temp.names#7]]），所以要写 `template`。这条要求在 C++20 也存在：旧规则的第二步只在外层上下文里找，`foo` 在那里找不到，同样不能把 `<` 当作模板实参列表的开头。例子三的区别是外层恰好有一个同名的 `::X`，C++20 的特殊规则借它判定了 `<` 的含义，新规则不再这样做。
</details>
