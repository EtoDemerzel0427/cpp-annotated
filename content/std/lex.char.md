!!! tldr
    - 源码里的每个字符都是翻译字符集的元素，而翻译字符集就是全部 Unicode 标量值。阶段 1 之后，编译器看到的只有 Unicode。
    - 字面量在运行时是什么数值，由字面量编码决定：`u8`、`u`、`U` 固定是 UTF-8、UTF-16、UTF-32；无前缀和 `L` 由实现定义。
    - 标准对实现定义的编码只保证几件事：基本字符各占一个非负的编码单元、空字符是 0、数字 `0`–`9` 连续。`'A' == 65` 不在其中。
    - 通用字符名有 `\u03B1`、`\U000003B1`、`\u{3B1}`、`\N{GREEK SMALL LETTER ALPHA}` 四种写法；在字面量之外不能用它写 ASCII 字符或控制字符。
    - 代理码位不是标量值，所以 `\uD83D\uDE00` 这种按 UTF-16 拆开写的 emoji 是非良构的。

## 源码里的字符和运行时的字节

```cpp run title="two-sides.cpp" ok
const char*     a = "é";     // 运行时的字节由普通字面量编码决定
const char8_t*  b = u8"é";   // 一定是 UTF-8：0xC3 0xA9
const char32_t* c = U"é";    // 一定是 UTF-32：0xE9
static_assert(sizeof(u8"é") == 3 && sizeof(U"é") == 2 * sizeof(char32_t));
int main() {}
```

同一个 `é` 在三个字面量里变成了三组不同的数值。这里有两个独立的问题：编译器怎样理解源码里的这个字符，以及字面量在程序里存成什么数值。[[lex.char]] 用两套概念把它们分开：源码一侧是翻译字符集，运行时一侧是字面量编码。

这一节在 C++23 被整体重写（[[P2314R4]]）。此前的标准有基本源字符集、执行字符集、扩展源字符集等一组互相纠缠的概念，源码里的非 ASCII 字符还要在阶段 1 先换成通用字符名再处理，这些现在都不存在了。

## 翻译字符集（[[lex.charset]] ¶1）

¶1 [[g:translation-character-set|翻译字符集]]（translation character set）的元素是：

- ¶1.1 Unicode 中每个分配了码位的抽象字符；
- ¶1.2 每个还没有分配给字符的 Unicode 标量值，各对应一个字符。

注 1 复习了 Unicode 的术语。**码位**（code point）是 0 到 0x10FFFF 的整数；**代理码位**（surrogate code point）是 0xD800 到 0xDFFF，UTF-16 用它们成对表示大于 0xFFFF 的字符；**标量值**（scalar value）是代理码位以外的码位。

所以翻译字符集和 Unicode 标量值一一对应。¶1.2 让还没分配字符的码位也能写出来，Unicode 新增字符时 C++ 的规则不必修改。代理码位不在其中，它们只是 UTF-16 的编码手段，不是字符。

阶段 1（[[lex.phases]]）把 UTF-8 源文件解码成标量值，再映射到翻译字符集；其他编码的文件以实现定义的方式映射。从此之后，源码就是一串 Unicode 字符。

## 基本字符集（¶2）

¶2 [[g:basic-character-set|基本字符集]]（basic character set）是翻译字符集中的 99 个字符：

- 4 个控制字符：水平制表 U+0009、垂直制表 U+000B、换页 U+000C、换行 U+000A；
- 空格 U+0020；
- 52 个字母 `A`–`Z`、`a`–`z`，10 个数字 `0`–`9`；
- 32 个标点：`!` `"` `#` `$` `%` `&` `'` `(` `)` `*` `+` `,` `-` `.` `/` `:` `;` `<` `=` `>` `?` `@` `[` `\` `]` `^` `_` `` ` `` `{` `|` `}` `~`。

也就是 ASCII 的 95 个可打印字符，加上 4 个空白控制字符。注 2 说，表中的 Unicode 名字只用来标明是哪个字符，码位的数值在这里没有别的含义。标准并不要求 `'A'` 的值是 65。

{{c++26}} `$`、`@`、`` ` `` 是 C++26 加入的（[[P2558R2]]），C++23 的基本字符集只有 96 个字符。目前没有任何语法用到这三个字符，加入它们的影响在别处：在字面量之外不能再用通用字符名写它们（见下文 ¶1）；每种字面量编码都必须把它们编码成单个编码单元（¶5）。

## 基本字面量字符集（¶3）

¶3 [[g:basic-literal-character-set|基本字面量字符集]]（basic literal character set）是基本字符集再加 4 个控制字符：空字符 U+0000、响铃 U+0007、退格 U+0008、回车 U+000D。

字面量里可以用转义序列 `\0`、`\a`、`\b`、`\r` 写出这 4 个字符，所以每种编码都必须能表示它们。它们不在基本字符集里，是因为它们不该出现在源码的字面量以外（回车在阶段 1 就被统一成了换行）。

## 编码单元与字面量编码（¶4）

¶4 **编码单元**（[[g:code-unit|code unit]]）是字符类型（[[basic.fundamental]]）的一个整数值。字符字面量和字符串字面量中的字符，按编码前缀（[[lex.ccon]]、[[lex.string]]）所决定的方式编码成一个或多个编码单元，这种方式叫做该字面量的[[g:literal-encoding|字面量编码]]（literal encoding）。多字符字面量 `'ab'` 和无法编码的字符字面量不在此列。

| 前缀 | 字面量编码 | 编码单元的类型 |
|---|---|---|
| 无 | 普通字面量编码（ordinary literal encoding） | `char` |
| `L` | 宽字面量编码（wide literal encoding） | `wchar_t` |
| `u8` | UTF-8 | `char8_t` |
| `u` | UTF-16 | `char16_t` |
| `U` | UTF-32 | `char32_t` |

字面量编码在编译时起作用：它决定编译器把 `"é"` 写进目标文件时用哪些字节。程序运行时处理文本所用的编码是另一回事，它和 locale 相关，叫做执行字符集的编码（[[character.seq]]），两者不必相同。GCC 的 `-fexec-charset=` 和 MSVC 的 `/execution-charset:` 改变的是普通字面量编码，不是程序运行时的 locale。

## 编码必须满足什么（¶5）

¶5 字面量编码，以及执行字符集的 locale 相关编码，都必须满足：

1. 基本字面量字符集的每个字符编码成单个编码单元，值非负，且彼此不同；
2. 空字符编码成 0，其他任何字符的编码单元都不是 0；
3. 数字 `0`–`9` 的值依次加 1。

除此之外，普通字面量编码和宽字面量编码由实现定义。注 3 补充，基本字面量字符集以外的字符可以编码成多个编码单元，而且其中某个编码单元的值可以和某个基本字符相同。Shift-JIS 就是这样：一些汉字的第二个字节是 0x5C，与 `\` 相同。

```cpp run title="digits.cpp" ok
constexpr int digit_value(char c) { return c - '0'; }   // 可移植：数字一定连续
static_assert(digit_value('7') == 7);
// 'z' - 'a' == 25 没有保证：EBCDIC 里字母不连续
int main() {}
```

由此可以推出：

- `c - '0'` 可移植，`c - 'a'` 不可移植。EBCDIC 中 `i` 和 `j` 之间有空位。
- 普通字符串字面量的编码结果里不会冒出意外的 0 字节，所以 `strlen` 对任何不含 `\0` 转义的普通字符串字面量都能正常工作。
- 即使 `char` 是有符号的，基本字符的值也非负，`'A'` 一定为正。`'é'` 如果能用一个 `char` 表示（例如在 Latin-1 编码下），值可能为负。

¶5 最后一句要求，UTF-8、UTF-16、UTF-32 字面量必须按 Unicode 标准相应的编码形式编码每个字符。所以 `u8`、`u`、`U` 字面量的内容是可移植的，无前缀和 `L` 的字面量不是。

!!! impl "实现视角"
    | 编译器 | 普通字面量编码（默认） | 宽字面量编码 | `wchar_t` |
    |---|---|---|---|
    | GCC、Clang（Linux、macOS） | UTF-8 | UTF-32 | 32 位 |
    | MSVC | 当前代码页（`/utf-8` 时为 UTF-8） | UTF-16 | 16 位 |

    MSVC 的宽字面量编码是 UTF-16，`L'😀'` 需要两个编码单元，放不进一个 `wchar_t`，按 [[lex.ccon#3]] 是非良构的。

## 通用字符名（[[lex.universal.char]]）

**通用字符名**（[[g:universal-character-name|universal-character-name]]，UCN）用纯 ASCII 写出任意一个字符。它有四种写法：

| 写法 | 例 | 引入 |
|---|---|---|
| `\u` 加 4 位十六进制数 | `\u03B1` | C++98 |
| `\U` 加 8 位十六进制数 | `\U0001F600` | C++98 |
| `\u{` 任意位数 `}` | `\u{1F600}`、`\u{3b1}` | C++23（[[P2290R3]]） |
| `\N{` 字符名 `}` | `\N{GREEK SMALL LETTER ALPHA}` | C++23（[[P2071R2]]） |

`\u{...}` 叫做分隔形式，位数不固定，免去了 `\u` 必须正好 4 位、`\U` 必须正好 8 位的麻烦。`\N{...}` 让人用可读的名字写字符。

```cpp run title="ucn.cpp" ok
int \u03B1 = 1;                        // 标识符 α
int \U000003B2 = 2;                    // 标识符 β
int \u{3B3} = 3;                       // 标识符 γ（C++23）
int \N{GREEK SMALL LETTER DELTA} = 4;  // 标识符 δ（C++23）
static_assert(u8"\u{1F600}"[0] == 0xF0);                       // 😀 的 UTF-8 首字节
static_assert(sizeof(u"\U0001F600") == 3 * sizeof(char16_t));  // 代理对 + 结尾的 0
int main() { return α + β + γ + δ - 10; }  // UCN 与直接写字符完全等价
```

阶段 3（[[lex.phases]]）在切分记号时识别通用字符名，并把它换成所指的字符，所以 `int \u03B1;` 和 `int α;` 声明的是同一个标识符。字符字面量、字符串字面量、原始字符串、头文件名的内部除外：字面量里的通用字符名要等到字面量求值时才按编码处理（[[lex.ccon#3]]、[[lex.string#10]]）。

### 字面量外不能写基本字符（¶1）

```cpp title="ucn-basic.cpp" error
int \u0041 = 1;             // error: U+0041 'A' 是基本字符
int \u0024x = 2;            // error: '$' 自 C++26 起是基本字符
int \u0009t = 3;            // error: 控制字符
const char* p = "\u0041";   // OK：字面量里可以
```

¶1 如果一个通用字符名出现在字符字面量或字符串字面量（包括用户定义字面量）的字符序列之外，而它指的是控制字符或基本字符集中的字符，程序非良构。

这条规则排除了一类没有意义的问题：如果允许在字面量外用 `\u0041` 表示 `A`，那么 `\u0023define` 算不算预处理指令，`i\u006Et x;` 里的 `i\u006Et` 算不算关键字 `int`？直接禁止最简单。基本字符集正是 C++ 语法用到的全部字符，其他字符在语法上没有特殊含义，用通用字符名写它们不会改变记号的切分，所以不必禁止；它们能不能出现在标识符里，交给 [[lex.name]] 判断。

注 1 说，原始字符串里形似通用字符名的字符序列不是通用字符名：`R"(\u0041)"` 的内容是 6 个字符。

### 数值必须是标量值（¶2）

¶2 `\u`、`\U`、`\u{}` 三种形式指代标量值等于其中十六进制数的那个字符。如果这个数不是 Unicode 标量值，也就是代理码位或大于 0x10FFFF，程序非良构。

```cpp title="ucn-range.cpp" error
char32_t a = U'\uD800';                 // error: 代理码位不是标量值
char32_t b = U'\U00110000';             // error: 超出 0x10FFFF
const char16_t* e = u"\uD83D\uDE00";    // error: 不能用两个代理码位拼出 😀
const char16_t* f = u"\U0001F600";      // OK：编译器自己编码出代理对
```

Java 和 JavaScript 允许把 😀 写成 `\uD83D\uDE00`，因为它们的 `\u` 指的是一个 UTF-16 编码单元。C++ 的通用字符名指的是一个字符，所以只能写 `\U0001F600` 或 `\u{1F600}`，代理对由编译器在编码 `u"..."` 时产生。确实需要一个孤立的代理编码单元时，可以用数值转义 `u"\xD800"`，它直接给出编码单元的值，而不是字符（[[lex.string#10]]）。

### 名字必须完全匹配（¶3）

¶3 `\N{...}` 指代 Unicode 标准中名字或某个别名与花括号里的内容相等的那个字符；找不到就非良构。注 2 说，别名列在 Unicode 字符数据库的 NameAliases.txt 里，所有名字和别名都没有首尾空格。

这里的相等是逐字符相等：不忽略大小写，也不忽略多余的空格或连字符。Unicode 自己为名字查找推荐的宽松匹配规则（UAX44-LM2）不适用。

```cpp run title="named.cpp" ok
static_assert(U'\N{LATIN CAPITAL LETTER A}' == U'A');
static_assert(U'\N{LINE FEED}' == U'\n');  // U+000A 没有正式名字，LINE FEED 是别名
static_assert(U'\N{LF}' == U'\n');         // 缩写别名也可以
// U'\N{latin capital letter a}'           // error: 大小写不匹配
// U'\N{LATIN CAPITAL LETTER  A}'          // error: 多了一个空格
int main() {}
```

控制字符在 Unicode 里没有正式名字，只有别名，所以 `\N{LINE FEED}` 能用，靠的是别名也算这一条。编译器要支持 `\N{...}`，就得在自身里带一张完整的 Unicode 名字表。Clang 对拼错的名字报告 is not a valid Unicode character name，并在可能时提示相近的名字。

## 历史与演进

!!! history
    - C++98 引入 `\u` 和 `\U`。当时的模型是阶段 1 把源码里所有非基本字符都换成通用字符名再处理，这与实际编译器的做法完全不符。字面量里的通用字符名也不能指代基本字符。
    - C++11 允许字面量里的通用字符名指代基本字符和控制字符，字面量外仍然禁止；新增 `u8`、`u`、`U` 前缀。
    - C++23 重写字符集模型，引入翻译字符集和字面量编码（[[P2314R4]]）；新增 `\N{}`（[[P2071R2]]）和 `\u{}`、`\x{}`、`\o{}`（[[P2290R3]]，后两种见 [[lex.ccon]]）；要求支持 UTF-8 源文件（[[P2295R6]]）。
    - C++26 把 `$`、`@`、`` ` `` 加入基本字符集（[[P2558R2]]）；行拼接拼出通用字符名从 UB 变为合法（[[P2621R2]]）。

## 常见误解

!!! pitfall "字面量编码就是源文件的编码"
    源文件用 GBK 保存、普通字面量编码却是 UTF-8，这完全可能：阶段 1 把 GBK 解码成 Unicode，编码字面量时再编码成 UTF-8。乱码通常出在反方向：源文件是 UTF-8，MSVC 却按 GBK 代码页读入。问题在阶段 1 的解码，不在字面量编码。

!!! pitfall "`'A' == 65` 是标准保证的"
    标准只保证数字连续、空字符为 0。在 EBCDIC 实现（例如 z/OS 上的 IBM 编译器）上，`'A'` 的值是 0xC1。只有 `u8'A'`、`u'A'`、`U'A'` 一定是 0x41。

!!! pitfall "用通用字符名绕过关键字"
    在字面量外写 `\u0069f` 想得到一个与 `if` 不同的标识符，结果是程序直接非良构。

## 思考题

!!! question "思考题"
    下面每一行各自放在命名空间作用域，是否良构？

    ```cpp
    int \u00C0 = 1;            // (a)
    int \u0040x = 2;           // (b)
    const char* s = "\u0040";  // (c)
    int \u{1F600} = 3;         // (d)
    auto r = R"(\u004)";       // (e)
    ```

<details markdown="1">
<summary>答案</summary>

- (a) 良构：U+00C0 `À` 不是基本字符，具有 XID_Start 属性，可以作为标识符的首字符，而且本身就是 NFC 形式（见 [[lex.name]]）。
- (b) 非良构：`@` 自 C++26 起是基本字符，字面量外的通用字符名不能指代它（¶1）。
- (c) 良构：字面量里的通用字符名可以指代基本字符。
- (d) 非良构：😀 没有 XID_Start 属性，不能出现在标识符中（[[lex.name]]）。
- (e) 良构：原始字符串里没有通用字符名，`\u004` 只是 5 个普通字符，不会因为位数不够而报错。
</details>
