!!! tldr
    - 翻译分 8 个阶段。实现只需表现得如同依次执行了这些阶段，实际可以合并；阶段规定的是谁先谁后、后一步看到什么。
    - 行拼接（阶段 2）先于识别注释（阶段 3），所以 `//` 注释末尾的反斜杠会吞掉下一行。
    - 注释在阶段 3 变成一个空格，宏在阶段 4 展开，所以宏既造不出注释，也看不到注释。
    - 字符串拼接（阶段 5）在宏展开之后，关键字到阶段 6 才出现，所以 `"a" MACRO "b"` 能拼接、`#if new` 的值是 0。
    - 模板实例化和常量求值属于阶段 7；C++26 的反射还让常量求值的副作用影响后续分析。

## 一个反斜杠引出的问题

```cpp run title="comment-splice.cpp" ok
int main() {
  int x = 1; // 这一行以反斜杠结尾 \
  x = 2;
  return x;   // 返回 1：x = 2; 成了注释的一部分
}
```

程序返回 1。行末的反斜杠把下一行接了上来，接起来之后，`x = 2;` 落在 `//` 注释里。本机 Clang 23 给出 `-Wcomment` 警告（multi-line // comment）。

原因在于标准规定的翻译顺序：先把物理行拼成逻辑行，再识别注释。[[lex.phases]] 用 8 个阶段描述了从源文件到程序映像的全过程。

¶1 这些阶段规定的是翻译的各条语法规则之间的优先次序。脚注 7 说明，实现只需表现得如同这些阶段依次发生，实际上可以把几个阶段合在一起做。例如 Clang 的词法分析器在一趟扫描里同时完成解码、行拼接和切分记号。所以下文说的先后是语义上的先后：前一个阶段的结果决定后一个阶段看到什么。

| 阶段 | 输入 → 输出 | 做什么 | 典型后果 |
|---|---|---|---|
| 1 | 字节 → 字符 | 解码（必须支持 UTF-8）；CR LF、CR 变成换行 | 换行风格不影响程序 |
| 2 | 字符 → 逻辑源行 | 删除 BOM；删除反斜杠加换行 | `//` 注释末尾的 `\` 吞掉下一行 |
| 3 | 字符 → 预处理记号和空白 | 切分记号；注释变成一个空格 | 宏造不出注释；最长匹配 |
| 4 | 预处理记号 → 预处理记号 | 执行指令、展开宏；`#include` 的文件递归走阶段 1–4 | 注释不能跨文件 |
| 5 | 预处理记号 → 预处理记号 | 拼接相邻的字符串字面量 | `"a" MACRO "b"` 能拼接 |
| 6 | 预处理记号 → 记号 | 转换成关键字、标识符、字面量等 | 关键字从这里才有 |
| 7 | 记号 → 翻译后的 TU | 语法和语义分析、实例化、常量求值 | 实例化失败即非良构 |
| 8 | 多个 TU → 程序映像 | 解析外部引用、链接库 | 链接 |

## 阶段 1：读入源文件（¶1.1）

¶1.1 实现必须支持由 UTF-8 编码单元组成的输入文件（UTF-8 文件），也可以支持实现定义的其他种类的文件。如果支持其他种类，就必须提供一种与文件内容无关的方式，把一个文件指定为 UTF-8 文件。注 1 点明：只靠识别字节序标记（BOM，U+FEFF）不够。换句话说，编译器要有命令行选项之类的开关，而不能只靠猜。

这条要求来自 C++23 的 [[P2295R6]]。此前从源文件到字符的映射完全由实现定义，同一份含中文注释的源码，MSVC 在没有 BOM 时按系统代码页解释，就可能读成乱码。

UTF-8 文件必须是良构的 UTF-8 序列，否则程序非良构。解码得到的每个 Unicode 标量值映射到[[g:translation-character-set|翻译字符集]]（[[lex.charset]]）的一个元素；其他种类的文件以实现定义的方式映射。

同一步还统一换行：CR LF 和单独的 CR 都换成一个换行字符，所以 Windows（CRLF）和老式 Mac（CR）风格的文件行为相同。这一点在原始字符串里能直接看到：

```cpp run title="crlf.cpp" ok
#include <cstring>
// 无论此文件以 LF 还是 CRLF 保存，s 里的换行都只是一个 '\n'
const char* s = R"(line1
line2)";
int main() { return std::strlen(s) == 11 ? 0 : 1; }
```

!!! impl "实现视角"
    GCC 默认把源文件当作 UTF-8，可以用 `-finput-charset=` 指定其他编码。Clang 只接受 UTF-8（可以带 BOM）。MSVC 在没有 BOM 时按当前代码页解释，`/source-charset:utf-8` 或 `/utf-8` 就是 ¶1.1 要求的那种与内容无关的开关。

### 三字符组

C++14 及以前，阶段 1 还要把 9 个三字符组（trigraph）替换成单个字符，例如 `??=` 换成 `#`、`??/` 换成 `\`。三字符组几乎只会意外出现：

```cpp run title="trigraph.cpp" std=c++14 flags="-std=c++14" impl
#include <cstdio>
int main() {
  // 会打印吗????/
  std::puts("yes");
}
```

C++14 中 `??/` 就是反斜杠，阶段 2 把下一行接进注释，`puts` 消失了。本机 Clang 23 用 `-std=c++14` 编译，什么也不打印，`-Wall` 下报告 multi-line // comment；用 `-std=c++17` 编译则打印 `yes`。

C++17 删除了三字符组（[[N4086]]）。[[diff.cpp14.lex]] 说明，实现仍可以把它作为实现定义的输入映射的一部分保留，但不能在原始字符串里替换。

## 阶段 2：行拼接（¶1.2）

¶1.2 先删除文件开头的 BOM（如果有）。然后，每个由反斜杠、若干个换行以外的空白字符、一个换行组成的序列都被删除，物理源行由此拼成[[g:logical-source-line|逻辑源行]]。每个物理行上只有最后一个反斜杠可以参与拼接。

反斜杠和换行之间允许有空白，是 C++23 的改动（[[P2223R2]]）。此前 GCC 容忍尾随空白，Clang 和 MSVC 不容忍，同一份代码在不同编译器上意义不同。尾随空白肉眼看不见，标准选择了让它不影响结果的 GCC 行为。

```cpp run title="splice.cpp" ok
#include <cstring>
int main() {
  const char* q = "a\   
b";   // 上一行反斜杠后有 3 个空格：C++23 起照样拼接，q 是 "ab"
  return std::strcmp(q, "ab");
}
```

本机 Clang 23 按标准拼接，同时给出 `-Wbackslash-newline-escape` 警告。

拼接在阶段 3 识别注释之前进行，开头的例子就是这样出错的。在注释里画 ASCII 图、或者注释以 Windows 路径 `C:\dir\` 结尾时尤其容易遇到。

注 2 说，行拼接可以拼出一个通用字符名（[[lex.universal.char]]，形如 `\u0041` 的写法）：

```cpp run title="ucn-splice.cpp" ok
const char32_t* s = U"\u00\
41";                 // 拼接后为 U"\u0041"，即 U"A"
int main() { return s[0] == U'A' ? 0 : 1; }
```

C++23 及以前这种情况是 UB，C++26 的 [[P2621R2]] 把它改成了合法。

非空的源文件如果拼接后不以换行结尾，就按末尾追加了一个换行处理。C++03 中这种情况是 UB。现在的规则保证，被 `#include` 的文件即使最后一行没有换行，也不会和包含它的文件的下一行粘在一起。

阶段 2 有一处例外：在原始字符串字面量的两个引号之间，阶段 2 做的拼接要撤销（[[lex.pptoken#5]]）。所以原始字符串里写的反斜杠加换行会原样保留。

## 阶段 3：切分预处理记号（¶1.3）

¶1.3 源文件被分解成[[g:preprocessing-token|预处理记号]]（[[lex.pptoken]]）和空白（包括注释）：

- 源文件不能以不完整的预处理记号或不完整的注释结尾。脚注 9 举的例子是缺少闭合 `"` 或 `>` 的头文件名，以及没有闭合的 `/*`。
- 每个注释替换成一个空格（U+0020），换行保留。
- 换行以外的连续空白是保留还是换成一个空格，未指定。这只影响 `-E` 输出的外观；字符串化（`#`）本身会规范空白，所以写不出依赖它的可移植程序。
- 形成预处理记号的过程中，通用字符名会被识别，并替换成它所指的字符。字符字面量、字符串字面量、原始字符串、头文件名内部除外。
- 怎样切分取决于上下文。例如在 `#include` 之后，`<` 可以开始一个头文件名（[[lex.header]]）。

字面量内部的通用字符名不在这里替换，是因为它要等到字面量求值时，按字面量的编码规则处理（[[lex.string#10]]）。原始字符串里的 `\u0041` 根本不是通用字符名，只是 6 个普通字符。头文件名里不替换，则避免误读 `#include "C:\users\..."` 这样含 `\u` 的路径。

### 宏造不出注释

注释在阶段 3 已经变成空格，到阶段 4 展开宏时，宏既看不到注释，也造不出注释：

```cpp title="no-comment-macro.cpp" error
#define CAT(a, b) a##b
CAT(/, /) this is not a comment   // error: 拼出的 // 不是预处理记号
```

`##` 的结果必须是一个合法的预处理记号，而 `//` 不是任何预处理记号，只是注释的开头。当前草案规定这种情况非良构（[[cpp.concat]]），C++23 及以前是 UB。本机 Clang 23 报错 pasting formed '//', an invalid preprocessing token。

同理，`a/**/b` 是两个记号 `a` 和 `b`。

## 阶段 4：预处理（¶1.4）

¶1.4 源文件作为一个 *preprocessing-file*（[[cpp.pre]]）分析：执行预处理指令，展开宏（[[cpp.replace]]），执行 `_Pragma` 运算符（[[cpp.pragma.op]]）。`#include` 指令让被包含的文件从阶段 1 到阶段 4 递归处理一遍。最后删除所有预处理指令；此后，分隔预处理记号的空白不再有意义。

由此可以推出几点。

每个被包含的文件各自经过阶段 1–3。每个文件有自己的编码判定和 BOM；一个文件里没闭合的注释也不能在另一个文件里闭合（见思考题 3）。

阶段 4 还没有关键字。[[lex.name]] 的注 4 说，阶段 4 的标识符包括那些到阶段 7 才被区分为关键字的记号。所以在 `#if` 里，除 `true`、`false` 外的标识符和关键字都替换成 0（[[cpp.cond]]）：

```cpp run title="if-keyword.cpp" ok
#if new == 0 && true && !false   // new 在这里只是标识符，值为 0
int ok = 1;
#endif
int main() { return ok - 1; }
```

阶段 4 内部空白仍然有意义。`#define F(x) ...` 定义函数式宏，`#define F (x) ...` 定义对象式宏（[[cpp.replace]]）。阶段 4 结束后，`a  +  b` 和 `a+b` 就没有区别了。

## 阶段 5：字符串拼接（¶1.5）

¶1.5 两个或更多相邻的字符串字面量预处理记号，先按 [[lex.string]] 确定一个共同的编码前缀，然后拼接成一个。

拼接在宏展开之后，所以宏产生的字符串可以参与拼接：

```cpp run title="concat.cpp" ok
#define GREETING "Hello, "
const char* s = GREETING "world";             // "Hello, world"
static_assert(sizeof(GREETING "world") == 13);
int main() {}
```

反过来，`#include` 在阶段 4 就处理完了，那时还没有拼接，所以 `#include "dir/" "file.h"` 不会变成 `"dir/file.h"`（[[cpp.include]] 的注 2）。

拼接的细节，例如 `"\xA" "B"` 不会合成 `"\xAB"`、前缀冲突怎样处理、用户定义字面量的后缀怎样处理，见 [[lex.string#7]]、[[lex.string#8]] 和 [[lex.ext#8]]。

## 阶段 6：转换成记号（¶1.6）

¶1.6 每个预处理记号转换成一个记号（[[lex.token]]）。这一步做了几件之前没有做的事：

- 区分关键字和标识符（[[lex.key]]）；
- 把预处理数字（pp-number）变成整数字面量或浮点字面量。两者都不是的（例如 `0xe+foo`、`1..2`），程序非良构（[[lex.pptoken#3]]）；
- 字面量从此有了类型和值。在此之前，预处理数字没有类型和值（[[lex.ppnumber#2]]）；
- 无法转换成记号的单个字符，例如源码里残留的 `` ` `` 或 `$`，使程序非良构。

## 阶段 7：分析、翻译与实例化（¶1.7）

¶1.7 记号构成一个**翻译单元**（translation unit），作为 *translation-unit*（[[basic.link]]）做语法和语义分析并翻译。这一阶段除了语法分析，还包括下面几件事。

注 3 提醒，分析时偶尔会把一个记号换成一串其他记号。最常见的是 [[temp.names]] 的规则：模板实参列表里第一个不在括号内的 `>>` 当作两个 `>`。这不是词法上的例外，词法上 `>>` 仍是一个记号（[[lex.pptoken#5]]），拆开是语法分析做的。

当前 TU 依赖的模块单元和头文件单元（[[module.unit]]、[[module.import]]），其源码是否必须可用，由实现定义。注 4 说，TU 之间通过有外部链接或模块链接的名字、以及数据文件交流。

分析的同时完成所需的实例化，包括显式实例化（[[temp.explicit]]）。实例化在什么上下文中进行，由实例化点决定（[[temp.point]]）。注 6 举例：一个 constexpr 函数模板特化的实例化点可能在 TU 末尾，但在某些常量表达式里使用它，要求更早实例化（[[temp.inst]]）。任何一次实例化失败，程序都是非良构的。

### 常量求值的副作用 {{c++26}}

分析过程中，每个显式常量求值（manifestly constant-evaluated）的表达式都会被求值（[[expr.const.defns]]）。它们的值会影响程序里用到的类型和反射值，从而影响语法分析本身。

C++26 的静态反射（[[P2996R13]]）让常量求值可以有副作用。例如 `std::meta::define_aggregate` 在 `consteval` 块中求值时，会补全一个类的定义。于是标准必须说明：分析程序中某一点 P 时，哪些副作用已经发生。

¶1.7 的回答是：表达式 E 作为完全表达式求值的副作用，在 P 处算作已完成，当且仅当

- ¶1.7.1 E 是某个 `consteval` 块声明（[[dcl.pre]]）对应的表达式，并且
- ¶1.7.2 这个 `consteval` 块（或它实例化自的模板定义）从 P 可达（[[module.reach]]）；或者 P 处于某些类的完整类上下文中，而这个块从其中最外层类的类定义之后的那一点可达。

第二个分支针对完整类上下文（[[class.mem.general]]）：成员函数体虽然写在类中间，却当作在类定义结束之后分析。下面是标准的例 2。本机 Clang 23 还不支持反射，这段代码按标准分析，没有经过编译验证。

```cpp
#include <meta>
class S {
  class Incomplete;
  class Inner {
    void fn() {
      /* p1 */ Incomplete i;   // OK：p1 在 S 的完整类上下文中
    }
  } /* p2 */ ;
  consteval {
    std::meta::define_aggregate(^^Incomplete, {});
  }
} /* p3 */ ;
```

在 p1 处 `Incomplete` 已经是完整类型：`define_aggregate` 的调用在 `consteval` 块中，p1 处于 `S` 的完整类上下文中，而这个块从 p3（`S` 的定义之后）可达。如果在 p2 处声明 `Incomplete i;`，p2 不在完整类上下文中，就不行。

## 阶段 8：链接（¶1.8）

¶1.8 翻译后的各个 TU 合在一起，所有对外部实体的引用得到解析（[[basic.link]]）；链接库组件，以满足对当前翻译中没有定义的实体的引用。所有输出收集成一个**程序映像**，其中包含在执行环境中运行所需的信息。

标准没有提到目标文件、静态库、动态库，这些都是实现细节（[[lex.separate]] 的注 2）。标准的模型里也没有动态链接：程序映像在执行之前就是完整的。

## 阶段先后的推论

| 现象 | 原因 |
|---|---|
| 宏造不出注释 | 注释在阶段 3 去掉，宏在阶段 4 展开 |
| `//` 注释末尾的 `\` 吞掉下一行 | 拼接（阶段 2）先于识别注释（阶段 3） |
| 原始字符串里的反斜杠加换行保留 | 原始字符串内撤销阶段 2 的拼接 |
| `#include "a" "b"` 不拼接 | `#include` 在阶段 4 处理，拼接在阶段 5 |
| `"x" MACRO "y"` 能拼接 | 宏展开（阶段 4）先于拼接（阶段 5） |
| `#if new` 的值是 0 | 关键字在阶段 6 才出现 |
| `#define R "x"` 之后 `R"y"` 不是 `"x" "y"` | 阶段 3 先切出原始字符串，见 [[lex.pptoken#6]] |
| `0xe+foo` 编译失败 | 阶段 3 切出一个预处理数字，阶段 6 转换失败 |
| `vector<vector<int>>` 可以写 | 阶段 7 的语法规则把 `>>` 拆成两个 `>` |

!!! history "从 9 个阶段到 8 个"
    C++20 有 9 个阶段：阶段 5 把字面量中的字符映射到执行字符集，6 拼接字符串，7 转换成记号并分析，8 实例化，9 链接。C++23 的字符集重构（[[P2314R4]]）把编码移进字面量自身的语义（[[lex.charset]]、[[lex.string]]），阶段 5 改成确定共同的编码前缀，但仍是 9 个阶段。C++23 之后的修改把确定前缀和拼接合并为阶段 5，转换成记号单独作为阶段 6，实例化并入阶段 7，成了现在的 8 个阶段。很多资料仍按旧编号写，例如“阶段 6 是字符串拼接”，阅读时要注意版本。

## 常见误解

!!! pitfall "编译器真的分 8 遍处理"
    阶段是概念模型。注释变成空格这一步，在实际编译器里只是跳过注释、记下这里有空白。阶段模型用来推导结果，不描述编译器内部的流程；诊断的位置、`-E` 输出的格式也不受它约束。

!!! pitfall "`#if 0` 里的内容不做词法分析"
    被跳过的部分仍然要切分预处理记号。按 [[lex.pptoken#1]]，`#if 0` 块里一个落单的 `'` 同样使程序非良构。本机 Clang 23 对被跳过部分里的这类字符不给诊断，但不能依赖这一点。在 `#if 0` 里写 `don't` 这样的英文说明，应该改用注释。

## 思考题

!!! question "思考题 1"
    下面的程序返回什么？

    ```cpp
    #define STR(x) #x
    #define XSTR(x) STR(x)
    int main() {
      const char* s = XSTR(a/**/b);
      return s[1] == ' ';
    }
    ```

<details markdown="1">
<summary>答案</summary>

!!! question "思考题 2"
    为什么 C++26 需要在阶段 7 专门规定常量求值的副作用何时完成，而 C++20 的 `constexpr`、`consteval` 不需要？

<details markdown="1">
<summary>答案</summary>

C++20 的常量求值只算出一个值，最多引起模板实例化，而实例化的上下文已经由实例化点的规则管理。C++26 的反射元函数（例如 `define_aggregate`）可以修改程序本身，比如补全一个类的定义。于是程序某一点上某个类是否完整，取决于哪些 `consteval` 块已经求值。标准必须给出一个与编译器内部顺序无关的答案，所以用可达性和完整类上下文来规定。
</details>

!!! question "思考题 3"
    a.h 的内容是 `/* begin`（没有换行），b.h 的内容是 `end */`。main.cpp 依次 `#include "a.h"` 和 `#include "b.h"`。程序是否良构？

<details markdown="1">
<summary>答案</summary>

非良构。`#include` 让 a.h 单独经过阶段 1–4，而阶段 3 要求源文件不能以不完整的注释结尾（¶1.3），a.h 以没闭合的 `/*` 结尾。注释不能跨文件。
</details>
