!!! tldr
    - 宏替换完成后，结果会连同源文件后面的记号一起再扫描一遍，所以替换结果的末尾可以和后面的 `(...)` 拼成一次新的宏调用。
    - 再扫描时遇到正在被替换的宏的名字，这个名字不展开，而且以后永远不会再展开，即使它被当作实参传给别的宏。这就是宏不能递归的原因。
    - 函数式宏的名字后面紧跟的记号不是 `(` 时，它只是错过了这次调用，没有被永久禁用。延迟展开技巧就利用了这一点。
    - 宏展开的结果即使看起来像 `#define`，也不会被当作预处理指令；但其中的 `_Pragma` 会被执行。

## 展开结果要再扫描一遍（¶1）

```cpp
#define LP (
#define F1(x) [x]
#define CALL(m) m(5)
F1 LP 1)        // 结果：F1 ( 1)，F1 没有展开
CALL(F1)        // 结果：[5]
```

第一行里，预处理器扫描到 `F1` 时，下一个记号是 `LP` 而不是 `(`，所以这不是一次调用，`F1` 被原样留下。随后 `LP` 展开为 `(`，但扫描已经越过了 `F1`，不会回头。

第二行里，`CALL(F1)` 先替换成 `F1(5)`。这个结果还要再扫描一遍，这时 `F1` 后面紧跟 `(`，于是它作为调用展开成 `[5]`。

¶1 规定了这一步。替换列表里的形参全部代入、`#` 和 `##` 都处理完之后，先删除所有[[g:placemarker|占位记号]]（placemarker，`##` 遇到空实参时临时插入的记号，见 [[cpp.concat]]）。然后把得到的记号序列，**连同源文件中之后的所有记号**，再扫描一遍，寻找可以继续替换的宏名。这一步叫**重新扫描**（rescanning）。

连同之后的记号这一点意味着，替换结果可以从源文件借记号：

```cpp
#define h g(~
#define g f
#define f(a) [a]
h 5)            // h → g(~ → f(~，再借上源文件里的 5) → f(~ 5) → [~ 5]
```

`h` 的替换结果 `g(~` 里的括号没有闭合，闭合的 `)` 在源文件后面。重新扫描把两者连起来，构成一次完整的 `f` 调用。

## 宏不会展开自己（¶3）

如果再扫描时又遇到同一个宏，一直展开下去就会无限循环。¶3 用三句话阻止了这一点。

¶3 第一句：扫描宏 M 的替换列表时，如果遇到 M 自己的名字，不替换它。括号里的限定很重要：只限于替换列表本身，源文件后面再出现的 M 照常展开。

```cpp
#define foo foo bar
foo         // → foo bar          替换列表里的 foo 不展开
foo foo     // → foo bar foo bar  第二个 foo 来自源文件，照常展开
```

第二句：在嵌套的替换中遇到 M 的名字，同样不替换。嵌套的替换指的是 M 的替换结果里又展开了别的宏。

```cpp
#define AA BB
#define BB AA
AA          // AA → BB → AA：展开 BB 时 AA 仍在被替换，不再展开。结果：AA
BB          // 同理，结果：BB
```

第三句：这些没有被替换的宏名记号，以后再也不能被替换，即使它们之后出现在本来会被替换的位置上。

```cpp
#define id(x) x
#define ff(x) x
#define gg ff(gg)
gg          // gg → ff(gg)，实参里的 gg 是在替换 gg 的过程中遇到的，不展开。结果：gg
id(gg)      // id 的实参先完全展开，得到一个不再展开的 gg；
            // 代入 id 之后再扫描，gg 已经不在被替换之列，但它仍然不展开。结果：gg
```

如果没有第三句，`id(gg)` 中的 `gg` 代入 `id` 之后就不再处于被替换之中，会再次展开为 `ff(gg)`。只要多套几层 `id(...)`，就能绕过前两句的保护。

所以不能展开是记号自身的性质，跟着记号走，经过实参传递也不会消失。社区里把这样的记号称为**涂蓝**（painted blue）的记号；标准正文没有这个词，只说 nonreplaced macro name preprocessing tokens。

## 标准的大例子（¶2）

¶2 是标准中最长的宏例子，上面每条规则在这里都能找到对应。定义如下：

```cpp
#define x       3
#define f(a)    f(x * (a))
#undef  x
#define x       2
#define g       f
#define z       z[0]
#define h       g(~
#define m(a)    a(w)
#define w       0,1
#define t(a)    a
#define p()     int
#define q(x)    x
#define r(x,y)  x ## y
#define str(x)  # x
```

先看前四行。定义 `f` 时 `x` 是 3，之后 `x` 被重新定义为 2。替换列表保存的是记号，定义时不展开，`x` 在使用时才替换，所以下面所有的 `x` 都是 2。

### 第一行

```cpp
f(y+1) + f(f(z)) % t(t(g)(0) + t)(1);
// → f(2 * (y+1)) + f(2 * (f(2 * (z[0])))) % f(2 * (0)) + t(1);
```

`f(y+1)` 代入后得 `f(x * (y+1))`。再扫描时，`f` 是正在被替换的宏，虽然后面跟着 `(` 也不展开；`x` 展开为 `2`。结果是 `f(2 * (y+1))`。

`f(f(z))` 的实参 `f(z)` 要先完全展开（[[cpp.subst#1]]）。`z` 展开为 `z[0]`，其中的 `z` 是涂蓝的；内层 `f` 得到 `f(2 * (z[0]))`，其中的 `f` 也是涂蓝的。外层代入再扫描，外层 `f` 涂蓝，内层 `f` 本来就是蓝的，结果是 `f(2 * (f(2 * (z[0]))))`。

`t(t(g)(0) + t)(1)` 先展开外层 `t` 的实参 `t(g)(0) + t`：

1. `t(g)` 的实参 `g` 展开为 `f`。这里 `f` 后面没有 `(`，只是没有调用，没有涂蓝。代入后得 `f`。
2. 再扫描 `f`，连同实参内后面的 `(0) + t`：`f(0)` 构成调用，得 `f(2 * (0))`。
3. 实参里的 `t` 后面没有 `(`，原样保留。实参展开的结果是 `f(2 * (0)) + t`。

外层 `t` 的替换列表就是 `a`，代入后得 `f(2 * (0)) + t`。再扫描时连同源文件后面的 `(1);`，但其中的 `t` 是在替换 `t` 的替换列表里遇到的，涂蓝，`(1)` 不构成调用。结果是 `f(2 * (0)) + t(1)`。

### 第二行

```cpp
g(x+(3,4)-w) | h 5) & m
    (f)^m(m);
// → f(2 * (2+(3,4)-0,1)) | f(2 * (~ 5)) & f(2 * (0,1))^m(0,1);
```

`g` 是对象式宏，展开为 `f`，再扫描时和源文件后面的 `(x+(3,4)-w)` 构成 `f` 的调用。实参只有一个：`(3,4)` 里的逗号在括号内，`w` 展开出的逗号要到实参划分完之后才出现，不会把实参拆成两个。

`h 5)` 就是上一节借记号的例子，得到 `f(2 * (~ 5))`。

`m` 和 `(f)` 之间隔着换行。在宏调用中换行只是普通空白（[[cpp.replace.general#13]]），所以这是调用 `m(f)`。代入 `a(w)` 得 `f(w)`；这时正在被替换的是 `m` 而不是 `f`，所以 `f(w)` 正常展开，结果是 `f(2 * (0,1))`。

`m(m)` 代入后得 `m(w)`。这个 `m` 是在替换 `m` 的过程中遇到的，涂蓝；`w` 展开为 `0,1`，结果是 `m(0,1)`。同一个替换列表 `a(w)`，换一个实参，结果就完全不同。

### 第三、四行

```cpp
p() i[q()] = { q(1), r(2,3), r(4,), r(,5), r(,) };
char c[2][6] = { str(hello), str() };
// → int i[] = { 1, 23, 4, 5, };
//   char c[2][6] = { "hello", "" };
```

`p()` 是零个形参的宏，展开为 `int`。`q()` 有一个空实参，展开为空，所以 `i[q()]` 变成 `i[]`。`r(4,)` 中 `4` 与占位记号拼接得 `4`，`r(,)` 拼接后只剩占位记号，删除后什么都不剩。`str()` 把空实参字符串化为 `""`。

本机 Clang 23 `-E` 对整个例子的输出与标准逐个记号一致，只有空白不同。

## 结果不会变成指令（¶4）

```cpp
#define DEFINE_X # define X 1
DEFINE_X        // → # define X 1，作为普通记号进入第 7 阶段，导致语法错误

#define WARN_OFF _Pragma("GCC diagnostic ignored \"-Wunused\"")
WARN_OFF        // OK：宏展开结果中的 _Pragma 会被执行
```

¶4 完全替换之后得到的记号序列，即使形状像一条预处理指令，也不会被当作指令处理。但其中所有的 `_Pragma` 运算符表达式都会按 [[cpp.pragma.op]] 处理。

这就是 `_Pragma` 存在的理由：宏可以生成 `_Pragma(...)`，不能生成 `#pragma`。[[cpp.pre]] 还有一条互补的规则：宏展开前不是指令的行，展开后也不会变成指令。

## 错过调用不等于涂蓝：延迟展开

开头的例子里，`F1` 后面跟的是 `LP`，`F1` 只是错过了调用，并没有被涂蓝。后面再有一轮扫描时，它仍然可以展开。宏元编程库正是利用这一点模拟递归：

```cpp run title="defer.cpp" ok
#define EMPTY()
#define DEFER(m) m EMPTY()
#define EXPAND(...) __VA_ARGS__
#define A() 123

// DEFER(A)()         → A ()   本轮扫描中 A 后面是 EMPTY，不是 (
// EXPAND(DEFER(A)()) → 123    多一轮扫描，A 和 ( 相遇
static_assert(EXPAND(DEFER(A)()) == 123);
int main() {}
```

`DEFER(A)` 代入后得 `A EMPTY()`。再扫描时 `A` 的下一个记号是 `EMPTY`，所以 `A` 被跳过；随后 `EMPTY()` 展开为空，留下 `A ()`。扫描不会回头，这一轮里 `A` 就留在那里了。

`EXPAND` 的作用是多给一轮扫描：它的实参先完全展开成 `A ()`，代入后再扫描，`A` 和 `(` 相遇，调用成功。把 `EXPAND` 嵌套几层，例如 `#define EVAL(...) EVAL1(EVAL1(EVAL1(__VA_ARGS__)))`，就能得到成百上千轮扫描。一个宏在本轮延迟引用自己，到下一轮时它已不在被替换之列，而那个被延迟的名字从未被涂蓝，于是可以继续展开。Boost.Preprocessor 等库的循环和递归都建立在这个技巧上。

这些技巧完全符合标准，但难读也难调试。大多数场合应改用模板、`constexpr` 函数、折叠表达式或反射。宏仍然适合的主要是生成声明（X-macro）、把标识符变成字符串、条件编译。

## 实现视角：隐藏集

!!! impl "Prosser 的隐藏集算法"
    标准用正在被替换、嵌套替换来描述规则，不便直接实现。C89 标准化期间，Dave Prosser 给出了一个参考算法：每个记号携带一个**隐藏集**（hide set），即对这个记号而言不能展开的宏名集合。

    - 对象式宏 `T` 展开时，结果中每个记号的隐藏集是：宏名记号 `T` 的隐藏集 ∪ {T}。
    - 函数式宏 `T(...)` 展开时，结果中每个记号的隐藏集是：(宏名记号 `T` 的隐藏集 ∩ 闭合 `)` 的隐藏集) ∪ {T}。
    - 扫描到一个宏名时，只要它不在该记号自己的隐藏集里，就展开。

    一个宏名在某记号的隐藏集里，就相当于这个记号被涂蓝了。GCC 和 Clang 用记号上的一个禁止展开标志，加上当前正在展开的宏的记录，实现同样的语义。

函数式宏那条规则里的交集，处理的是调用一半来自替换结果、一半来自源文件的情形。只有闭合括号也处在同一次展开里时，隐藏关系才会延续。下面这个例子来自 C 标准：

```cpp
#define f(a) a*g
#define g(a) f(a)
f(2)(9)
```

1. `f(2)` 展开为 `2*g`，其中 `g` 的隐藏集是 {f}。
2. `g` 和源文件中的 `(9)` 构成调用 `g(9)`。`g` 的隐藏集是 {f}，闭合 `)` 来自源文件，隐藏集为空，交集为空，再并上 {g}，得到 `f(9)`，各记号的隐藏集是 {g}。
3. `f` 不在 {g} 里，继续展开为 `9*g`。最终结果是 `2*9*g`。

但按标准的文字，`g(9)` 的展开算不算 `f` 的嵌套替换？如果算，`f(9)` 里的 `f` 应当涂蓝，结果就是 `2*f(9)`。C 标准在这个例子里明说两种结果都可能，属于未指定行为。C++ 标准没有类似的说明。本机 Clang 23 得到 `2*9*g`，与 Prosser 算法一致，GCC 也是如此。

## 常见误解

!!! pitfall "宏可以递归"
    ```cpp
    #define LIST(x, ...) x __VA_OPT__(, LIST(__VA_ARGS__))
    LIST(1, 2, 3)   // → 1 , LIST(2, 3)：内层 LIST 被涂蓝，不再展开
    ```
    处理个数不定的元素时，把 `__VA_ARGS__` 直接交给函数模板或折叠表达式；确实需要在预处理期循环时，才使用上面的延迟展开技巧。

!!! pitfall "宏名后面的括号可以来自另一个宏"
    定义 `#define LP (` 之后，`F LP x)` 不会调用函数式宏 `F`，因为扫描到 `F` 时下一个记号是 `LP`。需要再多一轮扫描才行：`EXPAND(F LP x))`。

## 思考题

!!! question "思考题 1"
    ```cpp
    #define a a b
    #define b a
    a
    ```
    展开结果是什么？说明每个 `a`、`b` 为什么展开或不展开。

<details markdown="1">
<summary>答案</summary>

结果是 `a a`，本机 Clang 23 `-E` 可以验证。

1. `a` 展开为 `a b`。替换列表里的 `a` 是在替换 `a` 时遇到的，按 ¶3 第一句不展开，涂蓝。
2. 继续扫描遇到 `b`，它不是正在被替换的宏，展开为 `a`。这是嵌套在 `a` 的替换之中的替换，按 ¶3 第二句，其中遇到的 `a` 不展开，涂蓝。
3. 结果是两个蓝色的 `a`。
</details>

!!! question "思考题 2"
    为什么 `m(f)` 展开为 `f(2 * (0,1))`，而 `m(m)` 展开为 `m(0,1)`？用隐藏集算法重新解释一遍。

<details markdown="1">
<summary>答案</summary>

`m(a)` 的替换列表是 `a(w)`，源文件里的 `m` 和 `)` 隐藏集都为空，所以替换结果中每个记号的隐藏集都是 {m}。

- `m(f)`：结果是 `f ( w )`。`f` 的隐藏集 {m} 不含 `f`，而且后面跟着 `(`，所以 `f(w)` 展开。
- `m(m)`：实参 `m` 单独展开时后面没有 `(`，原样保留。代入后的 `m ( w )` 中，`m` 的隐藏集 {m} 含有它自己，不展开；`w` 不在 {m} 中，展开为 `0,1`。

注意第二种情况里，`m` 在实参展开阶段并没有被涂蓝，只是后面没有 `(`。它是在代入之后、再扫描 `m` 的替换列表时才被涂蓝的。
</details>
