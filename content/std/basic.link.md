!!! tldr
    - 名字的链接决定了别处的同名声明能否指到同一个实体：外部链接跨翻译单元，模块链接只在同一模块内，内部链接只在本翻译单元内，无链接只在本作用域内。
    - 命名空间作用域的 `const` 变量默认是内部链接，除非它是 `extern`、`inline`、模板，或者写在模块接口里。`const int*` 不算 `const` 变量。
    - 两个声明是否声明同一实体，看它们是否对应、目标作用域是否相同，跨翻译单元时还要求链接为外部或模块并且附属于同一模块。名字查找能否找到对方无关紧要。
    - 同一实体的所有声明必须类型一致。跨翻译单元的不一致不要求诊断，链接器也常常发现不了。
    - 模块接口里对外可见的声明不能暴露 TU-local 实体，例如在导出的 inline 函数里调用 `static` 函数。普通头文件里这样写已被弃用。

## 两个翻译单元里的 `f` 是同一个东西吗（¶1–¶2）

¶1 一个**程序**由一个或多个翻译单元组成，它们分别翻译，然后链接在一起。**翻译单元**（translation unit，TU）大致就是一个源文件连同它 `#include` 进来的全部内容（[[lex.phases]]）。C++20 起，一个翻译单元也可以是模块单元，以 `export module M;` 或 `module M;` 开头（[[module.unit]]）。

```cpp title="a.cpp"
int counter = 0;              // 外部链接
static int hits = 0;          // 内部链接
namespace { int misses = 0; } // 内部链接
void bump() { ++counter; ++hits; ++misses; }
```

```cpp title="b.cpp"
extern int counter;           // 与 a.cpp 的 counter 是同一个变量
static int hits = 0;          // 与 a.cpp 的 hits 无关，各有一份
namespace { int misses = 0; } // 同上
void bump();
int main() { bump(); return counter - 1 + hits + misses; }   // 返回 0
```

两个文件都写了 `counter`、`hits`、`misses`，结果却不同。`counter` 是同一个变量，另外两个是两对互不相干的变量。决定这一点的是名字的**链接**（linkage）。

¶2 一个名字具有以下四种链接之一：

| 链接 | 别处的同名声明能否指到同一实体 | 典型例子 |
|---|---|---|
| 外部链接（external linkage） | 任何翻译单元都可以，包括其他模块 | 普通的全局函数和全局变量、导出的模块实体 |
| 模块链接（module linkage）{{c++20}} | 只有同一模块的翻译单元可以 | 具名模块里未导出的命名空间作用域实体 |
| 内部链接（internal linkage） | 只有本翻译单元可以 | `static` 函数和变量、命名空间作用域的 `const` 变量、无名命名空间的成员 |
| 无链接（no linkage） | 只有同一作用域里的声明可以 | 局部变量、局部类、函数形参 |

注 1 给出两个推论：内部链接实体的所有声明都在同一个翻译单元里；模块链接实体的所有声明都附属于同一个模块。

标准说的是名字具有链接。平时说某个变量或函数的链接，指的是声明它的那个名字的链接。无名的类型（无名类、lambda 的闭包类型）没有名字，也就谈不上链接，除非借助 typedef 获得一个用于链接的名字（见下文 ¶4.3）。

链接与存储期是两回事。函数里的 `static int n;` 有静态存储期，但它没有链接：

| | 静态存储期 | 自动存储期 |
|---|---|---|
| 外部链接 | 全局变量 | — |
| 内部链接 | `static` 全局变量、`const` 全局变量 | — |
| 无链接 | 函数内的 `static` 变量 | 普通局部变量 |

## 哪些名字有内部链接（¶3）

¶3 属于命名空间作用域的实体，在下面三种情况下名字具有内部链接：

- ¶3.1 变量、变量模板、函数或函数模板显式声明为 `static`；
- ¶3.2 非模板变量的类型是 const 限定、但不是 volatile 的类型，除非下面四条之一成立：
    - ¶3.2.1 它声明在模块接口单元（私有模块片段之外）或模块分区的管辖范围内；
    - ¶3.2.2 它显式声明为 `extern`；
    - ¶3.2.3 它是 `inline` 的；
    - ¶3.2.4 它之前已经声明过，而且之前的声明不是内部链接；
- ¶3.3 匿名联合体的数据成员。

```cpp run ok
const int c1 = 1;                 // 内部链接（¶3.2）
extern const int c2 = 2;          // 外部链接（¶3.2.2）
inline const int c3 = 3;          // 外部链接（¶3.2.3）
const volatile int c4 = 4;        // 外部链接：volatile，¶3.2 不适用
constexpr int c5 = 5;             // 内部链接：constexpr 隐含 const
const int* p1 = &c1;              // 外部链接：p1 本身不是 const
const int* const p2 = &c1;        // 内部链接：p2 本身是 const
extern const int z;
const int z = 5;                  // 外部链接（¶3.2.4）
static int s = 1;                 // 内部链接（¶3.1）
extern int s;                     // 重声明，仍是内部链接
int main() { return c1+c2+c3+c4+c5+*p1+*p2+z+s - 23; }
```

用 `nm` 查看本机 Clang 23 生成的可执行文件，`c2`、`c4`、`z`、`p1` 是全局符号，`c1`、`s` 是局部符号（`c5`、`p2` 被优化掉了）。

最容易看错的是 `p1`。`const int*` 里的 `const` 修饰所指向的 `int`，`p1` 本身的类型不是 const 限定的，所以它有外部链接，放进头文件就会在每个包含它的翻译单元里重复定义。

### 为什么 `const` 变量默认是内部链接

C 里 `const int x = 1;` 有外部链接，C++ 改成了内部链接，目的是让 `const` 常量能够取代宏，直接写在头文件里：

```cpp title="limits.h"
const int kMaxUsers = 1000;   // 每个包含它的翻译单元各有一个独立的 kMaxUsers
```

如果它有外部链接，每个包含这个头文件的翻译单元都会定义同一个变量，违反单一定义规则（ODR，[[basic.def.odr]]）。内部链接让每个翻译单元各有一份，互不相干。`kMaxUsers` 可以用于常量表达式，只读取它的值通常不占用存储。

几条例外各有原因：

- `extern` 是程序员明确要求外部链接，`extern const int x = 1;` 是定义外部链接常量的标准写法。
- `inline` 变量（C++17）本来就是可以在多个翻译单元里定义的同一个变量，必须有外部链接才有意义。
- 之前声明过的情形，如 `extern const int z;` 之后的 `const int z = 5;`，后者是前者的定义，链接沿用第一次声明。
- 模块接口只编译一次，不存在被多次包含的问题。如果其中的 `const` 变量仍是内部链接，它就不能导出，接口里用到它的 inline 函数也会构成暴露（见下文 ¶14）。
- 变量模板不受 ¶3.2 影响，因为它的特化必须在各翻译单元之间是同一个实体。注 2 补充，变量模板的 const 实例化可以有外部链接或模块链接。

## 其他命名空间成员的链接（¶4）

¶4 无名命名空间，以及直接或间接嵌套在无名命名空间里的命名空间，具有内部链接；其余命名空间都具有外部链接。

属于命名空间作用域、¶3 没有给它内部链接的变量、函数、类、枚举和模板（¶4.1–¶4.6），按下面的顺序确定链接：

- ¶4.7 如果是首次在友元声明中声明、并且就在那里定义的函数或函数模板，而外围类定义在 `export` 声明里，它的链接与外围类相同；
- ¶4.8 否则，如果是在友元声明中声明的函数或函数模板，而某个对应的非友元声明可达，链接由那个声明决定；
- ¶4.9 否则，如果外围命名空间是内部链接，名字是内部链接；
- ¶4.10 否则，如果声明附属于具名模块并且没有导出，名字是模块链接；
- ¶4.11 否则，名字是外部链接。

¶4.9 就是无名命名空间的工作原理。无名命名空间本身是内部链接，于是其中的变量、函数、类、模板都是内部链接。它比 `static` 更通用，因为 `static` 不能用于类型。

```cpp run ok
namespace { int u = 0; struct Hidden { int z; }; }    // 都是内部链接（¶4.9）
namespace outer { namespace { namespace deep { int dv = 0; } } }
// deep 间接嵌套在无名命名空间里，所以 dv 也是内部链接
int main() { Hidden h{}; return u + outer::deep::dv + h.z; }
```

¶4.10 是模块带来的变化。具名模块里没有 `export` 的函数、变量、类，过去在头文件里会是外部链接，现在是模块链接：同一模块的其他单元可以使用它们，导入这个模块的代码不能。

¶4.3–¶4.5 里的无名类和无名枚举，靠的是**用于链接的 typedef 名**（typedef name for linkage purposes，[[dcl.typedef]]）。C 风格的 `typedef struct { ... } Point;` 定义了一个无名类，typedef 给了它一个可以跨翻译单元认定的名字，于是它能像具名类一样写在头文件里。C++20 起这种无名类必须与 C 兼容，不能有成员函数、基类、默认成员初始化器等：

```cpp
typedef struct { int a; } P;                 // OK：P 是用于链接的 typedef 名
typedef struct { int b; void f() {} } Q;     // 非良构：有成员函数
enum { red, green } e;                       // 无名枚举以第一个枚举项 red 作为用于链接的名字（¶4.5）
```

本机 Clang 23 对 `Q` 只给出 `-Wnon-c-typedef-for-linkage` 警告，诊断之后照常编译，这符合标准对非良构程序只要求诊断的规定。

¶4.7–¶4.8 处理类内定义的友元函数（隐藏友元）：类被导出时，这样的友元随类获得外部链接；类没有导出时，在具名模块里它是模块链接。

## 类成员与块作用域的名字（¶5–¶7）

¶5 成员函数、静态数据成员、类作用域里的具名类和枚举（以及在类作用域里借 typedef 获得链接名的无名类和枚举），链接与所属的类相同。所以外部链接类的成员是外部链接，无名命名空间里的类的成员是内部链接。

¶7 其余规则没有覆盖的名字都没有链接。除非另有说明，在块作用域里声明的名字没有链接。局部变量、函数形参、局部类（以及按 ¶5，局部类的成员）、typedef 名、模板形参、枚举项都没有链接。

块作用域里的 `extern` 声明是另有说明的情形。¶6 的例 1：

```cpp run ok
static void f();
extern "C" void h();
static int i = 0;               // #1
void q() {
  extern void f();              // 内部链接：重声明上面的 static f
  extern void g();              // ::g，外部链接
  extern void h();              // C 语言链接
  int i;                        // #2：无链接，隐藏了 #1
  {
    extern void f();            // 内部链接
    extern int i;               // #3：内部链接，与 #1 是同一个变量
  }
}
int main() { }
```

难点在 #3。在 #3 的位置做名字查找，只能找到 #2 这个局部变量，#1 已经被隐藏了。但块作用域 `extern` 声明的**目标作用域**（target scope，名字实际所属的作用域）是外围的命名空间（[[basic.scope.scope#2]]），所以 #3 与 #1 名字相同、种类相同，目标作用域也相同。按下文 ¶8，它们声明的是同一个实体，#3 因此是内部链接。是否同一实体只看对应关系和目标作用域，不看名字查找的结果。

本机 Clang 23 按这个规则处理：在 #3 处给 `i` 赋值，修改的正是 #1。

!!! history "这条规则的旧版本"
    C++20 及以前，块作用域 `extern` 声明的链接取决于名字查找能否看到一个有链接的同名声明，看不到就是外部链接。按旧规则，#3 看不到被隐藏的 #1，于是得到外部链接，又与 #1 的内部链接冲突，程序非良构；当时的标准例子正是这样标注的。[[P1787R6]] 改用对应关系和目标作用域来判定同一实体，这个例子随之改为内部链接。

## 两个声明何时声明同一实体（¶8–¶10）

¶8 两个声明声明的是**同一实体**，需要满足：

- 它们**对应**（[[g:correspond]]），大致是名字相同、种类相同，对函数来说形参列表等也相同（[[basic.scope.scope#4]]）；
- 目标作用域相同，而且不是函数形参作用域或模板形参作用域；
- 都不是名字无关声明（例如 C++26 的 `_`）；

并且下面三条之一成立：

- ¶8.1 它们在同一个翻译单元里；
- ¶8.2 它们都声明类型别名或命名空间别名，并且别名的底层实体相同；
- ¶8.3 它们都声明外部链接或模块链接的名字，并且附属于同一个模块。

判断时，把 `typedef struct {...} P;` 这类无名类型的声明视为引入了它用于链接的名字。注 3 提醒，还有一些情形也会声明同一实体，例如不同命名空间里的 `extern "C"` 函数（[[dcl.link]]）。

由此可以读出几条结论：

- 在同一个翻译单元里，只要对应并且目标作用域相同，就是同一实体，与链接无关。`static int s; extern int s;` 是同一个 `s`。
- 跨翻译单元时，必须是外部或模块链接，并且附属于同一模块。内部链接的名字永远到不了别的翻译单元，开头例子里两个 `hits` 因此互不相干。
- `void f(int x); void f(int x);` 里的两个 `x` 不是同一实体，因为函数形参作用域被排除在外。

### 附属于不同模块的冲突（¶10）

声明**附属**（attached）于某个模块：具名模块的管辖范围里的声明一般附属于该模块，其余声明附属于全局模块（[[module.unit]]）。按 ¶8.3，附属于不同模块的两个声明即使完全相同，也是两个不同的实体。

¶10 的注 5 指出，如果两个声明对应但附属于不同模块，并且一个先于另一个出现，程序非良构（[[basic.scope.scope#6]]）。例 2，判定已用本机 Clang 23 验证：

```cpp title="decls.h"
int f();            // #1，附属于全局模块
int g();            // #2，附属于全局模块
```

```cpp title="M.cppm（模块 M 的接口）"
module;
#include "decls.h"
export module M;
export using ::f;   // OK：不声明新实体，导出 #1
int g();            // error: 与 #2 对应，但附属于 M
export int h();     // #3
export int k();     // #4
```

```cpp title="other.cpp"
import M;
static int h();     // error: 与 #3 冲突
int k();            // error: 与 #4 冲突
```

`int g();` 一行体现了模块的强所有权。写在 `export module M;` 之后的声明附属于 M，与全局模块里的 `int g();` 是两个实体，而它们又对应，于是冲突。想在模块里重新导出全局模块的函数，要像 `f` 那样用 using 声明。

所以一个实体的所有声明都附属于同一个模块，称这个实体**附属于**该模块。

!!! impl "模块链接在符号层面的样子"
    Clang 采用强所有权模型，附属于具名模块的实体，修饰名里编码了模块名：

    ```cpp
    export module M;
    const int k = 1;            // 模块接口里不再默认内部链接（¶3.2.1），是模块链接
    int hidden() { return 2; }  // 模块链接
    export int api() { return hidden() + k; }   // 外部链接
    ```

    本机 `nm` 显示的符号是 `__ZW1M1k`、`__ZW1M6hiddenv`、`__ZW1M3apiv`。导出的 `api` 也带 `W1M` 标记，所以两个模块里的同名实体在链接器层面也不会冲突。

### 头单元里的内部链接声明（¶9）

¶9 如果一个声明内部链接名字的声明 H 先于另一个翻译单元 U 里的声明 D，而 H 假如出现在 U 里就会与 D 声明同一实体，程序非良构。注 4 说明，这样的 H 只能出现在**头单元**（header unit）里。

`import "util.h";` 导入的头单元是一个独立的翻译单元，但它的声明先于导入者的代码。如果头单元里有 `static int helper();`，导入者又写了 `int helper();`，用 `#include` 时这是链接冲突的错误；改用 `import` 后二者本来分属两个翻译单元，可以相安无事。¶9 把这种情况也判为非良构，让 `#include` 和 `import` 的结果保持一致。

## 同一实体的声明必须一致（¶11）

¶11 对实体 E 的任意两个声明：

| ¶ | 一个声明把 E 声明为 | 另一个必须 |
|---|---|---|
| 11.1 | 变量或函数 | 声明为相同类型的变量或函数 |
| 11.2 | 枚举项 | 也是枚举项 |
| 11.3 | 命名空间 | 也是命名空间 |
| 11.4 | 类型 | 同一种类的类型（`class` 和 `struct` 可以互换，`union`、`enum` 不行，[[dcl.type.elab]]） |
| 11.5 | 类模板 | 种类相同，模板头等价（注 6：默认模板实参可以不同） |
| 11.6 | 函数模板、变量模板或其偏特化 | 模板头和类型都等价 |
| 11.7 | 别名模板 | 模板头和被别名的类型等价 |
| 11.8 | 概念 | 也是概念 |

比较类型之前先做完所有调整，类型别名替换成它代表的类型。数组对象的声明可以在有没有最外层边界上不同，例如 `extern int a[]; int a[10];`。

在同一个翻译单元里，违反这条规则一定会被诊断。例 3：

```cpp error
int f(int x, int x);    // error: 两个 x 是不同实体（形参作用域被 ¶8 排除），二者冲突
void g();               // #1
void g(int);            // OK：与 #1 不对应，是重载
int g();                // error: 与 #1 对应，是同一实体，但类型不同
void h();               // #2
namespace h {}          // error: 与 #2 是同一实体，但不是函数
```

跨翻译单元时情况不同。如果两个声明彼此都不可达，不要求诊断（{{ifndr}}）：

```cpp title="a.cpp"
int config = 42;
```

```cpp title="b.cpp" ifndr
extern double config;            // 同一实体，类型不同
double read() { return config; } // 把 int 的字节当 double 读
```

链接器发现不了这个错误。Itanium C++ ABI（Linux、macOS 上的 GCC 和 Clang）的修饰名不编码变量的类型，也不编码普通函数的返回类型。形参类型不同的 `void f(int)` 和 `void f(double)` 会得到不同的符号，结果是链接失败；`int g();` 和 `long g();` 却会链接成功，然后在运行时出错。让每个实体只在一个头文件里声明，就能避免这类问题。

¶12 是一个注：要与非 C++ 代码链接，用链接说明 `extern "C"`（[[dcl.link]]）。这里的**语言链接**（language linkage）决定调用约定和名字修饰方式，与本页讲的链接是两个独立的维度。

## 模块接口不能暴露 TU-local 实体（¶13–¶19）{{c++20}}

### 问题从哪里来

头文件里的 inline 函数调用一个 `static` 函数，在只有 `#include` 的时代勉强能工作，因为每个翻译单元都有自己的一份 `static` 函数（严格说这已经违反 ODR，见 [[basic.def.odr]]）。

模块接口只编译一次，导入者看到的是接口里 inline 函数的定义。如果这个函数调用了接口里的 `static` 函数，导入者的翻译单元里根本没有那个函数，既无法内联，也无法链接。

C++20 的解决办法（[[P1815R2]]）是定义只属于一个翻译单元的 **TU-local 实体**，并禁止模块接口里对外可见的声明暴露它们。

### 命名一个实体（¶13）

¶13 下面几种情况下，说声明 D **命名**（names）了实体 E：

- ¶13.1 D 里有一个闭包类型为 E 的 lambda 表达式；
- ¶13.2 D 里有一个表示 E 的反射表达式 `^^E`，或者指称 E 的拼接说明符 {{c++26}}；
- ¶13.3 D 是一个注入声明，用到了类型为 E 的数据成员描述 {{c++26}}；
- ¶13.4 E 不是函数或函数模板，D 里有指代 E 的名字（id-expression、类型说明符、嵌套名说明符、模板名或概念名）；
- ¶13.5 E 是函数或函数模板，D 里有命名 E 的表达式（[[basic.def.odr#4]]），或者指代一个包含 E 的重载集的名字。

¶13.5 的后半句意味着，只要一个内部链接的重载出现在重载集里，即使重载决议最后没有选中它，声明也命名了它。注 8 补充，实例化后的声明里，非依赖名字不指代重载集（[[temp.res]]）。

### TU-local 实体与 TU-local 值（¶15–¶16）

¶15 下面这些实体是 [[g:tu-local|TU-local]] 的：

- ¶15.1 名字是内部链接的类型、类型别名、命名空间、命名空间别名、函数、变量或模板，以及在这样一个实体的定义里声明的、名字没有链接的同类实体（包括其中 lambda 引入的闭包类型）；
- ¶15.2 定义在类定义、函数体和初始化器之外的无名类型，或者只用来声明 TU-local 实体的无名类型，例如 `static auto x = []{};` 的闭包类型；
- ¶15.3 TU-local 模板的特化；
- ¶15.4 有 TU-local 模板实参的模板特化；
- ¶15.5 其声明（可能是实例化出来的）构成暴露的模板特化。

注 10：特化可以由隐式实例化或显式实例化产生。

¶16 值和对象也有 TU-local 之分，因为导入者会直接使用 constexpr 变量的值（常量折叠、模板实参）。下面这些值或对象是 TU-local 的：

- ¶16.1 类型是 TU-local 的；
- ¶16.2 本身是 TU-local 函数或 TU-local 变量的对象，或者是指向它们的指针；
- ¶16.3 类或数组对象，其某个子对象、或其引用成员所引用的对象或函数是 TU-local 的，并且可用于常量表达式；
- ¶16.4 表示 TU-local 实体、值或对象的反射值，以及与 TU-local 类型有关的几类反射值 {{c++26}}。

一个指向 `static` 函数的 constexpr 函数指针，值就是那个函数的地址，导入者无法使用。¶16.4 把同样的推理推广到反射：`f` 是 `static` 函数时，`constexpr auto r = ^^f;` 的值表示一个 TU-local 实体。

### 暴露（¶14）

¶14 一个声明如果命名了 TU-local 实体，它就是一个**暴露**（[[g:exposure|exposure]]），但下面这些部分不计入：

- ¶14.1 非 inline 函数或函数模板的函数体。但如果函数的返回类型用了占位符（`auto`），推导出的返回类型要计入；
- ¶14.2 变量或变量模板的初始化器（变量的类型要计入）；
- ¶14.3 类定义里的友元声明；
- ¶14.4 对一个用常量表达式初始化、内部链接或无链接的非 volatile const 对象或引用的引用，只要它不是 odr-use（只读取值，见 [[basic.def.odr]]）。

此外，定义一个初始化为 TU-local 值的 constexpr 变量，也是暴露。

这些例外对应的正是导入者需不需要看到的东西：

- 非 inline 函数的函数体只在本翻译单元编译，导入者只需要声明，函数体里可以随意使用 TU-local 实体。
- inline 函数的函数体导入者要用（内联、ODR 合并），不能忽略。
- 返回类型为 `auto` 的函数，导入者要知道推导出的类型。
- 只读取值的常量会被直接代入，导入者不需要实体本身。

注 9：即使 inline 函数模板的某些显式特化可以在其他翻译单元使用，模板本身仍可能是暴露。

### 违反的后果（¶17–¶18）

¶17 在模块接口单元（私有模块片段之外）或模块分区里，如果一个非 TU-local 实体的声明（包括实例化出来的声明）或推导指引是暴露，程序非良构。在其他地方，这样的声明已弃用（[[depr.local]]）。

后半句意味着，普通头文件里 inline 函数调用 `static` 函数的写法仍然合法，只是被弃用了。

¶18 如果一个翻译单元里的声明命名了另一个翻译单元（头单元除外）里声明的 TU-local 实体，程序非良构。为模板特化实例化出来的声明，视为出现在该特化的实例化点（[[temp.point]]）。

¶17 管接口不能暴露，¶18 管导入者不能使用。模板实例化是在导入者的翻译单元里用接口中的定义产生声明，需要两条一起才能覆盖。

### 例子（¶19）

下面是标准例 4 的主体（省略了与反射有关的几行），逐行加了注释。翻译单元 #1 是模块 A 的接口：

```cpp title="TU #1：export module A;"
export module A;
static void f() {}
inline void it() { f(); }           // error: inline 函数体要计入，命名了 TU-local 的 f
static inline void its() { f(); }   // OK：its 自己就是 TU-local 的
template<int> void g() { its(); }   // OK：非 inline 函数模板的函数体不计入（¶14.1）
template void g<0>();               // 显式实例化 g<0>

decltype(f) *fp;                    // error: 变量的类型要计入，decltype(f) 命名了 f
auto &fr = f;                       // OK：初始化器不计入（¶14.2）
constexpr auto &fr2 = fr;           // error: constexpr 变量的值引用 f，是 TU-local 值
constexpr static auto fp2 = fr;     // OK：fp2 是内部链接，本身就是 TU-local

struct S { void (&ref)(); } s{f};               // OK：s 不是 constexpr
constexpr extern struct W { S &s; } wrap{s};    // OK：s 不可用于常量表达式，¶16.3 不适用

static auto x = []{f();};           // OK：x 和它的闭包类型都是 TU-local
auto x2 = x;                        // error: x2 的类型是 TU-local 的闭包类型
int y = ([]{f();}(),0);             // error: 这个闭包类型不是 TU-local 的，
                                    //   而它 inline 的 operator() 命名了 f
int y2 = (x,0);                     // OK：初始化器不计入

namespace N {
  struct A {};
  void adl(A);
  static void adl(int);
}
void adl(double);

inline void h(auto x) { adl(x); }   // OK，但某些特化是暴露
```

翻译单元 #2 是模块 A 的实现单元：

```cpp title="TU #2：module A;"
module A;
void other() {
  g<0>();                           // OK：g<0> 已在 TU #1 显式实例化
  g<1>();                           // error: g<1> 在这里实例化，用到了 TU #1 的 TU-local 实体 its（¶18）
  h(N::A{});                        // error: 实例化中 adl(x) 经 ADL 得到的重载集包含 TU-local 的 N::adl(int)
  h(0);                             // OK：实参是 int，ADL 不查 N，只找到 ::adl(double)
  adl(N::A{});                      // OK：这里的查找找不到别的 TU 里的 N::adl(int)
  fr();                             // OK：通过非 TU-local 的引用 fr 调用 f
  constexpr auto ptr = fr;          // error: fr 在这里不可用于常量表达式
}
```

几组对比值得注意：

- `it` 与 `its` 调用的是同一个函数。`it` 是模块链接的 inline 函数，导入者需要它的函数体，所以构成暴露；`its` 是 `static inline`，本身就是 TU-local 的，不对外承诺任何东西。
- 通过 `fr` 间接使用 `f` 是允许的，运行时经由引用调用不需要知道 `f` 的名字。但其他翻译单元不能在常量求值中使用 `fr`，因为它的初始化器是 TU-local 值（[[expr.const]]）。
- `y` 的初始化器里的闭包类型不只用来声明 TU-local 实体，所以不是 TU-local 的；它的 `operator()` 是 inline 的并调用了 `f`，构成暴露。`y2` 只用了已有的 `x`，初始化器不计入。

标准例子里被省略的几行说明 ¶16.4：`constexpr std::meta::info r3 = ^^f;` 是暴露，因为 `r3` 的值表示 TU-local 实体 `f`。

!!! impl "Clang 的实现状况"
    本机 Clang 23 编译上面的 TU #1，只对 `it` 和 `auto x2 = x;` 给出 `-WTU-local-entity-exposure` 警告，`decltype(f) *fp;`、`fr2`、`y` 都没有诊断。标准要求这些都是非良构的，所以截至写作时 Clang 的实现并不完整。

## 实现视角

!!! impl "链接在目标文件里的样子"
    在本机 Clang 23（Mach-O）上用 `nm` 观察：

    | 声明 | 符号 | 说明 |
    |---|---|---|
    | 普通全局函数 `int use();` | `T __Z3usev` | 大写字母表示全局符号（外部链接） |
    | `static int s1 = 1;` | `d __ZL2s1` | 小写字母表示局部符号；`L` 是 Itanium ABI 的内部链接标记 |
    | 无名命名空间里的 `hidden()` | `t __ZN12_GLOBAL__N_16hiddenEv` | `_GLOBAL__N_1` 是无名命名空间的修饰 |
    | `extern const int z; const int z = 5;` | `S _z` | 外部链接，变量名不经修饰 |
    | 模块 M 里未导出的 `hidden()` | `T __ZW1M6hiddenv` | 模块链接：全局符号，修饰名里有模块名 |

    命名空间作用域里类型为无名命名空间中某个类的变量（如 `Hidden h;`），按 ¶4 是外部链接，但 Clang 把它发射为局部符号。其他翻译单元写不出它的类型，也就不可能合法地声明它，所以这个优化观察不到。

## 历史与演进

!!! history
    - C++98 有外部链接、内部链接、无链接三种。命名空间作用域里用 `static` 声明对象被弃用，推荐改用无名命名空间；当时无名命名空间的成员是外部链接，只是名字独一无二，别的翻译单元写不出来。
    - C++11 撤销了对 `static` 的弃用，无名命名空间及其成员改为内部链接，同时允许用局部类型和无名类型作模板实参。
    - C++17 引入 inline 变量，`inline const` 变量是外部链接（¶3.2.3）。
    - C++20 的模块（[[P1103R3]]）带来了模块链接和附属的概念，模块接口里的 `const` 变量不再默认内部链接；[[P1815R2]] 引入 TU-local 实体和暴露；用于链接的 typedef 名只能给与 C 兼容的无名类。
    - [[P1787R6]] 用对应关系和目标作用域重写了同一实体的判定（¶8），块作用域 `extern` 的例子因此改变了结论。
    - C++26 加入了与反射有关的命名规则（¶13.2–¶13.3）和 TU-local 反射值（¶16.4），并把名字无关声明排除在同一实体之外。

## 常见误解

!!! pitfall "`const int*` 是 const 变量"
    `const int* p = ...;` 在命名空间作用域是外部链接，放进头文件会导致重复定义。想要内部链接就写 `const int* const p`，想要全程序只有一个就写 `inline const int* p`。

!!! pitfall "函数里的 `static` 变量有内部链接"
    它没有链接。静态存储期与内部链接无关。inline 函数里的 `static` 局部变量在全程序只有一个，这是 ODR 的保证（[[basic.def.odr]]），不是链接的效果。

!!! pitfall "跨翻译单元的类型不一致会被链接器发现"
    `int x;` 与另一个翻译单元的 `extern long x;` 是同一实体但类型不同。这是 IFNDR（非良构，但不要求诊断），链接器通常不会报错。

!!! pitfall "头文件里的 inline 函数可以放心调用 `static` 函数"
    在非模块代码里这已被弃用（¶17），而且各翻译单元里的 inline 函数调用的是不同的 `static` 函数，严格说违反 ODR。把辅助函数也改成 inline，或者放进 `detail` 命名空间并声明为 inline。

## 思考题

!!! question "思考题 1"
    下面各个名字分别是什么链接？

    ```cpp
    namespace { namespace X { int a; } }
    struct S { static int b; };
    const int c = 1;
    constexpr const char* d = "hi";
    void f() { static int e; struct L { void m(); }; }
    template<class T> const T g = T();
    ```

<details markdown="1">
<summary>答案</summary>

- `X` 和 `X::a`：内部链接。`X` 嵌套在无名命名空间里（¶4），`a` 由 ¶4.9 得到内部链接。
- `S` 和 `S::b`：外部链接（¶4.3、¶5）。
- `c`：内部链接（¶3.2）。
- `d`：`constexpr` 让指针本身成为 const，类型是 `const char* const`，所以 ¶3.2 适用，是内部链接。
- `e`：无链接，它在块作用域里（¶7）。
- `L` 和 `L::m`：无链接。`L` 是局部类（¶7），成员随类（¶5）。
- `g`：¶3.2 只管非模板变量，所以按 ¶4.6、¶4.11 是外部链接。
</details>

!!! question "思考题 2"
    `static int s; void f() { int s; { extern int s; } }` 里最内层的 `extern int s;` 是新声明了一个外部链接的 `s`，还是指全局的 `s`？在 C++20 的规则下呢？

<details markdown="1">
<summary>答案</summary>

按当前规则，它指全局的 `s`。块作用域 `extern` 声明的目标作用域是外围命名空间（[[basic.scope.scope#2]]），它与 `static int s;` 对应，目标作用域相同，又在同一个翻译单元里，¶8.1 判定二者是同一实体，于是它是内部链接。中间的局部 `int s;` 只在名字查找层面隐藏了全局 `s`，不影响这个判定。这就是例 1 中的 #3。

按 C++20 及以前的规则，链接取决于查找能否看到一个有链接的声明。被隐藏的全局 `s` 看不到，于是最内层的 `s` 得到外部链接，与全局 `s` 的内部链接冲突，程序非良构。
</details>
