候选函数集确定之后（[[over.match.funcs]]），重载决议的第二步是筛选**可行函数**（viable functions），即原则上能用这组实参调用的候选。只有可行函数才会进入第三步的比较（[[over.match.best]]）。

可行性只是一个是或否的判断，不涉及好坏。把这两件事分开是标准的一个重要设计：先排除根本不能调用的，再在能调用的候选里比较。很多时候，问"为什么没选它"，答案是它根本不可行；而问"为什么选了它然后报错"，原因往往是可行性检查有意忽略了某些因素（访问性、deleted、窄化、位域……）。

## 概述（¶1）

¶1 从候选函数集中选出可行函数集，再通过比较实参转换序列与关联约束（[[temp.constr.decl]]）从中选出最佳者。选择可行函数时，考虑关联约束（如果有），以及实参与形参之间除转换序列排序以外的关系。

三道关卡依次是：

| 关卡 | 段落 | 内容 |
|---|---|---|
| 一 | 第 2 段 | 形参个数与实参个数相符（考虑省略号与默认实参） |
| 二 | 第 3 段 | 关联约束得到满足 |
| 三 | 第 4 段 | 每个实参都存在到对应形参的隐式转换序列 |

## 第一关：个数（¶2）

¶2 候选函数必须有足够的形参与实参个数相符。设实参有 `m` 个：

- ¶2.1 形参恰好 `m` 个的候选可行（就这一关而言）。
- ¶2.2 形参少于 `m` 个的候选，仅当形参列表中有省略号（[[dcl.fct]]）时可行。没有对应形参的实参都视为匹配省略号（[[over.ics.ellipsis]]）。
- ¶2.3 形参多于 `m` 个的候选 `C`，仅当下面定义的作用域集合 `G` 非空时可行。

### 省略号

```cpp run ok
#include <cstdio>
void f(int)      { std::puts("f(int)"); }
void f(int, ...) { std::puts("f(int, ...)"); }
void g(...)      { std::puts("g(...)"); }
int main() {
  f(1, 2);     // 只有 f(int, ...) 可行：实参 2 匹配省略号
  g();         // 0 个实参也能匹配纯省略号
  g(1, "a");
}
```

那么 `f(1)` 呢？两个候选都可行：`f(int)` 恰好一个形参；`f(int, ...)` 的第一个形参也对上了，省略号不需要匹配任何实参。对实参 `1`，两个候选的 ICS 都是 `int → int` 的恒等转换，无法区分；决胜规则里也没有不带省略号者优先这一条。所以这个调用有歧义：

```cpp
void f(int);
void f(int, ...);
void use() {
  f(1);      // error: 歧义
}
```

只有当某个实参真正匹配省略号时，省略号才处于劣势（省略号转换序列是最差的一种，[[over.ics.rank#2]]）。仅仅在声明里有省略号，不构成任何劣势。

### 默认实参与唯一作用域（¶2.3）

C++26 草案把默认实参的可行性规则规定得更精确了。¶2.3 定义集合 `G`：它由满足下列两个条件的每个作用域 `X` 组成：

- ¶2.3.1 重载决议考虑的 `C` 的某个声明，其宿主作用域（host scope，[[basic.scope.scope#2]]）是 `X`；
- ¶2.3.2 对每个第 `k` 个形参（`k > m`），都存在一个宿主作用域为 `X` 的可达声明为它指定了默认实参。

`G` 非空则（就个数而言）可行。若 `C` 最终被选为最佳可行函数，还有额外要求：

- ¶2.3.3 `G` 必须恰好包含一个作用域 `S`；
- ¶2.3.4 {{c++26}} 若候选由 *splice-expression* 指代，`S` 不能是块作用域；
- ¶2.3.5 调用所用的默认实参，就是宿主作用域为 `S` 的那些可达声明所指定的默认实参。

为了重载决议，形参列表在右侧截断，使之恰好 `m` 个形参。

为什么需要这么复杂？因为默认实参附着在声明上，而同一个函数可以在不同作用域有不同的声明：命名空间里一个，块作用域里又重新声明一个；或者两个命名空间里各有一个 `extern "C"` 声明（它们是同一个函数），再由 *using-declaration* 一起引入。旧规则只说后面的形参都有默认实参，没说用哪个声明的默认实参。新规则的要求是：可行性只看有没有某个作用域能凑齐全部默认实参；而真正选中时，这样的作用域必须**只有一个**，否则就无法在两套默认实参之间做出选择。

```cpp nocheck
namespace A {
  extern "C" void f(int, int = 5);
  extern "C" void f(int = 6, int);   // 同一作用域中逐步添加默认实参
}
namespace B {
  extern "C" void f(int, int = 7);   // 与 A::f 是同一个函数（extern "C"）
}

void use() {
  using A::f;
  using B::f;
  f(3, 4);     // OK：没用到默认实参
  f(3);        // error: G = {A, B}，两个作用域都能提供第二个默认实参
  f();         // OK：G = {A}，只有 A 能凑齐两个默认实参
}
```

在块作用域重新声明的传统用法仍然有效：

```cpp run ok
#include <cstdio>
void h(int x = 7) { std::printf("%d\n", x); }
void local() {
  void h(int = 8);   // 块作用域重声明，带不同的默认实参
  h();               // 打印 8：只考虑块作用域中的声明（它隐藏了外层的），G = {块作用域}
}
int main() { h(); local(); }
```

形参包的情形：

```cpp
template<typename... Ts>
int k(int = 3, Ts...);
int i = k<int>();   // error: 第二个形参（类型 int，来自包展开）没有默认实参
int j = k<>();      // OK：只有一个形参，它有默认实参
```

!!! impl "Clang 的偏离"
    截至写作时，Clang 23 在 *using-declaration* 引入两个作用域的例子上与标准相反：它接受 `f(3)`（不诊断两套默认实参），却拒绝 `f()`（报 "requires at least 1 argument"，没有把 `A` 中两个声明的默认实参合并起来看）。块作用域与形参包的例子则与标准一致。标准例子中的 *splice-expression* 部分需要反射支持，本机 Clang 尚不能编译。

在 C++23 及以前，¶2.3 只有一句："形参多于 `m` 个的候选，仅当第 `m+1` 个及以后的形参都有默认实参时可行"；多个作用域提供默认实参的情形规定在 [[dcl.fct.default]] 中，且措辞不完整。C++26 把它统一到这里，并顺带处理了 splice 的情形（`[:^^f:]()` 绕开了在哪个作用域查找这一概念，必须明确用哪套默认实参）。

## 第二关：约束（¶3）

¶3 若候选有关联约束（[[temp.constr.decl]]），约束必须得到满足（[[temp.constr.constr]]）。

对函数模板而言，约束在模板实参推导过程中就已检查（[[temp.deduct]]），不满足约束的特化根本不会成为候选。所以 ¶3 真正起作用的场合，主要是非模板函数的约束，也就是类模板的非模板成员函数上的尾随 *requires-clause*：

```cpp
#include <concepts>
template<class T>
struct Wrapper {
  void reset() requires std::default_initializable<T>;
  void set(int) requires std::integral<T>;
  void set(double);
};
struct NoDefault { NoDefault(int); };
void use(Wrapper<int>& wi, Wrapper<NoDefault>& wn, Wrapper<double>& wd) {
  wi.set(1);          // OK：两个 set 都可行，set(int) 精确匹配
  wd.set(1);          // OK：set(int) 的约束不满足 → 不可行 → set(double)
  wi.reset();         // OK
  wn.reset();         // error: 唯一候选不可行（约束不满足）
}
```

`wd.set(1)` 是约束的典型用法：同样的调用，对不同的 `T`，候选集相同但可行集不同。

为什么把约束放在可行性而不是排序里？因为约束表达的是能不能用，而不是好不好。更受约束者优先是另一条决胜规则（[[over.match.best#2.6]]），只在两个候选都可行时才用。

## 第三关：隐式转换序列（¶4）

¶4 对每个实参，必须存在一个把它转换到对应形参的隐式转换序列（[[over.best.ics]]）。若形参是引用类型，隐式转换序列包含绑定引用的操作；"非 const 左值引用不能绑定到右值""右值引用不能绑定到左值"这两条会影响可行性（[[over.ics.ref#3]]）。

```cpp
void f(int&);
void g(int&&);
void h(const int&);
void use(int i) {
  f(i);       // OK
  f(1);       // error: 唯一候选不可行——非 const 左值引用不能绑定到右值
  g(i);       // error: 唯一候选不可行——右值引用不能绑定到左值
  g(1);       // OK
  h(i);       // OK
  h(1);       // OK：const 左值引用可以绑定到右值（绑定到临时对象）
}
```

这个例子中各调用都失败在可行性阶段。如果有其他重载，不可行的候选会被悄悄排除，调用转而选择别的函数。这正是 `T&`/`const T&`/`T&&` 三种重载能够按值类别分派的基础。

### 可行性检查不看的东西

[[over.best.ics#2]] 的注 1 和 [[over.ics.ref#4]] 明确列出了 ICS 不关心的因素。它们都不影响可行性，只在候选被选中后才导致非良构：

| 因素 | 例子 | 何时出错 |
|---|---|---|
| 访问性 | 选中 `private` 成员函数 | 选定后（[[over.match#3]]） |
| 是否被删除 | 选中 `= delete` 函数 | 选定后 |
| 位域 | 非 const 左值引用形参绑定到位域实参 | 选定后（[[dcl.init.ref]]） |
| 窄化 | `f({1.5})`，`f(int)` | 选定后（[[dcl.init.list]]） |
| explicit（拷贝列表初始化） | `f({1})`，`f(X)`，`X` 的 `explicit X(int)` | 选定后（[[over.match.list]]） |
| 歧义的转换序列 | 实参到形参有两条用户定义转换路径 | 选定后（[[over.best.ics#12]]） |

```cpp
struct S { int bf : 4; };
void f(int&);
void f(long);
void use(S s) {
  f(s.bf);    // error: 选中 f(int&)（视为 int 左值，精确匹配），然后发现不能把非 const 引用绑定到位域
}
```

把位域当作普通 `int` 左值来计算 ICS，而不是在可行性阶段就排除 `f(int&)`，看起来不太友好，却与访问性的处理一脉相承：不让这些与类型无关的性质悄悄改变重载结果。

## 实现视角

!!! impl
    - 编译器的 "candidate function not viable" 诊断说明的就是三道关卡中哪一道没有通过：Clang 会细分为 "requires N arguments, but M were provided"（第一关）、"constraints not satisfied"（第二关）、"no known conversion from 'X' to 'Y' for Nth argument"（第三关）。
    - 第一关的计算代价很低，编译器总是先做它，再做代价较高的约束检查与 ICS 计算。约束检查在第三关之前（¶3 在 ¶4 之前）也有实际意义：约束可以保护后续的 ICS 计算不去实例化一些会导致硬错误的模板。
    - 默认实参的唯一作用域要求，需要编译器记录每个默认实参来自哪个声明；Clang 目前把同一函数在同一作用域中的默认实参合并到最新声明上，因而没有严格实现 ¶2.3 的跨作用域判定（见上文）。

## 历史与演进

!!! history
    - **C++98**：三条规则中的第一、三条已经存在；默认实参只要求后续形参都有默认实参。
    - **C++11**：随着右值引用的引入，右值引用不能绑定到左值成为第三关的新条件。
    - **C++20**：加入第二关（约束）。
    - **C++26**：{{c++26}} ¶2.3 引入宿主作用域集合 `G`，精确规定默认实参来自哪组声明，并处理 *splice-expression*。

## 陷阱

!!! pitfall "以为 `f(int, ...)` 天然劣于 `f(int)`"
    只有当某个实参真的匹配省略号时，省略号才带来劣势。`f(1)` 在二者之间歧义。

!!! pitfall "以为被删除、私有或会窄化的候选不可行"
    它们都是可行的，而且可能被选中，然后才报错。想在可行性阶段排除某个重载，要用约束或 SFINAE。

!!! pitfall "在不同作用域给同一函数不同的默认实参"
    合法但危险：哪套默认实参生效取决于调用点能看到哪些声明，using-declaration 混入两套时（按 C++26 规则）非良构。

## 思考题

!!! question "1. 下面的 `f(x)` 调用哪个函数？如果把 `#2` 改成 `void f(Base) = delete;` 呢？"
    ```cpp nocheck
    struct Base {};
    struct Derived : Base {};
    void f(Base&);       // #1
    void f(Derived&&);   // #2
    Derived x;
    // f(x);
    ```

<details markdown="1">
<summary>答案</summary>

`x` 是左值。#2 的右值引用不能绑定到左值，因此不可行；#1 可行（派生到基类的引用绑定），选中 #1。

改成 `void f(Base) = delete;` 后：#2 可行（拷贝初始化一个 `Base`，ICS 是派生到基类转换，Conversion 等级），#1 也可行（引用绑定，派生到基类，也是 Conversion 等级）。两者都是派生到基类、同等级；[[over.ics.rank]] 中没有规则能区分按值与按引用的同类转换，于是调用有歧义，deleted 在这里根本没有机会起作用。
</details>

!!! question "2. 为什么 [[over.match.viable]] 把约束检查（¶3）放在 ICS 检查（¶4）之前？"

<details markdown="1">
<summary>答案</summary>

就是否可行的结论而言，三道关卡都必须通过，顺序无关紧要。但顺序决定了编译器要做哪些工作。约束常用来保护某个重载：若约束不满足，计算该重载的 ICS 时可能需要实例化某些类模板（例如为了查找转换构造函数、判断派生关系），而这种实例化可能产生硬错误，或在概念的递归检查中造成循环依赖。先检查约束，可以让不满足约束的候选在触发这些实例化之前就被排除。对函数模板，C++20 之后的缺陷报告也出于同样的理由，把约束检查提前到把推导出的模板实参代入函数形参类型之前（[[temp.deduct]]）。
</details>

## 小结

!!! summary
    - 可行的条件：个数相符 ∧ 约束满足 ∧ 每个实参都有 ICS。
    - 个数：恰好相等；或更少但有省略号；或更多但多出来的形参都有默认实参，且（被选中时）这些默认实参来自唯一的宿主作用域（C++26）。
    - 约束：主要影响类模板的非模板成员函数；函数模板的约束在推导阶段就已检查。
    - ICS：引用绑定的左右值限制会让候选不可行；访问性、deleted、位域、窄化、explicit、歧义转换都不影响可行性。
